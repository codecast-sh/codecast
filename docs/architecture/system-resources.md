# System resources and guided offload

The daemon samples macOS and Linux every 30 seconds, reusing the session resource monitor's process snapshot. Only one collection may run at a time. Each OS probe has a caller deadline and an in-flight gate: a child that is slow to exit cannot hold up a report or spawn duplicate probes. It reports normalized machine CPU, load, memory availability (an estimate on macOS), OS memory pressure where available, compression/swap, disk and physical-interface network rates, process counts and attribution. Unsupported measurements remain absent. If process enumeration times out, machine telemetry still reports with an absent process count and no attribution; existing session metrics are preserved. Process CPU uses one-core percentages and can exceed 100%; machine CPU is normalized across all cores.

`systemResources.ts` assigns a process to its nearest known session ancestor. Multiple sessions sharing a root appear as shared ownership, counted once. Group totals cover the entire process table; detail is bounded to the largest 256 resident processes, with the omitted count exposed. Only executable names are transmitted, never command arguments or full paths. RSS includes shared pages and must not be described as reclaimable memory. Detached services and browser/simulator state may stay local after a session moves. Thread counts and per-process I/O are currently unavailable.

`machineResources.report` accepts an authenticated daemon report only for a registered device belonging to that user, respecting a token's device binding. Numeric and payload bounds are validated before storage. Each device keeps its latest report and at most 120 history points from the last two hours, throttled to at most one accepted report every 15 seconds. `listMine` exposes only the signed-in owner's registered machines. The web reads the registered `machineResources` store collection; the sync host owns its subscription.

A pressure incident requires at least three high samples spanning a minute. Recovery requires three healthy samples spanning another minute, at lower CPU/load thresholds; a gap over 90 seconds breaks continuity. Offline or stale reports cannot drive recommendations. High load alone does not establish CPU saturation. The dashboard's dismiss control supplies a cooldown without changing telemetry.

`buildOffloadPlan` ranks exclusively attributed Claude sessions by disruption and observed resource use. Pins, unsupported harnesses and shared ownership are not offered. `evaluateOffloadRequirements` is shared between the planner and the server: observed Apple tooling requires macOS; attached browser/app/simulator state and known failed host prerequisites block moves. Unknown project portability, credentials, services and local dependencies remain explicit user attestations, never verified facts.

`resourceOffload.start` serves both dry-run preflight and execution. In one transaction it rechecks authenticated ownership, current device placement, pins, unfinished children, process sharing, fresh source measurements, host requirements and aggregate memory for each selected destination. Every currently pending prerequisite must appear verbatim in the user's attestation list. Execution reuses `performCreateBatch` with `interrupt_on_timeout: false`. Both the runner and backend enforce that policy: a busy timeout fails the row while leaving the session running, and an older runner cannot force-quiesce it. Retry must pass this same resource preflight again. The existing migration rail handles cancellation, fencing, file transfer and destination resume.

The start action paints one optimistic batch per destination with a stable client-generated `mg-` identifier. The existing local-first list machinery preserves these rows across older snapshots and replaces each with its same-ID server echo. Replaying the same intent returns the recorded batches instead of starting new moves. Validation refusals are durable failed rows and enqueue no daemon commands. Each batch retains its original intent for a newly validated retry; the generic migration retry endpoint refuses resource-offload batches. Cancellation paints immediately, protects its exact acknowledgement timestamp, and accepts authoritative row progress. Cancel is unavailable during initial preflight, before a server batch exists.

Rollout requires deploying the backend before shipping the web subscription and releasing/restarting the updated daemon for telemetry. Older daemons produce an honest cold-data state. No production deployment, real session migration, or host provisioning is needed for fixture verification. Backend tests exercise real Convex schema/authentication and safe batch creation; UI fixtures exercise pressure, stale/empty states, attribution and offload review without moving real work.
