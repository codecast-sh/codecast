## 4. Delegation, review, decisions, and lifecycle

### Existing rails and proposed flow

**Existing, from the reviewed source.** Task bindings, pending messages, daemon commands, decision records, and session state already move work through Codecast. Some native processes are discovered after launch. Existing message delivery does not prove a manager processed the message. These mechanisms do not already provide the admission and authority contract below.

**Proposed.** Every managed transition uses the records in section 3. The server authorizes internal effects in a transaction. An isolated execution gateway mediates external effects as described in section 5. A local observer can recommend the same steps, but cannot promise to enforce them against a hostile process on the host.

### Adopt and delegate a task

The first project lead starts in observe/recommend mode. A human selects the project and tasks, checks source access, chooses the responsible person and host, and reviews the proposed budget. Saving the preview records explicit consent. Existing sessions remain manual unless separately adopted. A reporting link is not consent to send instructions, stop a process, or move its inbox card.

A delegation request names a task, acceptance criteria, evidence requirements, runtime capability, and operation identifier. The task's canonical project and plan bindings determine scope. A specialist request retains one accountable lead; a second role receives a narrow request and does not become another manager. A lead cannot create a task in a sibling scope merely because both projects share a workspace.

The proposed `admitTask` transaction performs these steps:

1. Authenticate the principal and check its current generation, grant revision, scope, and consent. Validate task access separately from role membership.
2. Read the expected task execution revision. Refuse a live claim or an expired claim whose external execution remains uncertain. Confirm that the requested adapter can enforce the selected management mode.
3. Resolve the bounded canonical ancestor path. Check role and workspace admission accounts, the device capacity row, account quota eligibility, and the required reservation. Queued permits consume capacity.
4. Create the conversation metadata, immutable origin, permit, task claim, task-history entry, and launch command. Increment authoritative counters in the same commit. Stamp policy, consent, topology, and attribution revisions on the permit.
5. Return the accepted operation receipt. The client replaces its provisional row by operation identifier. Failure returns a reason and removes the pending claim without inventing a completed launch.

Concurrent requests conflict on the same task and shared budget rows. Only one task claimant commits. A retry with the same identifier and arguments returns its prior receipt without another attempt or charge. A request declined for capacity may be retried after capacity changes, using a new identifier. Repeating the original request retains its original refusal.

### Dispatch and confirm a start

A dispatcher leases the command and moves its permit from `queued` to `starting` in one transaction. Immediately before launch, it validates the role generation, task generation, policy, consent, and account eligibility again. The gateway uses `launch_token` as its idempotency key and persists an external execution identifier before reporting `running`.

A command lease is scheduling ownership, not proof of process uniqueness. If the dispatcher crashes before receiving the launch result, mark the permit `uncertain`. Another dispatcher queries the gateway by launch token. Finding an execution attaches to it. A definitive absence permits retry. An adapter that cannot distinguish absence from a lost response cannot safely replay a launch and does not qualify for managed starts.

A lost heartbeat retains the capacity reservation. A reconciler confirms termination or keeps the permit uncertain. Task lease renewal requires the current task fencing counter and authenticated execution identity. After lease expiry, old task writes fail even if its process continues. A new executor is admitted only after the old execution is fenced at the gateway and its process or effects are reconciled. This avoids treating elapsed time as a kill acknowledgment.

Every start path must use admission: ordinary spawn, fork, trigger, refill, resumed compute, model turn, and native helper launch. Retrospective daemon discovery labels an unpermitted process unmanaged. It cannot retroactively make its launch safe. A managed adapter must disable native helpers or intercept them before creation.

### Report with evidence, then review

A worker's state update reports its next actor and current situation. It does not complete the task. The report mutation validates the active execution and stores claims, evidence references, source revisions, observed times, and limitations in task history. It changes a managed task to `in_review` and inserts the review event in the same transaction.

The task may remain in review after the worker process stops and its capacity is released. The completion proposal survives in `completion_history_id`. A later review compares both task revision and evidence revision. If another attempt changes the task or replaces the evidence, an old approval fails with `REVISION_CONFLICT`.

An independent review policy requires a reviewer principal different from the executor and outside its delegated credentials. Another conversation controlled by the same executor does not satisfy independence. The server checks the reviewer assignment, resource access, and current authority. Where meaningful independence cannot be provisioned, a human reviews. A managing role that implemented the work cannot approve its own report under this policy.

The reviewer examines artifacts and reproduces relevant checks. Acceptance writes the verdict, reviewer identity, reviewed revisions, task completion, and parent event atomically. Rejection appends specific unmet claims and leaves the task unfinished. Further implementation requires a valid execution claim and compute admission. A reviewer does not silently restart the old worker by sending an unbudgeted message.

A role report links these records rather than treating completed-task percentage as proof of quality. It distinguishes verified results, worker claims, stale evidence, unresolved effects, and coverage gaps. Digests read only material visible to their destination. Private source text must never enter a broad model prompt in the hope that its output will omit it.

### Decide without delaying human asks

A decision has a typed answer authority. A protected or unknown request is assigned to the responsible human at insertion. That same transaction makes it visible in the human queue and creates its notification outbox. The queue never waits for a lead to recommend, forward, or finish a model turn.

For an ordinary coordination question, route to the nearest available role authorized for that class and resource. Keep the task's assigned reporting role unchanged. A vacant or paused role is skipped only when computing this escalation destination. The human can inspect and take any routed question. A genuine runtime permission prompt also escapes folds, regardless of a session's origin or automation mode.

A recommendation appends a bounded hop and leaves human answer authority intact. An ordinary role answer compares the question revision, assignee generation, and policy. Answer, audit hop, and pending answer delivery commit together. Duplicate answers return the original receipt. Competing answers resolve by revision conflict, never last-writer replacement.

An action approval additionally binds the concrete resource, argument hash, resource revision, audience, policy revision, and expiry. Editing an option invalidates prior approval. Free-text approval of an approach does not authorize a deployment, purchase, or message to another person. Section 5 defines the gateway check.

Timeout processing pages the decision deadline index. Each mutation advances one decision to an eligible ancestor or the human and records why. Upward routing is bounded; no automatic downward bounce exists. A missing recommendation is acceptable when it would delay escalation. Repeated equivalent questions can be shown together, but remain distinct requests unless they share an exact operation identifier.

A human override cancels pending authorization and dispatch where cancellation is still possible. If dispatch started, set the effect to uncertain and reconcile. If an effect completed, record a corrective request with evidence of what happened. Do not automatically undo database changes, revert unrelated commits, or claim that an override erased an external action.

### Wake events and acknowledgment after effect

A wake key is a tuple encoded canonically: `(source_type, source_id, source_revision, kind, destination_role_id)`. Two settles at different revisions create two events. Replaying the same source revision creates one. A destination role, rather than its current conversation, owns the event across rotation.

The source transition and event insertion commit together. A scheduler pages ready events, checks audience and current destination authority, and leases at most 32. It creates an immutable pending-message batch. Several routine changes may share one turn, but every event remains recorded. An active lead reads its inbox at a safe yield rather than receiving repeated interruptions. Coalescing delay is configurable; urgent human delivery bypasses it.

Processing uses deterministic operation identifiers derived from event identity and effect kind. For an internal effect, `applyRoleEffect` checks all fences, applies the change, stores the effect receipt, and acknowledges the event in one transaction. For an external effect, it first records a dispatch intent. Only reconciled completion can acknowledge successful processing. A durable cancellation or explicit human deferral can also close processing, with that disposition recorded.

If transport succeeds but acknowledgment is lost, delivery may repeat. A new consumer reads the receipt and acknowledges without repeating the effect. Several external effects for one event have separate identifiers; the final acknowledgment requires all dispositions. Sending a message to a pane is not sufficient evidence.

Retries use bounded exponential delay and an attempt limit. Use a retry delay of `min(retry_base_ms * 2^attempt_count, 300000)` with bounded jitter. The selected policy records attempt limits; the pilot must measure them before choosing defaults. Exhausted retries create a visible dead letter with replay and reconciliation controls. Routine budget exhaustion leaves events pending. It does not drop them or allow free recommendation turns. A non-model path stores human questions and emergency-stop requests even with zero compute allowance.

Loop controls bound sends per ordered principal pair, total role wakes, and causal depth. Persist window counters in budget account subjects such as `send:<from>:<to>` and `wake:<role>`. Agent-authored chat never wakes another bot. A refusal records a terminal control event that does not itself trigger the same model wake. Backlog size and oldest event age remain visible.

### Pause, hibernate, vacancy, and rotation

Pause changes routing. It stops routine managed dispatch to the role, preserves its inbox, and sends urgent asks to the human or an eligible escalation target. It does not prove the process stopped. Resume routing requires current consent and policy, then drains retained events through normal admission.

Hibernate changes physical execution. A daemon command checkpoints if reserved capacity permits, stops the process, and records acknowledgment. Only confirmed termination releases its runtime capacity. The anchor remains occupied by the same conversation unless the operator also vacates it. Waking a hibernated conversation requires a new admitted resume and current credentials. Routing can be paused independently.

Vacancy removes the current role occupant. Killing a role conversation increments its generation, revokes its capability, and clears `conversation_id` in one mutation. Child reporting edges and provenance remain unchanged. This action does not stop the subtree. Workers retain their own bounded execution authority; a replacement lead can manage them after reading current claims. Any request carrying the former lead's capability is rejected.

The vacancy mutation records a reconciliation event rather than rewriting every decision and pending message. Readers immediately treat the role as unavailable. Bounded workers reroute ordinary decisions and redispatch unacknowledged events. Protected asks were already with the human. A stale consumer cannot acknowledge an event after the generation changes.

Rotation combines vacancy and replacement while preserving the role identity. An optional handoff captures current claims, evidence, open decisions, and uncertain effects. A dead role can be replaced without a handoff. A compare-and-swap advances generation and selects one replacement; launch follows admission. The old session cannot reclaim the seat by waking first. Its token, pending commands, state writes, task actions, answers, dispatches, and acknowledgments all face the generation fence.

### Revocation, scope moves, and retained work

Membership revocation first invalidates the principal's access epoch and prevents new reads and dispatches. Server transactions recheck current resource ACLs. Removal events clear replicas and derived summaries. A gateway rechecks before dispatch; an already dispatched effect is reconciled, since permission changes cannot retract bytes already sent. Revoking a person does not silently choose a new responsible human. Unassigned responsibility is a visible blocker.

Reparenting begins with a human preview of affected tasks, audiences, budgets, and running or uncertain permits. The first managed pilot rejects moves with active execution. A later migration may freeze admissions, increment topology and grant revisions, and page through bindings with a durable cursor. Each page validates the expected scope revision. A concurrent binding edit becomes a conflict, not a silent rewrite. Finalization requires all pages reconciled before admissions reopen.

Old receipts and permit attribution paths never move. New work uses the new path. Existing permits finish or reconcile against the path reserved at admission; moving a project cannot erase a parent's liability. Changing workspace requires a separate visibility migration and explicit consent, not merely a parent-pointer edit.

Retirement stops new admissions and preserves decisions, receipts, and role history. A subtree stop requires an explicit preview and only affects sessions covered by managed consent. Existing containment behavior remains separate from reporting. No lifecycle transition deletes a worktree. Retention may archive verified clean work after a policy period. Dirty files, unmerged commits, pending approvals, and uncertain effects block automatic archival cleanup. Destructive deletion remains a separate human-authorized action.
