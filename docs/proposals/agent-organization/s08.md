## 8. Failure cases, tests, and evaluation

### What this section can establish

**Existing, from the source review.** The repository has source guards, shared projection tests, mutation fixtures, and daemon tests using a messaging harness. They provide patterns to extend. Their existence does not mean the proposed organization contract has been implemented or tested.

**Proposed.** Acceptance requires observable behavior under concurrency, partial failure, malicious requests, and mixed clients. A source check can flag a forbidden write site, but cannot prove token isolation, transaction semantics, or external idempotency. The tests below are implementation gates. No benchmark result or rollout success is claimed here.

### Failure matrix

Every case needs a server assertion and a visible outcome where applicable. Use synthetic scopes and accounts. Never run destructive fault tests against production resources.

| Failure | Required behavior and meaningful test | Visible result |
|---|---|---|
| Duplicate admission | Submit one operation concurrently and replay after response loss. Assert one permit, claim, launch count increment, and command. | One accepted request receipt. |
| Simultaneous task claim | Two authorized principals claim the same execution revision. A real transaction test must yield one winner. | Losing client removes its pending claim and shows the conflict. |
| Shared ancestor exhaustion | Two sibling requests each fit alone. Commit them concurrently. At most one may consume the remaining ancestor balance. | Refusal names the permitted budget scope. |
| Queued launch oversubscription | Hold dispatch while filling all device slots with queued permits. Another admission must fail before process creation. | Queue and held capacity agree. |
| Crash before launch acknowledgment | Kill dispatcher after gateway creation but before response storage. Reconcile by launch token. | One external execution, possibly an interim uncertain state. |
| Expired lease with live process | Advance time without terminating the process. Assert no capacity release or replacement executor admission. | Uncertain execution needs reconciliation. |
| Stale generation | Rotate a role, then attempt state, claim, answer, dispatch, policy edit, and acknowledgment with its old token. Reject every role effect. | Expired role authority, with no false current state. |
| Old resume versus refill | Race old-session resume against replacement CAS. One current generation wins; the old session cannot reclaim the role. | Stable role identity and unchanged spawn origin. |
| Duplicate wake | Insert the same source revision and destination twice. Assert one event. Replay delivery and assert one effect receipt. | One logical action, with retry audit. |
| New revision suppressed | Emit two settled transitions for the same conversation at different revisions. Assert two events survive coalescing. | Both revisions visible in event history. |

### Transaction and runtime gates

Use pure tests for scope resolution, bounded paths, immutable attribution, cost arithmetic, audience intersections, and inbox placement. Generate graphs with missing role levels, invalid edges, cycles, and absent membership. Assert that no invalid graph grants more access. Property tests should vary event order and duplicate count, not merely compare one prepared snapshot.

Use a transactional test environment for claims, quotas, generation changes, answer revisions, and receipt settlement. A fake database that serializes every request cannot establish that concurrent admission is safe. The test must make competing transactions read the same initial state and verify the committed invariant after retries. Assert both row contents and side effects: a refusal cannot leave a hidden command or reservation.

Run gateway and daemon integration tests with controlled launch and receipt adapters. Inject crashes before dispatch, after external creation, before receipt commit, and after receipt commit. Persist the simulator's external execution registry across dispatcher restart. Otherwise the test cannot distinguish a second process from the first process rediscovered.

Exercise real CLI entrypoints for spawn, fork, trigger, resume, and native helper requests against the test gateway. Inspect process count as well as conversation rows. For isolated runtime qualification, attempt credential reads, host-browser access, unauthorized network calls, and use of legacy endpoints. Run the same suite per adapter version. Unsupported paths must be denied or marked observed before the managed pilot.

Source guards remain supplemental. They can prohibit raw managed-claim writes outside the admission helper, access decisions based on `team_id`, provenance rewrites, or component subscriptions to registered feeds. A passing text search does not prove the helper checks the correct principal or that a tool cannot bypass it.

### Adversarial simulator sequence

Use a seeded clock, deterministic identifiers, and an event log that records committed mutations and simulated external effects. All counts and dollars in this scenario are illustrative. Seed one workspace, project role R at generation 7, a plan scope without its own role, tasks A and B, and an isolated test adapter. Give the project two process slots and a $12 allowance. Begin with $4 settled and no reservation.

1. Two clients claim A with different operation identifiers at the same task revision. Each requests a $3 bound. Expect one active execution, one queued permit, one launch command, $3 reserved, and one `CLAIM_HELD` refusal. Task history records one admitted attempt.
2. Claim B with another $3 request. Expect two held slots and $6 reserved. A third launch is refused by capacity. The budget accounts remain at $4 settled plus $6 reserved, not $9 reserved.
3. Dispatch A, create its external process, and crash before the gateway response reaches the server. Expect an uncertain permit. Restart dispatch and query the same launch token. Expect attachment to that process, not a second launch or freed capacity.
4. Emit A state revisions 11 and 12, then replay revision 12. Expect two `role_events` rows for R and one immutable delivery batch containing both. The batch identifier links the pending message to those rows.
5. Process revision 11 into a task-history report, commit its effect receipt, and drop the response. Redeliver. Expect the existing receipt to satisfy processing and no duplicate report. Revision 12 still needs its own disposition.
6. Insert a production approval request from B while exhausting the remaining ordinary turn allowance. Expect one human decision and notification outbox without a model call. Hold all recommendation work. The human can still answer the exact request.
7. Vacate R and advance it to generation 8 before its old consumer acknowledges revision 12. Expect the old acknowledgment to fail and the event to remain available for a future replacement. Spawn origin and task reporting role remain unchanged. New role compute still requires available capacity.
8. Through the authenticated human control path, submit a gateway dispatch using approval for a different resource revision. Expect refusal with no gateway call. Restore the exact approved revision, dispatch once, and lose its response. Expect an uncertain effect until outcome lookup returns its receipt.
9. Settle A at $2.50 and B at $1.50 with termination confirmed, then replay both receipts. Expect $8 total settled, zero remaining reservation, and zero held task-process slots. Daily task-launch admissions stay at two. A replacement role session can now obtain its own separately counted admission.
10. With no active permits in the moving scope, try a scope move, then create a new admitted request after the move completes. Existing receipts retain the old path. The new permit carries the new topology revision and attribution path.
11. Revoke a source audience before a queued digest is delivered. Expect delivery cancellation or safe regeneration, removal records for replicas, and no private digest input reaching the model.
12. Mark A complete after independent review, leave an unmerged commit in its worktree, and advance retention. Expect the completion record to survive and the worktree to remain protected.

After every step, compare claims, permits, budget balances, event status, effect receipts, decisions, and client projections. Assert that all retained reservations have an explainable permit and that no acknowledged event lacks a durable disposition. Export the seed and transition log on failure so the sequence can be replayed exactly.

### End-to-end paired evaluation

Run the deterministic scenario through the real server, daemon, CLI, browser, and mobile UI in a scratch workspace before enabling managed execution. Verify clicks and rendering, including collapsed roles, offline pending requests, human ownership, stale counts, and permission prompts. Shared projection fixtures do not prove native mobile implements nesting or cache invalidation.

Evaluate usefulness separately from mechanical correctness. Collect seven working days of baseline observations before setting rollout defaults. Then run small paired tasks with similar scope and difficulty: human coordination versus an observed lead, followed by a managed lead only after its capability gates pass. Alternate ordering, use equivalent task sets where replay would reveal the solution, and keep reviewer judgments independent of the tested role.

Measure human attention time, manager compute overhead, unresolved escalations, missed critical asks, quality-adjusted outcomes, and unpriced usage coverage. Record task difficulty and evidence completeness. Do not treat a low override rate as proof of correctness: humans may miss bad recommendations or accept them without inspection. Investigate every missed critical ask and unauthorized effect separately from average performance.

Report quality is the match between claims and evidence, freshness of that evidence, and coverage of the actual work. A report with 90 percent of tasks marked done can still omit the only production blocker. Review sampled claims against source artifacts and revisions. Score unsupported assertions, stale evidence, missing critical constraints, and truthful uncertainty. A shorter report that exposes an unresolved effect can be better than a complete-looking task summary.

### Performance targets and release decisions

The following are proposed targets, not measurements. Under a synthetic load of 100 active executions, 1,000 pending routine events, and three standing role levels, target p95 admission below 500 ms excluding external launch time. Target protected asks visible within two seconds of server commit for an online client. Target routine dispatch within ten seconds when budget and capacity exist, with a configurable coalescing window inside that allowance.

Keep each hot mutation within the bounded reads and writes in section 3. Target no growth in admission work with total historical conversations. Measure contention, retries, event backlog age, browser rerenders, and mobile memory. Benchmark large histories separately from active execution counts. Do not borrow unrelated machine-load anecdotes as evidence that these targets are met.

Gate observation on privacy and truthful reports. Gate managed project pilots on authenticated actors, claims, admission, event recovery, independent review, and adapter isolation. Gate wider hierarchy and automation on paired evaluation and operational evidence. A failed safety case blocks the affected capability, even if average latency and completion counts look good.

Rollback disables new managed admissions and preserves outstanding permits, receipts, decisions, and human controls. Continue reconciliation until liabilities are resolved. Do not erase the ledger, clear reservations because the feature flag changed, or kill unrelated sessions. Record which guarantee failed and which modes remain usable. The release decision must name tested coverage, remaining unknowns, and the evidence supporting it.
