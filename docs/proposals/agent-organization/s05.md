## 5. Authority, runtime limits, and budgets

### What can be enforced

**Existing, from the architecture review.** CLI authentication identifies a user and token, not a session principal. Native runtimes can launch detached processes. Account heartbeats report account windows, while transcript messages may contain model and token usage. None of these facts establishes isolated worker authority, complete usage coverage, or a hard monetary cap.

**Proposed.** Offer two honest modes. An observed role on a trusted local machine produces scoped reports and recommendations. Managed execution requires an isolated runtime, a scoped principal, mediated effects, and supported admission controls. No existing Claude, Codex, or other adapter is assumed to satisfy those requirements merely because it supports spawning or reports tokens.

A human sharing a workstation with an unrestricted agent cannot rely on a prompt to protect credentials. The agent may read configuration, launch another CLI, reuse a browser session, or call a provider directly. Server checks cannot stop an effect that never reaches the server. Local observation is useful, but its cooperative limits must remain visible.

### Actor authentication and current authority

A proposed scoped token contains signed claims `{principal_id,actor_kind,role_id?,session_id,generation,workspace,audience,scope_ref,expires_at,grant_version,access_epoch,permit_id?}`. For a role principal, `role_id` and the current anchor generation are required. For a worker, `permit_id` is required and generation is its task fencing counter; its reporting role is attribution, not the worker's credential owner. `actor_kind` is `worker`, `role`, or `service`; the token cannot claim human authority. Tokens are short lived and audience-bound. `--from`, session identifiers, `acting_user_id`, and origin fields remain attribution only.

Store revocation state in proposed `execution_principals`: `principal_id`, `actor_kind`, `role_id?`, `permit_id?`, `delegation_root_id`, `session_id`, `generation`, `workspace`, `scope_ref`, `grant_version`, `access_epoch`, `audience`, `expires_at`, `revoked_at?`, and `credential_key_id`. Index by `principal_id` and `role_id,generation`. No raw token enters a synced record or transcript. A service authenticates its own dispatcher role and does not impersonate a worker by changing request arguments.

Every managed mutation checks the token signature and audience, then loads current principal, applicable anchor or task fence, policy, consent, and target access. The check and internal write occur in one transaction. Equality of generation is required, not merely a lower-bound comparison. Historical ownership, a device identifier, or a plausible session name cannot replace the check.

A reviewer assignment requires a different `delegation_root_id` from the executor. Only the human control path may provision an independent reviewer root; workers cannot mint one by opening another session.

A human-only endpoint uses a distinct control channel whose credentials are unavailable to the managed runner. Browser login alone is insufficient if the runner controls that browser. Sensitive confirmation binds the exact operation through this channel. Legacy host-token endpoints cannot offer an alternate path to mutate managed claims, grants, approvals, or permits. During migration they must reject those writes or delegate to the same verified control path.

Grants narrow resource authority. Workspace access, resource ACL, role scope, and allowed operation must all pass. Visibility of a team project does not imply permission to stop its sessions. Parent scope does not grant membership in private rooms or `#standup`. A chat request from a human creates a preview of scope, adopted tasks, allowance, and sensitive effects. Confirming that preview creates one operation keyed to the source thread message and its revision.

### Protected effects and approvals

Protected classes are purchases and billing, destructive data changes, production changes, auth and access changes, external communication, and unresolved user-facing product choices. Ordinary coordination includes choosing among already authorized implementation approaches or scheduling an allowed retry. A question labeled `approach` can still request a protected effect. The gateway classifies the concrete operation and resource, rather than trusting the label.

Unknown operations require human review and remain disabled if no safe execution adapter exists. Keywords may flag suspicious prose for review. They never grant authority, prove the absence of a protected effect, or secure shell access.

An approval binds operation, exact resource, argument hash, resource revision, policy revision, destination audience, expiry, and permitted principal. A mutation that changes any of these requires a new approval. Approval of a production deployment does not also approve deletion of a database or a message announcing the release. An ordinary answer and its rationale grant no implicit external capability.

The gateway validates the approval immediately before dispatch and records its operation identifier. Internal authorization and dispatch intent commit together. External success cannot share the database transaction, so the gateway records a receipt or an uncertain outcome. It retries only when the provider supports idempotency or reconciliation proves no effect occurred. Human overrides cancel pending intents. Completed effects require an explicit corrective action.

Compute allowance is a separate permission. It may fund model turns within an approved budget. It does not authorize buying subscriptions, increasing provider limits, provisioning paid infrastructure, changing billing, or sending email. A budget increase and a purchase approval are different operations with different targets.

### Sandbox and adapter capability matrix

Managed isolation must deny access to host tokens, the human browser profile, production secrets, and unrestricted host filesystem paths. Filesystem writes are restricted to approved workspaces. Network credentials and effectful services are reached through gateways. Native child processes and tools are either mediated before execution or disabled. An adapter unable to impose these restrictions remains observed.

The following matrix is a proposed qualification scheme. “Eligible” means eligible after the tests in section 8, not supported by an existing adapter today.

| Runtime configuration | Scoped identity and secret isolation | Launch and turn admission | Monetary guarantee | Managed eligibility |
|---|---|---|---|---|
| Existing unrestricted local CLI or native harness | Not established by the review | Direct starts can bypass admission | Estimates where usage is available | Observer only |
| Isolated runner with uncontrolled provider or native tool access | Possible, must be verified | Incomplete if children or continuations escape | No hard USD claim | Observer until bypasses close |
| Isolated runner with every launch mediated, but incomplete pricing | Required and tested | Hard counts for mediated starts and turns | Estimated totals with explicit missing coverage | Eligible only with human consent to estimated mode |
| Isolated runner with bounded provider requests and effect gateway | Required and tested | Every entrypoint admitted | Hard bound only for covered requests and charges | Eligible for declared coverage |
| Adapter whose result cannot be reconciled after a lost response | May be isolated | Uncertain starts retain reservations | Uncertain liability remains held | No unattended replay; qualification fails where replay is required |

Each adapter advertises versioned capabilities: `scoped_credentials`, `secret_isolation`, `launch_idempotency`, `termination_confirmation`, `turn_admission`, `child_admission`, `effect_mediation`, `usage_receipts`, `charge_bound`, and `outcome_lookup`. The server validates a tested capability revision, not a self-reported claim from a worker. Downgrades block new managed admissions while existing liabilities reconcile.

Hard launch concurrency covers admitted executions only. A human can still overload a shared machine outside this system. A device-health refusal can stop further admissions, but cannot manufacture control over unrelated host processes. Worktrees are retained artifacts, not interchangeable units of process capacity.

### Reservations before compute

All queued, starting, running, and uncertain launches occupy capacity at the role's applicable ancestors and device. A queued launch is already a reservation, so two daemons cannot both consume the last slot. Admission also increments daily launch count. A cancelled admission releases capacity and unused money after reconciliation; it does not erase the admission from the daily count and invite unlimited launch churn.

Each model turn, trigger wake, resume, fork, and supported native helper requires the relevant permit before spending. A long-lived process does not gain unlimited autonomous turns from its initial launch permit. A new turn can reserve money without taking another process slot. Permit kinds make the distinction explicit.

For each applicable ancestor, enforce:

`settled_usd_micros + reserved_usd_micros + request_usd_micros <= limit_usd_micros`.

The admission transaction checks every account independently. A minimum of nominal limits is insufficient because siblings have already spent different amounts. Capacity and daily counters use analogous checks. Ancestor budget rows exist even where no standing role occupies that scope. Skipping a manager does not skip the workspace budget.

**Illustrative example, not measured usage.** A workspace allows $100 for a period, a project $40, and a plan $20. Workspace settled spend is $70 with $15 reserved. The project has $20 settled with $12 reserved. The plan has $8 settled with $4 reserved. A request bounded at $6 yields totals of $91, $38, and $18. All three checks pass.

After that reservation, a sibling plan requests another $4. Its own account might have ample room, but the shared project now has $20 settled and $18 reserved. Adding $4 would reach $42, so admission fails. No permit or task claim is created. The workspace's larger limit does not rescue the project.

For an illustrative count check, suppose workspace, project, plan, and device hold 5/8, 3/4, 1/2, and 3/4 slots. The accepted launch takes them to 6/8, 4/4, 2/2, and 4/4. Another project launch fails even if a sibling plan has zero workers. These counts include queued starts and uncertain executions.

If the admitted $6 request completes at $4.50, settlement transfers $4.50 to settled usage and releases the remaining $1.50. Each ancestor applies the same unique receipt once. A duplicate receipt makes no change. The three views describe the same $4.50 charge; adding workspace, project, and plan totals together would triple-count it.

### Hard money bounds and honest estimates

A hard USD cap requires a defensible maximum charge before dispatch, covering the provider request, bounded output, applicable tools, retries, and billing rules. If the adapter cannot provide that bound, `hard_required` admission fails. The most expensive model currently in a price table is not an upper bound for an unknown model or future tool charge.

Estimated mode still enforces admitted launch and turn counts. It records priced estimates, authoritative charges where available, and missing coverage separately. A spend threshold can refuse further requests once known estimates exhaust it, but it cannot guarantee a dollar ceiling. Do not claim a universal overshoot bound of one heartbeat or one turn; those units have no known monetary maximum on an uncontrolled adapter.

Reservations for hard coverage include a small configured checkpoint allowance. It is charged against every ancestor when admitted, not invented when the main budget runs out. A checkpoint permit may use only that reserve for a bounded handoff. If no reserve remains, record status and the human decision without another model call. Emergency stop, approval storage, and reading the queue remain available at zero compute budget.

Already admitted requests may finish within their reserved bounds. Further requests are denied at the boundary. Emergency revocation may interrupt a running request; the design does not promise that every process always finishes. Unknown in-flight charges remain reserved until reconciliation rather than being released by a timer.

### Receipts, periods, and historical attribution

Transcript usage and provider or adapter receipts supply evidence. Account percentage windows describe account quota health, not session cost or pricing. Keep quota checks independent of estimated dollars. Respect the parent account's limits and provider restrictions. Do not create or switch to a fresh account to evade them. Reset or an explicitly permitted account change requires a new admission check.

Normalize receipt sources before settlement. Provider request identifiers take precedence over a matching transcript observation when they describe the same charge. A stable mapping prevents charging both. Replayed transcript lines deduplicate by source identity and revision. Cumulative counters carry an epoch and apply only validated differences. Resets start a new epoch; edits append correction evidence. Contradictory or unmatched observations remain incomplete rather than becoming guessed charges.

The receipt insert, normalized delta, permit settlement revision, ancestor balance updates, and bounded daily projections commit atomically. Corrections preserve prior evidence. Periodic rebuilds compare the projection with receipts and permits. They run in pages and cannot reset live admission counters beneath active permits. A mismatch freezes affected admissions until reconciled.

Each workspace policy selects an explicit timezone. Store concrete start and end instants for every period, including daylight-saving changes. All descendants use those period boundaries regardless of host location. Timezone changes take effect only at a future closed boundary, never by rebucketing today's spend. Concurrency uses lifetime capacity rows rather than resetting at midnight.

Book a request to the immutable scope and ancestor path captured by its permit. Receipt arrival after midnight or after a move still settles that original reservation. This admission-period budget view can differ from a provider invoice-date view; label them separately. A turn spanning a boundary retains its original period until it settles. New requests use the new period.

Scope moves affect future permits only. Old liabilities stay under the old parent even when the UI now groups the role elsewhere. A current-parent activity view can link historical charges, but cannot reassign their accounting. Work without a reliable admission binding stays explicitly unattributed or observed; the proposal does not fabricate a conversation workspace or claim complete historical coverage.

### Human control and visible limits

A budget edit records an immutable policy revision, effective period, reason, and authenticated human authority. Raising a child allowance does not raise an ancestor. Lowering a cap below settled plus reserved usage blocks new admissions and shows the existing commitment; it does not rewrite history or blindly cancel completed work.

The interface should distinguish settled charges, estimates, reservations, and unpriced coverage. It names the refusing ancestor or device only when the viewer may read it. Queue age, quota reset information, uncertain liabilities, and checkpoint availability explain why work is waiting. Warning colors are presentation choices, not alternative enforcement thresholds. No dollar amount, concurrency count, or automatic refill policy becomes consent merely by appearing as a suggested default.
