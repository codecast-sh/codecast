## 9. Rollout gates, implementation DAG, and launch decision

### Release by demonstrated capability

Begin with P0, the observer foundation. Release it when a human can add one project lead, review selected accessible work, and understand a supported next step within the proposed first ten minutes of adoption. Observation does not authorize workers. Existing sessions remain manual unless their owners explicitly adopt them.

Managed execution follows separate gates. Claims, authenticated identity, admission, and durable wakes must all work before a project lead can direct execution. Project experience must demonstrate value before plan leads expand the hierarchy. No calendar promise substitutes for these gates.

| Gate | Required proof | Permission unlocked |
|---|---|---|
| P0: useful observer | Correct scope and owner, authorized evidence, honest missing data, actionable brief, store rendering | Observation requested by a human and recommendations |
| P1: managed execution foundation | Scoped credentials, protected effect checks, exclusive attempts, reservations, receipts, reliable events, recovery | Controlled testing with synthetic workers |
| P2: supervised project pilot | Approved intake through independently verified result; mobile intervention, denied access, stale clients, and rollback tested | Selected managed tasks in one approved project |
| P3: optional expansion | Paired evidence of reduced human effort with acceptable quality and total cost coverage | Explicitly approved plan lead trial or additional project |

### Pilot scope and operating limits

The first pilot should use one project, one lead, selected tasks, and a named responsible human. Choose work with reproducible criteria and reversible local artifacts. Keep production changes, purchases, destructive actions, auth changes, and external communications as protected requests outside worker authority. Existing human sessions remain independently controlled. Do not bulk adopt a project's historical sessions.

Use a supported isolated runtime for managed work. Record the billing account, device, allowed tools, compute allocation, concurrency limit, and review classes before admission. Where metering cannot establish reliable priced exposure, stay in observation or use a separately authorized supervised test that clearly discloses the limitation. Uncontrolled native tools offer an estimated meter and launch cap only. They do not provide a hard money cap.

Admission must check `settled + reserved + request <= limit` at every ancestor. Queued and starting work count. Receipts settle each usage event once. Rollups display the immutable attribution path without charging it twice. Daily periods use an explicit workspace timezone fixed for that period. Unknown costs remain visible, including the fraction of activity that could not be priced.

### Compatibility, deployment, and rollback

Implementation should add compatible fields and read fallbacks first. Existing anchors retain behavior until explicit adoption. Legacy decisions keep their human route; missing classification is unknown. Do not backfill old questions as ordinary approvals. An old client may read safe compatible state, but cannot acquire managed authority through missing actor or version fields.

Release the backend through `packages/convex/deploy.sh` before a client calls new functions. Ship the required CLI adapters before enabling managed execution on a device. Web and native mobile oversight must be ready before managed workers depend on nesting. Shared projection changes alone do not satisfy mobile acceptance. These are future deployment requirements; this proposal performs no deployment.

Rollback disables new managed admission and returns pending human obligations to visible human routing. Existing approved attempts are inspected and either allowed to finish within their authority or stopped through an explicit control. Preserve tasks, evidence, decisions, receipts, lineage, and unresolved effects. Revoke old capabilities and fence stale sessions. Never delete dirty worktrees or unmerged commits as rollback cleanup.

The operator must be able to store a human answer and request emergency stop when the compute allowance is exhausted. Completed external effects require reconciliation. Retrying a stopped or uncertain operation must not repeat a purchase, message, or deployment blindly.

### Dogfood measurement

All baselines are unknown until measured. Observe seven working days before choosing improvement targets. Then use small paired runs with comparable scope, acceptance criteria, runtime, model, and review policy. Compare direct execution and simple routing with lead coordination. Record mismatches between pairs and avoid interpreting a small sample as proof of broad savings.

| Measure | Required interpretation |
|---|---|
| Human effort | Time reading, deciding, locating evidence, correcting, and recovering per accepted outcome |
| Quality | Independent sample of results and answered decisions; reopened work, missed criteria, and unresolved concerns |
| Missed critical obligations | Critical obligations not surfaced correctly, divided by independently identified critical obligations |
| Escalation | Unresolved count, age, next actor, and reason; high escalation does not imply grants should widen |
| Manager overhead | Coordination turns, review delay, and lead compute in addition to worker execution |
| Total cost coverage | Priced and unpriced usage, reservations, provider coverage, and cost per comparable accepted outcome |
| Operational reliability | Duplicate effects, stale claims, backlog, dead letters, intervention success, and recovery time |

Splitting one outcome into more tasks must not improve its score. Sample correctness even when nobody overrides a lead. Let humans inspect any worker; enforced folding would corrupt the attention measurement. Record compute and human review costs together. Machine load may be diagnostic, but provides no guaranteed product benefit without matched workload and hardware.

### Founder decisions before each gate

These six choices are proposals with recommended defaults. Silence approves none of them. Protected human control and privacy are technical prerequisites.

| Decision | Recommended proposal | Required before |
|---|---|---|
| Initial pilot | Choose one project with bounded local work and an available owner. Consider Codecast: Sync & Reliability only after reviewing the specific tasks and risks. | P0 adoption |
| Budget amount and billing host | Human selects the amount, period, payer, and runtime after reviewing coverage and available capacity. Leave money authorization unset until confirmed. | Any model run needing new allocation; P2 managed admission |
| Autonomy | Begin in observe mode. Enable managed execution only for selected tasks and exact grants after P1 and oversight checks pass. | P2 |
| Naming | Use “lead” and “worker” in product copy. Retain existing anchor implementation names where compatible. | Product review |
| Review classes | Require independent review for managed implementation completion and explicit human approval for protected effects. Refine ordinary review classes using pilot evidence. | P2 |
| Expansion standard | Set quality and human effort targets after baseline measurement, with explicit cost coverage requirements. Require explicit adoption of further leads. | P3 |

### Launch and no-launch criteria

Launch the observer only when scope, ownership, privacy, missing evidence, and the first useful recommendation pass their acceptance checks. Launch the managed project pilot only when every execution path has tested identity, claims, admission, wake recovery, and human intervention. Require exact approval and evidence versions, independent review where specified, usable mobile oversight, and a successful rollback drill.

No-launch applies if a worker can impersonate a human approver, bypass a protected effect boundary, spend through an unadmitted execution path, lose a critical ask, expose private evidence, duplicate an external effect, or hide an unresolved obligation. Unsupported hard cost claims also block launch. Remain at the last proven gate until corrected. Expand beyond the pilot only when paired measurements meet the targets chosen after the baseline, with no unresolved critical regression and enough cost coverage to judge the result.
