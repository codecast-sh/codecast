## 7. Product surfaces and interaction contract

### One consistent account of the work

Every surface should answer the same questions: what work is in scope, who is responsible, who acts next, what evidence supports the current claim, and what authority applies. Role names and scope chips provide navigation. Runtime status, automation mode, and next actor remain separate labels.

All displayed server state goes through store feeders. This includes audit history, digest fields, evidence previews, decision recommendations, metering coverage, and pending operation receipts. Global feeders follow the elected sync host. Histories for an individual view may load lazily, but feed a store collection before rendering. A component must not use a direct query as a second rendering source.

A populated cache paints immediately. A skeleton is appropriate only for a cold collection with no rows. Cached figures carry their freshness and coverage. A partial replica says “Loaded work only” or “Count incomplete.” A reliable server digest includes its source watermark, covered scope, checked time, and source links. Recorded counts can be accurate while a worker's completion claim remains unverified.

User actions update the store immediately as requested state. Confirmation requires a server receipt. “Pause requested,” “Approval submitted,” and “Launch pending” are distinct from “Paused,” “Approved,” and “Running.” Rejection reconciles the optimistic request and shows why. Revoked access removes restricted cached content across windows and mobile.

### Organization overview and level of detail

The organization overview should open at the scale needed for the selected workspace. Its initial list shows leads and meaningful obligations. Expand a lead to see adopted plans and workers. Open an individual row to see attempts, decisions, and evidence. A flat “All sessions” view remains available. Expansion is a personal display choice and never changes routing or consent.

| Level | Content | Interaction |
|---|---|---|
| Workspace overview | Lead, scope, mode, responsible human, next actor, open human obligations, data freshness | Select a lead or filter to work needing attention |
| Expanded lead | Adopted work, current worker attempts, review obligations, available escalation target | Open the task, lead, or independent human ask |
| Work detail | Acceptance criteria, owner, reviewer, current attempt, evidence and pending effects | Review sources or open the precise control |

The overview does not fill missing hierarchy levels with setup prompts. “Add project lead” is a single entry point. A project with no lead remains ordinary work. A vacant role stays visible with its reason, last confirmed session, and durable backlog status. It should not resemble an empty project.

The lead row should prioritize its own action state over its latest prose. Proposed copy: “Reviewing reported completion,” “Waiting for owner approval,” or “Coordination paused.” A quoted lead statement is marked “Lead report” and linked to its source. Counts show coverage and identify incomplete organization data.

### Lead detail

The lead detail opens with scope, responsible human, observation or managed mode, current session, and current next actor. Primary controls are “Open conversation,” “Pause coordination,” and “Review permissions.” Maintenance actions belong in a secondary menu.

“Pause coordination” explains that it stops new automated dispatch. Running attempts are listed separately. “Stop running work” previews eligible managed attempts and unresolved effects. “Hibernate process” describes runtime suspension. These controls must not collapse routing, process state, and consent into a single ambiguous pause button.

The detail contains adopted work, pending decisions, the latest evidence brief, permissions, usage coverage, and activity. The usage panel shows settled usage, reserved exposure, configured limits at each relevant ancestor, provider coverage, and the billing account. It names the limit that prevents admission. It never computes a single effective money limit by taking the minimum of ancestor limits.

The activity history reuses existing orchestration and task events alongside durable role events. Selecting an event opens its source and operation receipt. The brief editor separates human instructions from system facts. A saved brief shows whether the current session has acknowledged that version. Editing prose cannot widen a grant.

### Project, plan, and task integration

The project page is the main adoption surface. It keeps the existing project structure and adds a compact lead summary. The update stream can filter lead digests; there is no compulsory new standup destination. “Add project lead” opens the scope and access review with the current project selected.

| Surface | Required fields | Behavior |
|---|---|---|
| Project header | Human owner, lead, mode, next actor, latest verified result | Open the lead or review adoption scope |
| Plan header | Plan owner, dedicated or inherited coordinator, criteria, review state | Explain why the project lead coordinates when no plan lead exists |
| Task row | Owner, working session, reviewer, status | Preserve the assignee even when a worker starts |
| Task detail | Criteria, active attempt, linked history, evidence revision, unresolved concerns | Separate historical sessions from the exclusive execution claim |
| Conversation header | Actual session identity, work binding, observation or management relationship | Explain allowed coordination without implying transferred ownership |

A plan with no dedicated lead can read “Coordinated by the project lead.” A task completion claim reads “Reported complete” until the required verification occurs. “Verified against criteria” names the reviewer and checked revision. “Accepted by owner” appears only after the relevant human acceptance. A human completion action also follows applicable review requirements and does not silently approve deployment.

Scope moves show the proposed coordinator, audience, active work, and authorization consequences before confirmation. A changed version returns “Work changed since this preview. Review the updated scope.” The page retains the rejected request for explanation while displaying the confirmed scope.

### Inbox and independent human obligations

Managed worker rows may nest under their lead after routing and oversight are proven. Existing containment and Claude team nesting remain intact. Human sessions retain their independent placement. Display follows the current role session; history retains original spawn lineage.

Protected decisions and genuine permission prompts escape folds. Failed supervision also reaches the responsible human when no authorized recovery path can act. An independently actionable ask has its own queue entry even when its worker is hidden inside a group. The lead cannot hold it while preparing advice.

Routine updates may be coalesced. Distinct human obligations remain distinct. A single obligation appearing in chat, inbox, and push shares one underlying operation so notification deduplication does not create duplicate answers. The queue offers “Review decisions with leads” and “Take over.” The answered history exposes rationale and resulting effects for audit.

Proposed empty copy is “No action requested from you.” Where applicable, follow it with current verification and counts of routed decisions, clearly marked for coverage. “No action requested” does not claim that all work is correct or complete. Budget exhaustion cannot prevent a human from saving an answer or requesting emergency stop.

### Decision card: exact action and source evidence

The card leads with the actual decision. It names the eligible human, affected resource, audience, action class, proposal revision, and expiry. It explains why a human is needed. Recommendations follow as optional evidence. The exact effect being approved must fit on the card or in an accessible attached preview.

<!-- MOCKUP:decision -->

The card is illustrative: an owner reviews whether to deploy the checked revision to production, with the lead recommending additional receipt verification first. The context states the target service, included change, expected effect, verification result, rollback procedure, and expiry. Options are “Approve this deployment,” “Request changes,” and “Decline.” Any other target or revision requires a new request.

| Card field | Required content |
|---|---|
| Asked by and accountable lead | Actual worker identity, task, responsible human, and coordinator |
| Why you | Protected effect, unresolved product choice, missing authority, or failed escalation |
| Exact proposal | Action, resource, revision, audience, expiry, and relevant cost authorization |
| Options | Each action and consequence in full; recommended option labeled with its author |
| Evidence | Source artifact, checked revision and time, method, result, reviewer, limitations |
| Recommendation history | Who advised what, when, and on which proposal version |
| Outcome receipt | Pending, accepted, rejected, expired, or superseded, with resulting operation |

A reader should be able to move from sentence to proof. An illustrative “Replay check passed” statement opens the verification record. That record shows command, result, checked revision, verifier, and time. Its source link opens the authorized test artifact. The task then links the accepted criteria. If the current artifact changed, the interface distinguishes the checked revision from the latest one.

Evidence is authorized on retrieval and rendering. A viewer may see “Evidence unavailable to you. Ask the owner for an approved summary” only when revealing its existence is allowed. Otherwise omit it. Private transcripts never become public digest attachments. A lead's access does not transfer to the decision audience.

Editing the proposal invalidates previous approval. Concurrent answers resolve against the current version. An override pauses affected pending work and identifies completed effects that need reconciliation. Proposed copy: “Change this decision and pause affected work for reassessment. Completed actions may need repair.” Sending a second instruction alone cannot undo an effect.

### Chat as scoped intake

Chat supports questions and explicit work proposals. A human mention may wake a lead already allowed in that audience. Creating a lead does not join it to private channels or a standup room. Messages authored by agents do not wake other bots. A group thread and a direct message have separate audiences, even when they address the same role.

<!-- MOCKUP:chat -->

An illustrative request is “Can we fix duplicate notifications?” The lead first looks for related accessible work. It then returns an intake preview in that thread: “Proposed task: Prevent duplicate notifications. Project: Mail. Human owner: Maya. Deliverable: reproduce, fix, and verify one notification per event. Scope: code and tests. Deployment excluded.” The preview names the proposed worker count, configured compute limit, payer, host, input artifacts, and sensitive effects.

The controls are “Approve and start,” “Edit proposal,” and “Dismiss.” In observation mode or on an unsupported runtime, use “Save proposal” and explain the execution prerequisite. Before confirmation there is no active task, assignment, or launch. An authorized human confirmation creates the operation once, keyed to the originating thread message and proposal version.

Quotes, reactions, a bot message, and a participant saying “looks good” do not grant authority. Repeated clicks produce one task and one launch attempt. The receipt names the approver, linked task, and next expected update. A failed launch stays visible with its reason and retry status.

A DM proposal cannot silently publish its source text to a project channel. A group proposal must respect every artifact's source audience. If work requires broader sharing, the preview identifies the exact material and destination for separate approval. Task and thread link both ways without copying private content. Later replies remain attached to the same intake unless a human confirms a separate task.

### Memory and context health

The lead detail exposes its brief version, current acknowledged version, last successful context refresh, unresolved events, and evidence freshness. Avoid a single “healthy” badge that conceals missing inputs. Distinguish inaccessible sources, stale sources, a delayed inbox, and a session that has not read a changed brief.

A replacement session reconstructs context from durable scope, claims, decisions, evidence, and event records. The interface shows reconstruction progress and outstanding gaps. A prior handoff is linked as supplemental context. The user can inspect which facts entered the current brief and their source audience.

A correction should record the disputed statement and revised evidence. It should not merely overwrite prose and erase the earlier claim. Where a source is revoked, any derived summary must be rechecked before display or delivery. Permission loss can make a previously complete brief incomplete.

### Mobile, keyboard, and accessibility

Native mobile requires explicit implementation of nesting, decision detail, source access, and intervention. Shared projection data alone does not render those behaviors. Mobile uses the themed text components and keeps the same distinction between requested and confirmed state.

| Capability | Mobile requirement for managed pilot |
|---|---|
| Organization browsing | Expandable lead list, scope and next actor labels, accessible flat view |
| Human decision | Full action, owner, resource, revision, audience, evidence, options, and receipt |
| Evidence review | Open the checked artifact and return to the same decision position |
| Intervention | Take over review, pause new dispatch, preview stop of running managed work |
| Incomplete connection | Clear freshness, disabled stale approvals, visible unsubmitted requests |
| Detailed grant editing | May remain on desktop; inspection and emergency oversight remain available |

Use native buttons and labeled disclosure controls. Tree or list semantics expose expanded state, level, name, and obligation count without relying on indentation. Status uses text as well as color. Text enlargement, screen reader order, reduced motion, and high contrast must preserve decision content and controls.

Keyboard navigation follows the existing shortcut registry. All displayed keys use `KeyCap`, with platform modifiers derived from the shared shortcut helpers. Focus stays on the selected row as background state changes. Opening a source or dialog returns focus to its trigger. Revoked rows move focus to a clear notice. No background wake steals focus, and no single key confirms a protected action without the current proposal visible.

### Empty, delayed, and failed states

| State | Proposed copy and behavior |
|---|---|
| No lead | “Add a project lead to review selected work and propose a next step.” |
| No adopted work | “Choose work this lead may observe.” Preserve unrelated sessions. |
| No workers | “No workers yet. Choose approved work to start.” |
| Cold loading | Show labeled skeletons only where no cached rows exist. |
| Stale or incomplete | “Showing cached work. Counts may be incomplete.” Display last confirmed time. |
| Offline approval | “Not submitted. Reconnect to review the current request.” Preserve the draft choice without granting authority. |
| Pending action | “Request submitted. Waiting for confirmation.” Show its operation receipt. |
| Failed action | Show the specific rejection and confirmed current state. Retry reconciles the same operation. |
| Revoked access | Remove restricted previews and disable controls. Reveal no forbidden existence or count. |
| Vacant lead | Show the vacancy reason, backlog coverage, and available escalation target. |
| Budget exhausted | Show the limiting scope and reserved exposure. Answer storage and emergency stop remain available. |

These states are part of the release contract. They must be exercised in web and native mobile before managed work can depend on the interface.
