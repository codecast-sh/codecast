## 3. Schema, API, and replica contract

### Existing foundations and proposed changes

**Existing, as recorded in the architecture review.** Anchors cover team and user scopes. They separate bot display identity from the human host and current conversation. Tasks already have historical conversation links and an `in_review` status. Decisions, pending messages, daemon commands, task history, orchestration events, and the client store provide useful foundations. These facts describe inspected source, not a deployed organization feature.

**Proposed.** Extend anchors to workspace, project, and plan roles. Tasks receive temporary executions, not standing roles. Add operational records where a separate lifetime or transactional invariant requires them. There is no table-count target. All fields and endpoints below are proposed additions or changes unless marked existing. Section 4 defines transitions; section 5 defines enforcement.

Source integration points are `packages/convex/convex/anchors.ts`, `tasks.ts`, `sessionDecisions.ts`, `pendingMessages.ts`, `spawn.ts`, `lib/access.ts`, and `syncLog.ts`; runtime integration starts at `packages/cli/src/agents/runtime.ts`. These are pointers from the reviewed drafts, not claims that the proposed helpers exist.

Use `Id<T>` for a database identifier, UTC milliseconds for timestamps, nonnegative safe integers for counters, and integer USD microdollars for money. Optional fields are written as `?`. Every new record has `_id`, `created_at`, and `workspace`; mutable records also have `revision` and `updated_at`. `workspace` is the positive access key `team:<id>` or `user:<id>`. It is never inferred from routing `team_id`.

### Durable role and consent records

Proposed anchor fields are:

```ts
scope_type: "team" | "user" | "project" | "plan"
scope_id: string
short_id: string
parent_anchor_id?: Id<"anchors">
topology_revision: number
conversation_id?: Id<"conversations">
generation: number
responsible_user_id: Id<"users">
bot_user_id: Id<"users">
host_user_id: Id<"users">
device_id?: Id<"devices">
automation_mode: "manual" | "observed" | "managed"
consent_revision: number
consented_by?: Id<"users">
consented_at?: number
policy_revision_id: Id<"role_policy_revisions">
lifecycle: "provisioning" | "active" | "vacant" | "retired"
routing_state: "enabled" | "paused"
runtime_state: "absent" | "starting" | "running" | "hibernated" | "uncertain"
refill_mode: "manual" | "authorized"
brief_doc_id?: Id<"docs">
brief_revision: number
handoff_doc_id?: Id<"docs">
next_event_sequence: number
migration_operation_id?: string
```

The existing scope identifier fields remain during migration. Validators require the correct identifier type for `scope_type`. One nonretired anchor may hold a given `(workspace, scope_type, scope_id)`. Enforce uniqueness by an indexed lookup and insert in one transaction. Retain retired identities and their history. Index anchors by `workspace,scope_type,scope_id`, `workspace,parent_anchor_id`, `workspace,lifecycle`, `conversation_id`, and `short_id`.

A project without a workspace role reports directly to its responsible human. A plan can report to a workspace role if no project role exists. The configured reporting role remains assigned when vacant. Availability is a separate routing calculation. Scope edges must follow canonical project and plan relationships and pass workspace equality. A bounded walk permits at most the three standing levels. Reject cycles and conflicting task, plan, or project bindings.

`role_policy_revisions` is append-only. Fields are `scope_key`, `anchor_id?`, `version`, `previous_revision_id?`, `created_by_user_id`, `operation_id`, `reason`, `allowed_operations:string[]`, `ordinary_decision_classes:string[]`, `resource_grants:{resource_type,resource_id,actions:string[]}[]`, `max_concurrent`, `max_launches_daily`, `max_turns_daily`, `money_mode:"estimated"|"hard_required"`, `daily_usd_micros?`, `checkpoint_usd_micros`, `timezone`, `effective_at`, and `expires_at?`. Resource grants are capped at 64 entries per revision; larger scopes use canonical project membership predicates, not growing identifier arrays. Index by `scope_key,version`, `anchor_id,version`, and `operation_id`. Workspace, project, and plan rows gain `org_policy_revision_id?`; this allows budgets without standing roles. Anchor policy may further narrow a scope policy. Scope policy owns the timezone, which descendants cannot override. Unspecified operations deny. Missing money limits do not imply free compute; commissioning must explicitly select the budget mode and allowance.

Policy revision and consent are distinct. Grant changes do not silently enroll sessions. `responsible_user_id` names the accountable human, `host_user_id` names the operating account, and `device_id` names a location. None proves who sent a request. Bot users stay out of `session_owners`. Human ownership survives adoption.

### Authenticated execution principals

The proposed `execution_principals` table in section 5 stores scoped credential identity, expiry, access epoch, generation and revocation state. It is a server-only authority record, separate from bot display identity and human ownership. Its indexed lookup participates in every managed mutation. Credential secrets never enter display replicas. Role principals use a role generation; worker principals use the task attempt fence. A grant revision cannot expand the credential scope without an authorized new issuance.

### Conversations and exclusive task execution

Add to conversations `reports_to_anchor_id?`, `role_generation?`, `automation_mode`, `consent_revision`, `work_binding_revision`, and `active_permit_id?`. Existing `anchor_id` identifies a role's own conversation. Existing `parent_conversation_id`, fork lineage, and `spawned_by_conversation_id` keep their meanings. Spawn origin is immutable once known. Rotation changes the anchor's current conversation, never historical origin.

Index reporting queries by `reports_to_anchor_id,_creationTime`; use existing binding indexes where available. These indexes support paging and display. They are not admission counters. Display grouping resolves the reporting role through its current conversation map while preserving containment and Claude team nesting. Association alone does not fold or control a human session.

Add task fields `execution_revision`, `automation_mode`, `consent_revision`, `adopted_by_user_id?`, `adopted_at?`, `review_policy:"human"|"independent"|"assigned_reviewer"`, `review_revision`, `assigned_reviewer_principal_id?`, `completion_history_id?`, and:

```ts
active_execution?: {
  attempt_id: string
  conversation_id: Id<"conversations">
  lease_until: number
  generation: number
  permit_id: Id<"execution_permits">
}
```

Here `generation` is a task fencing counter advanced on each new attempt. The permit separately captures the admitting role generation. Role credentials fence that role's effects. Workers receive their own task-generation credentials; a reporting role's rotation does not revoke those credentials or change the task fence. Pending launches authorized by an old role must be reauthorized before dispatch. Claim compares `execution_revision`, checks an absent or safely released claim, increments the counter, and writes the claim with admission. Historical `conversation_ids` remains a many-conversation history. It is never the lock. An expired lease prevents further writes but does not prove the old process stopped.

Extend existing `task_history` with typed report entries: `operation_id`, `attempt_id`, `task_revision`, `evidence_revision`, `claims:{text,evidence_ids:string[]}[]`, `evidence:{id,kind,uri,content_hash?,observed_at,source_revision?,audience_ref}[]`, `limitations:string[]`, `reviewer_principal_id?`, and `verdict?`. Bound each entry to 32 claims, 64 evidence references, and 32 KiB; large logs remain separately stored artifacts. Completion references the exact entry and revision reviewed. Existing docs gain optional `org_digest:{role_id,source_watermark,source_revision_refs,audience_ref,generated_at,coverage,claims,limitations}`; source references and claims use the same bounds as reports. Larger digests are paged, not stored as growing arrays. A source revision change marks the digest stale until regeneration.

### Decisions, recommendations, and bounded history

Extend `session_decisions` with `operation_id`, `question_revision`, `source_conversation_id`, `source_revision`, `source_audience_ref`, `responsible_user_id`, `assigned_role_id?`, `assigned_generation?`, `answer_authority:"human"|"role"`, `decision_class`, `action_request?`, `next_hop_sequence`, `route_deadline?`, and `answer?`. Keep the existing question and answer presentation fields. The class defaults to `unknown`, which requires human authority.

The action request is `{operation,resource_type,resource_id,arguments_hash,resource_revision,policy_revision_id,audience_ref,expires_at}`. An answer is `{answer_id,question_revision,principal_id,principal_kind,option_id?,text?,action_request_hash?,answered_at}`. Recommendation text grants no action capability. Decision visibility is constrained by the source audience in addition to workspace access. Conversations have their own visibility rules; do not pretend they carry a workspace key.

Proposed `decision_hops` fields are `decision_id`, `question_revision`, `sequence`, `operation_id`, `actor_principal_id`, `actor_generation?`, `from_role_id?`, `to_role_id?`, `kind:"recommendation"|"escalated"|"answered"|"overridden"|"timed_out"`, `recommendation_option_id?`, `rationale`, and `source_audience_ref`. Limit rationale to 4 KiB. Index by `decision_id,sequence` and `operation_id`. Each mutation appends at most one hop. Routing moves upward through the bounded hierarchy and then to the human. Additional recommendations remain paged rows, never an unbounded array inside the decision.

Index decisions by `responsible_user_id,status,created_at`, `assigned_role_id,status,route_deadline`, and `operation_id`. Do not collapse different requests by normalized prose. An exact retry shares an operation identifier; a different resource, revision, audience, or option set creates a distinct request.

### Durable event inbox and existing delivery rails

Proposed `role_events` fields are `event_key`, `operation_id`, `source_type`, `source_id`, `source_revision`, `kind`, `destination_role_id`, `sequence`, `source_audience_ref`, `payload_ref?`, `status:"pending"|"leased"|"dispatched"|"acked"|"dead_letter"|"cancelled"`, `available_at`, `lease_owner?`, `lease_until?`, `delivery_generation?`, `attempt_count`, `pending_message_id?`, `batch_id?`, `effect_receipt_id?`, `acked_at?`, and `last_error_code?`.

Index by `event_key`, `destination_role_id,status,sequence`, `status,available_at`, and `status,lease_until`. Keys include source identity, revision, event kind, and destination role. Uniqueness is enforced transactionally. Increment `anchors.next_event_sequence` when inserting an event. No in-anchor wake array exists.

A committed task transition inserts its event in the same mutation. Dispatch uses existing `pending_messages`; process commands use existing `daemon_commands`. Extend both rails with optional `operation_id`, `permit_id`, `role_id`, and `role_generation`. A wake message references at most 32 event rows. Once dispatched, its batch is immutable. A transport acknowledgment is not an effect acknowledgment. Existing `orchestration_events` gains `operation_id`, `anchor_id`, `generation`, `effect_status`, `effect_receipt`, `request_hash`, `result_code`, `migration_cursor?`, `expected_topology_revision?`, and indexes `operation_id` and `anchor_id,created_at`. This provides the deduplication receipt for committed role effects and their audit, not a second transport.

### Execution reservations and accounting records

Proposed `execution_permits` fields are `operation_id`, `attempt_id`, `kind:"launch"|"turn"|"resume"|"request"|"checkpoint"`, `parent_permit_id?`, `task_id?`, `conversation_id`, `role_id`, `role_generation`, `task_generation?`, `policy_revision_ids:string[]`, `topology_revision`, `consent_revision`, `principal_id`, `device_id`, `account_id`, `adapter_id`, `adapter_capability_revision`, `attribution_path:string[]`, `budget_account_ids:string[]`, `period_id`, `reserved_usd_micros`, `price_bound_ref?`, `status:"queued"|"starting"|"running"|"uncertain"|"settled"|"cancelled"`, `lease_owner?`, `lease_until?`, `launch_token`, `external_execution_id?`, `settlement_revision`, and `last_error_code?`. Arrays contain unique keys and have a maximum of eight entries for the proposed scope chain.

Index permits by `operation_id`, `status,lease_until`, `device_id,status,created_at`, `role_id,status,created_at`, and `task_id,created_at`. Conversation metadata may exist before launch. A permit and its dispatch record are the authority to start it.

Proposed `budget_accounts` holds authoritative admission aggregates: `subject_key`, `period_id`, `timezone`, `period_start`, `period_end`, `settled_usd_micros`, `reserved_usd_micros`, `launches_admitted`, `turns_admitted`, `capacity_held`, `operations_admitted`, `limit_revision`, and `reconciled_through`. Device rows gain `managed_capacity_limit` and `managed_capacity_revision`; these configure the device capacity account. Policy revisions also carry `max_sends_per_hour`, `max_wakes_per_hour`, `max_causal_depth`, `max_event_attempts`, `retry_base_ms`, and `coalesce_ms`. Event rows gain `causal_root_id` and `causal_depth`. Send and wake counters use fixed UTC hourly periods, separate from daily money periods. Index uniquely by `subject_key,period_id`. Daily rows track money and daily counts. A separate `period_id:"capacity"` row tracks lifetime concurrent occupancy for each scope and device, so midnight does not release running processes. Device capacity uses the same atomic admission transaction as ancestor capacity.

`usage_receipts` is append-only evidence: `dedup_key`, `permit_id?`, `conversation_id?`, `source_kind:"provider"|"adapter"|"transcript"`, `source_id`, `source_revision`, `source_audience_ref`, `counter_epoch?`, `provider?`, `model?`, `billing_mode`, `pricing_revision?`, `input_tokens?`, `output_tokens?`, `cache_read_tokens?`, `cache_write_tokens?`, `authoritative_usd_micros?`, `estimated_usd_micros?`, `coverage:"complete"|"partial"|"unknown"`, `attribution_path:string[]`, `period_id`, `observed_at`, `supersedes_receipt_id?`, and `normalized_delta`. Index by `dedup_key`, `permit_id,created_at`, and `conversation_id,created_at`. A correction appends evidence and applies only its normalized difference.

`usage_daily` is a rebuildable display projection. Fields are `scope_key`, `period_id`, `audience_key`, `timezone`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `authoritative_usd_micros`, `estimated_usd_micros`, `unpriced_receipt_count`, `complete_receipt_count`, `partial_receipt_count`, `launches_admitted`, `turns_admitted`, `receipt_watermark`, and `coverage`. Index by `scope_key,period_id,audience_key`. It never authorizes admission. Section 5 explains attribution, settlement, and incomplete prices.

### API signatures and transaction boundaries

Proposed authenticated APIs derive `actor` from the credential, not request fields:

```ts
admitTask({ operationId, taskId, expectedExecutionRevision,
  roleId, expectedRoleGeneration, consentRevision, adapterId,
  deviceId, requestBoundMicros }): Result<PermitReceipt>
answerDecision({ operationId, decisionId, expectedQuestionRevision,
  optionId, actionRequestHash? }): Result<AnswerReceipt>
applyRoleEffect({ operationId, eventIds, expectedGeneration,
  effect }): Result<EffectReceipt>
changePolicy({ operationId, roleId, expectedRevision,
  policy, consentRevision }): Result<PolicyReceipt>
listRoleEvents({ roleId, cursor?, limit }): Page<RoleEventView>
```

Success receipts carry `{operationId,resourceId,revision,state}`; permit receipts also carry `permitId`, `attemptId`, and `taskGeneration`. The receipt confirms the stated server transition, such as `queued`, not a future launch.

`Result<T>` is `{ok:true,value:T,replayed:boolean}` or `{ok:false,error:{code,retryable,retryAfterMs?,currentRevision?,dimension?,used?,reserved?,requested?,limit?}}`. Codes include `UNAUTHENTICATED`, `FORBIDDEN`, `SCOPE_CONFLICT`, `STALE_GENERATION`, `REVISION_CONFLICT`, `CLAIM_HELD`, `CONSENT_REQUIRED`, `APPROVAL_REQUIRED`, `ACCESS_REVOKED`, `BUDGET_EXHAUSTED`, `ACCOUNT_QUOTA`, `UNSUPPORTED_ADAPTER`, and `OUTCOME_UNCERTAIN`. Unauthorized callers receive no resource counts. A refusal that needs audit returns an error value after inserting its audit row; throwing would roll that insert back. An operation identifier reused with different arguments returns `OPERATION_CONFLICT`.

Admission atomically checks identity, access, consent, task CAS, topology, policies, every budget account, and device occupancy, then inserts the permit, claim, launch command, and audit. Answering atomically writes the answer, hop, and delivery outbox. Effects atomically validate generation, commit internal changes, record the receipt, and acknowledge relevant events. External calls happen after commit and require reconciliation. No mutation scans every live session. Read at most eight budget subjects and process at most 32 events or 100 migration rows per invocation.

### Source of truth and replica behavior

Canonical task and scope rows own binding. Anchors own role identity and current generation. Policy revisions own grants. Permits and budget accounts own admission. Receipts own usage evidence. Daily totals and digests are projections. Pending messages own transport state; event acknowledgments own processing state. Runtime observations describe processes and never replace task verdicts or who acts next.

Register all displayed collections, including event history, usage summaries, and digest fields, in `store/clientSyncRegistry.ts`. Global feeders run only on the sync host. Per-view paged history feeders populate store collections with delta semantics. Components read signatures through store hooks. Bump the cache schema and projection contract when implemented, without hardcoding today's version. Optimistic `action()` writes show requested changes plus an operation receipt; they cannot claim a launch or approval succeeded before server acceptance.

Extend access stamps, tracked tables, and sync entity validators together. Cargo contains bounded display fields; large evidence, policy bodies, and event payloads use authorized detail reads into the store. Missing cargo is explicitly partial. Capability secrets and raw principal records never enter human display feeds. Budget-account totals require explicit financial read authority; workspace membership alone does not expose private descendant spending. Other viewers receive audience-filtered usage projections with coverage, not full enforcement totals. Never suppress a field's updates as churn if a visible meter depends on it. Paged responses carry `{items,nextCursor,watermark,coverage}`; an incomplete page does not remove unseen rows or justify exact counts.

Derived views retain source audience dependencies and are invalidated when any dependency changes. Revocation emits audience-specific removal records to previously authorized replicas without including revoked content. Tombstones remove rows from memory, IndexedDB, follower windows, search caches, and derived digests. Reconnect checks the access epoch before exposing cached protected data; an obsolete epoch clears that partition before hydration. Offline clients cannot learn a new revocation instantly. Managed access requires an online authorization check, and cached human views disclose their last authorization time. Native mobile needs its own nesting, pending receipts, removals, and protected-ask rendering tests.

### Additive migration

First deploy optional fields and read compatibility, then page through deterministic backfills. Existing anchors remain observed or manual; no default spend consent, automatic refill, or session adoption is inferred. Existing decisions retain human authority and source visibility. Keep the old cap field until all readers and rollback paths are retired.

Next enable project observation and explicit task adoption. Add claims, credentials, permits, events, and access invalidation behind capability gates before managed execution. Reconciliation jobs store cursor and revision in existing orchestration events, index by operation identifier, and resume in bounded pages. They report conflicts rather than silently crossing workspaces. Old clients retain readable flat views and human asks; managed writes require the new protocol. Backend capability deployment precedes clients that call new endpoints. Rollback disables new admissions while preserving receipts, decisions, and reconciliation of outstanding effects.
