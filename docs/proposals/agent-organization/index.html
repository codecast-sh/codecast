1. Recommendation and practical value

Start with a useful project lead

Build a durable lead for a real body of work. Start with one project. Give the lead a clear brief, selected work to observe, a named responsible human, and access to the evidence it needs. Its first contribution should be a factual project brief and one actionable recommendation. The human should understand the next step without reconstructing several conversations.

The lead would retain responsibility for coordination across temporary sessions. It would track the intended outcome, notice blocked work, assemble review evidence, and keep unresolved questions visible. Later, within explicitly approved permissions, it could direct workers through routine execution. The human would retain responsibility for the work and control over protected actions.

This proposal uses implementation seams identified in the completed surveys. Whether a management layer saves attention or improves quality remains a hypothesis to test through comparable work. The first release should earn continued use by helping someone make a sound decision about an existing project.

The practical problem

Several sessions can each make progress while leaving a person to reconstruct the whole. A worker finishes a turn. Another waits for context. A third claims completion without linking a check. The person must determine whether these are separate obligations, related symptoms, or ordinary updates. The cost includes reading, locating evidence, choosing the next actor, and remembering to return.

Durable coordination could reduce that repeated reconstruction. A lead would keep the acceptance criteria and current evidence attached to the work. A worker could report a blocker once. The lead could resolve it from approved context or identify the exact human decision required. A completed implementation would enter review with its revision, verification method, result, and remaining concerns.

The proposal therefore has two practical tests. Does the human spend less effort reaching an accepted outcome? Does the outcome meet its criteria with at least the same reliability? A smaller visible inbox alone answers neither question. Folding sessions can hide obligations. Splitting tasks can inflate output counts. Both require independent checks.

No reliable baseline has been established for daily attention cards, undeclared sessions, peak machine load, manager overhead, or cost savings. Figures in earlier drafts were anecdotes, snapshots, or proposed targets. They should not determine launch thresholds. Measure the baseline before setting improvement targets.

First release scope

The first release is an observer foundation. A person chooses “Add project lead,” reviews the allowed scope and host, and selects tasks to observe. Existing task owners and human sessions keep their ownership. The lead can read authorized material, produce a brief, and prepare recommendations. It cannot adopt the rest of the workspace because it shares a project name or has a bot identity.

The release would include project context, linked evidence, a visible human owner, an explicit observation mode, and a current next actor. It would also include a way to pause observation, inspect what the lead read, and correct its brief. Missing evidence, denied access, and stale data must remain visible.

Managed execution would follow a separate gate. It requires authenticated actor identity, exclusive task claims, enforced admission, reliable wakes, and usable human oversight. Shared local credentials and unrestricted shell access cannot enforce isolation from a malicious worker. Such hosts may support observation. Unattended managed operation requires scoped service credentials, secret isolation, runtime adapters, and enforced resource capabilities.

The difference should be visible in ordinary copy. Proposed copy: “Review this project and propose the next step. Starting workers requires your approval.” If the selected host cannot support managed execution, the proposal remains useful as an observer. The product should explain the available mode before a person invests in setup.

The first ten minutes

This proposed acceptance scenario describes the adoption experience to test. Its timing needs validation during the pilot.

An illustrative recommendation could read: “Investigate the missing fixture. Owner: Maya. Deliverable: reproduce the failure and identify its cause. Proposed execution: one worker, code and tests only. Deployment is excluded.” Its evidence would link the failing test and the last relevant change.

Inaccessible work should yield a bounded statement such as “I could not verify the latest test result.” A project with no blocker should receive a supported next step or a clear statement that no action is recommended. Non-goals and adoption discipline

There is no standing role per task, no automatic hierarchy filling, and no mandatory plan creation. Existing task depth remains unchanged. The proposal does not require standups, a new reporting destination, or a ceremonial approval for each reversible implementation choice. Workers may resolve such choices within approved criteria and capabilities.

The first release excludes automatic session migration, autonomous purchases, production changes, destructive cleanup, and execution across workspaces. It makes no hard money cap claim for uncontrolled native tools. It does not promise a CPU load reduction. Archive and cleanup remain separate from successful task completion.

A template may suggest a brief and review practice. The owner accepts its scope and permissions explicitly. A recommendation to add another lead remains a proposal, even when task volume rises. Continued adoption depends on measured human effort, verified quality, unresolved escalation, and total cost coverage. One lead with temporary workers may remain sufficient.

2. The model and a day of work

A durable lead, temporary sessions, named humans

A lead is a durable role attached to work. A session is the current conversation and process carrying out that role. Workers are temporary sessions assigned to bounded execution. A named human remains responsible for the project or plan. Task ownership, review responsibility, hosting, and billing remain separate facts.

The proposed model generalizes anchors at workspace, project, and plan scope. Tasks keep their existing depth limit and receive workers. Adding a reporting role does not add task levels. A subtask can be executed separately where the task model permits it, while its coordinator follows the same valid scope chain.

Scope Coordination responsibility When no dedicated lead exists
Workspace, team or personal Coordinate approved work across projects and surface unresolved responsibilities Named humans retain direct coordination
Project Maintain project context, sequence adopted work, arrange reviews, and report material changes An available authorized workspace lead may coordinate adopted work
Plan Coordinate a bounded outcome and its tasks Its project lead handles adopted work, or the available workspace lead if the plan has no project
Task and subtasks A worker executes agreed criteria; a reviewer checks evidence The task's human owner determines the next step

One scope has one accountable lead. Missing levels remain missing. A project can have a lead without a workspace lead. A plan can exist without a project. A task can be filed directly in a project without a plan. The product should show each arrangement without treating absent roles as errors.

Resolve scope before assigning coordination

Explicit work bindings determine reporting independently of launch provenance. For a task in a plan, the plan's project determines the project scope. A separately stored task project must agree. A subtask must agree with its parent's filing. Workspace disagreement is rejected before a reporting assignment or execution can be created.

Situation Proposed resolution Human consequence
Task has a plan and matching project Resolve the plan lead, then project lead, then workspace lead Show the selected coordinator and the reason
Task has a project and no plan Resolve the project lead, then workspace lead No plan creation is needed
Plan has no project Resolve the plan lead, then workspace lead Keep the plan independent
Task project differs from its plan's project Reject the conflicting filing Offer “Move the plan” or “Remove task from plan” through a scope preview
Parent and subtask have conflicting scope Reject the conflicting filing Resolve the work structure before starting an attempt
Linked objects have different workspaces Reject the binding No implicit sharing or management across workspaces

A scope move is a versioned change. Its preview identifies the current and proposed coordinator, affected tasks, running attempts, access changes, pending decisions, and budget attribution. Confirmation reconciles the affected records against that version. A concurrent move or grant change invalidates the preview. Running work pauses where its authorization no longer applies. New authority requires confirmation before execution resumes.

An existing reporting assignment stays attached to the durable role when its session becomes vacant. The system computes an available escalation target separately. This preserves accountability while letting an urgent question reach someone who can act. A task should never appear to change managers merely because a process crashed.

A role reads only when the workspace gate, resource ACL, and scoped role grant all allow it. Scope visibility grants no execution authority. Retrieval and rendering recheck the source audience.

Keep responsibility and infrastructure separate

The lead's durable identity survives replacement of its current session. anchor.conversation_id and a monotonic generation identify the current holder. reports_to_anchor_id remains stable. The displayed parent resolves through the current role session map. Original spawned_by_conversation_id and fork lineage remain unchanged forever. Existing containment and Claude team nesting keep their meanings.

Fact Meaning
Responsible human Accountable for the work and for identifying eligible approvers
Task owner Owns the task's agreed outcome; adoption does not silently reassign it
Lead identity Coordinates a defined scope under its current grant
Current session and generation Holds the role now; old generations cannot continue role effects
Working session Holds a specific execution attempt, with its own evidence and history
Reviewer Checks the result against criteria and the reviewed revision
Host and device Supply the runtime and resources
Billing account Pays for approved compute under explicit configuration

Bot users stay out of session_owners. Human ownership of a session remains human ownership even when the conversation is linked to adopted work. Hosting a lead does not make the host the authorized approver. If no eligible person is available, the product says “Waiting for an authorized owner. No approval has been granted.”

Authentication must establish the actor and its scope. A supplied session ID or --from value is attribution only. Section 5 defines the required control boundary. The product must not present a worker using shared human credentials as independently constrained authority.

Observation and managed automation

Adoption records automation_mode: manual, observed, or managed. Manual work follows its existing human control. Observed work allows the lead to inspect approved evidence and recommend a next step. Managed work permits defined actions under a grant, supported runtime, and explicit human consent. Neither bot identity nor spawn provenance changes that mode.

Observation of a human session is itself explicit and scoped. It does not permit the lead to message, stop, hide, or take over the session. A managed task can also have human conversations linked as evidence. Those links do not make the conversations managed workers.

Workers may choose reversible implementation details inside approved acceptance criteria. Leads handle coordination and unresolved ambiguity within their grant. Purchases or billing changes, destructive data changes, production changes, auth or access changes, external communication, and unresolved user facing product choices require a human decision. Unknown effect classes escalate. Drafting can continue only where it is independently authorized and does not commit the protected choice.

Runtime state and next actor answer different questions. A process can be alive while a human owes approval. A stopped lead can have a recovery action assigned to another authorized lead. “Waiting” therefore names both the reason and the actor who can change it. Section 4 describes delivery and escalation in detail.

One accountable lead with scoped experts

A project lead may request expertise from another project without sharing management authority. The request names the accountable lead, question, allowed artifacts, deliverable, desired response time, and approved cost allocation. The expert receives only the permitted inputs and returns evidence to the requesting task. It cannot reassign the task, inherit workspace access, or direct the requesting workers.

An illustrative consultation reads: “Review this proposed token validation change. Share the patch and test output only. Return security concerns and suggested checks. Mail lead remains accountable.” The expert's response is advisory evidence. If the lead implemented the change, an eligible independent reviewer still has to verify the final revision where review policy requires it.

Project and plan leads also have distinct ownership. A plan lead coordinates its bounded result. The project lead coordinates dependencies and competing priorities across adopted plans. A conflict about scope or acceptance reaches the named human. Two leads cannot issue competing directions to the same active task attempt.

A full day, illustrative

The following day is illustrative. Names, times, task counts, and events are invented. It assumes the managed project gate has passed. Mail has one project lead, a responsible human named Maya, and selected tasks with explicit consent. It has no workspace or plan lead. Another project supplies an expert consultation under a separate request.

Time Event and evidence Next actor
08:30 Maya opens Mail. The brief links a verified replay test, an unresolved fixture blocker, and a proposed notification fix. It marks production behavior unverified. Maya selects the proposal to inspect
09:00 Maya confirms the exact scope, acceptance criteria, runtime, payer, and configured allowance. A task attempt and execution permit are admitted once. The admitted worker starts reproduction
10:10 The worker reports a missing fixture. The lead finds an accessible earlier task with the correct fixture path and records the source in its reply. The worker resumes within the approved attempt
11:15 The patch raises a token validation concern. The lead requests a bounded review from the shared expert, with only the patch and test output shared. The expert returns findings; the Mail lead retains coordination
12:30 A proposed retry cannot fit the remaining reservation and ancestor limits. The lead presents existing evidence and the reason admission was declined. Maya may approve a revised compute allocation or leave the attempt paused
13:20 A human asks in the project channel whether customer notifications can be changed. The lead previews a separate intake proposal and its audience. The authorized human edits or confirms the proposal
14:40 The worker reports completion. Its evidence contains the patch revision, replay command, result, and known limitations. The assigned reviewer checks that revision
15:30 Review verifies the agreed local behavior. A deployment request reaches Maya directly as a protected decision. Lead advice appears when ready. Maya decides on the exact deployment request
17:00 Maya reads the update: accepted local result, deployment still pending, one review concern resolved, and the remaining admission limit. Maya owns the deployment decision; the lead has no new execution to start

The budget event does not imply permission to buy a service. A compute allowance funds only the supported model activity it names. Human answers remain recordable even if no compute remains to process them. The interface distinguishes “Answer saved” from “Worker resumed.”

The final update does not say the project is on track unless a target and evidence support that claim. It separates reported completion, verification against criteria, and owner acceptance. Task completion does not approve a release. No role is added because the day became busy. Archive only verified clean work after the chosen retention period. Dirty worktrees, unmerged commits, pending approvals, and unresolved effects remain protected. Time alone does not authorize deletion.

A failed manager, illustrative

This failure scenario is illustrative. The Mail lead reports that a fix is verified, but its evidence points to an older revision. Maya opens the claim, follows the source link, and sees the mismatch. She chooses “Take over review.” The current acceptance claim becomes disputed. New dependent dispatch pauses while the exact affected work is identified.

The lead then crashes before writing a handoff. Its role remains present and vacant. The durable inbox retains unacknowledged events. Task records retain active attempts, pending decisions, and evidence. Replacement reconstructs approved scope and unresolved obligations from those records. A handoff document can assist, but recovery does not depend on the failed session producing one.

Refill advances the generation with a generation compare and swap check and revokes the old capability. If the old session resumes, every attempted role effect is fenced. Duplicate event delivery may occur; the operation identifier prevents a second effect. An external action with an uncertain result enters reconciliation before any retry.

Maya is the next actor for the disputed acceptance. The replacement lead is the next actor for reconstructing the review packet. The worker may continue only independent, already authorized work. Stopping the lead session vacates the role; stopping a managed subtree is a separate previewed action. Completed effects may require repair. Neither override nor refill silently undoes them.

3. Schema, API, and replica contract

Existing foundations and proposed changes

Existing, as recorded in the architecture review. Anchors cover team and user scopes. They separate bot display identity from the human host and current conversation. Tasks already have historical conversation links and an in_review status. Decisions, pending messages, daemon commands, task history, orchestration events, and the client store provide useful foundations. These facts describe inspected source, not a deployed organization feature.

Proposed. Extend anchors to workspace, project, and plan roles. Tasks receive temporary executions, not standing roles. Add operational records where a separate lifetime or transactional invariant requires them. There is no table-count target. All fields and endpoints below are proposed additions or changes unless marked existing. Section 4 defines transitions; section 5 defines enforcement.

Source integration points are packages/convex/convex/anchors.ts, tasks.ts, sessionDecisions.ts, pendingMessages.ts, spawn.ts, lib/access.ts, and syncLog.ts; runtime integration starts at packages/cli/src/agents/runtime.ts. These are pointers from the reviewed drafts, not claims that the proposed helpers exist.

Use Id<T> for a database identifier, UTC milliseconds for timestamps, nonnegative safe integers for counters, and integer USD microdollars for money. Optional fields are written as ?. Every new record has _id, created_at, and workspace; mutable records also have revision and updated_at. workspace is the positive access key team:<id> or user:<id>. It is never inferred from routing team_id.

Authenticated execution principals

The proposed execution_principals table in section 5 stores scoped credential identity, expiry, access epoch, generation and revocation state. It is a server-only authority record, separate from bot display identity and human ownership. Its indexed lookup participates in every managed mutation. Credential secrets never enter display replicas. Role principals use a role generation; worker principals use the task attempt fence. A grant revision cannot expand the credential scope without an authorized new issuance.

usage_receipts is append-only evidence: dedup_key, permit_id?, conversation_id?, source_kind:"provider"|"adapter"|"transcript", source_id, source_revision, source_audience_ref, counter_epoch?, provider?, model?, billing_mode, pricing_revision?, input_tokens?, output_tokens?, cache_read_tokens?, cache_write_tokens?, authoritative_usd_micros?, estimated_usd_micros?, coverage:"complete"|"partial"|"unknown", attribution_path:string[], period_id, observed_at, supersedes_receipt_id?, and normalized_delta. Index by dedup_key, permit_id,created_at, and conversation_id,created_at. A correction appends evidence and applies only its normalized difference.

usage_daily is a rebuildable display projection. Fields are scope_key, period_id, audience_key, timezone, input_tokens, output_tokens, cache_read_tokens, cache_write_tokens, authoritative_usd_micros, estimated_usd_micros, unpriced_receipt_count, complete_receipt_count, partial_receipt_count, launches_admitted, turns_admitted, receipt_watermark, and coverage. Index by scope_key,period_id,audience_key. It never authorizes admission. Section 5 explains attribution, settlement, and incomplete prices.

API signatures and transaction boundaries

Proposed authenticated APIs derive actor from the credential, not request fields:

admitTask({ operationId, taskId, expectedExecutionRevision,
  roleId, expectedRoleGeneration, consentRevision, adapterId,
  deviceId, requestBoundMicros }): Result<PermitReceipt>
answerDecision({ operationId, decisionId, expectedQuestionRevision,
  optionId, actionRequestHash? }): Result<AnswerReceipt>
applyRoleEffect({ operationId, eventIds, expectedGeneration,
  effect }): Result<EffectReceipt>
changePolicy({ operationId, roleId, expectedRevision,
  policy, consentRevision }): Result<PolicyReceipt>
listRoleEvents({ roleId, cursor?, limit }): Page<RoleEventView>

Success receipts carry {operationId,resourceId,revision,state}; permit receipts also carry permitId, attemptId, and taskGeneration. The receipt confirms the stated server transition, such as queued, not a future launch.

Result<T> is {ok:true,value:T,replayed:boolean} or {ok:false,error:{code,retryable,retryAfterMs?,currentRevision?,dimension?,used?,reserved?,requested?,limit?}}. Codes include UNAUTHENTICATED, FORBIDDEN, SCOPE_CONFLICT, STALE_GENERATION, REVISION_CONFLICT, CLAIM_HELD, CONSENT_REQUIRED, APPROVAL_REQUIRED, ACCESS_REVOKED, BUDGET_EXHAUSTED, ACCOUNT_QUOTA, UNSUPPORTED_ADAPTER, and OUTCOME_UNCERTAIN. Unauthorized callers receive no resource counts. A refusal that needs audit returns an error value after inserting its audit row; throwing would roll that insert back. An operation identifier reused with different arguments returns OPERATION_CONFLICT.

Admission atomically checks identity, access, consent, task CAS, topology, policies, every budget account, and device occupancy, then inserts the permit, claim, launch command, and audit. Answering atomically writes the answer, hop, and delivery outbox. Effects atomically validate generation, commit internal changes, record the receipt, and acknowledge relevant events. External calls happen after commit and require reconciliation. No mutation scans every live session. Read at most eight budget subjects and process at most 32 events or 100 migration rows per invocation.

Source of truth and replica behavior

Canonical task and scope rows own binding. Anchors own role identity and current generation. Policy revisions own grants. Permits and budget accounts own admission. Receipts own usage evidence. Daily totals and digests are projections. Pending messages own transport state; event acknowledgments own processing state. Runtime observations describe processes and never replace task verdicts or who acts next.

Register all displayed collections, including event history, usage summaries, and digest fields, in store/clientSyncRegistry.ts. Global feeders run only on the sync host. Per-view paged history feeders populate store collections with delta semantics. Components read signatures through store hooks. Bump the cache schema and projection contract when implemented, without hardcoding today's version. Optimistic action() writes show requested changes plus an operation receipt; they cannot claim a launch or approval succeeded before server acceptance.

Extend access stamps, tracked tables, and sync entity validators together. Cargo contains bounded display fields; large evidence, policy bodies, and event payloads use authorized detail reads into the store. Missing cargo is explicitly partial. Capability secrets and raw principal records never enter human display feeds. Budget-account totals require explicit financial read authority; workspace membership alone does not expose private descendant spending. Other viewers receive audience-filtered usage projections with coverage, not full enforcement totals. Never suppress a field's updates as churn if a visible meter depends on it. Paged responses carry {items,nextCursor,watermark,coverage}; an incomplete page does not remove unseen rows or justify exact counts.

Derived views retain source audience dependencies and are invalidated when any dependency changes. Revocation emits audience-specific removal records to previously authorized replicas without including revoked content. Tombstones remove rows from memory, IndexedDB, follower windows, search caches, and derived digests. Reconnect checks the access epoch before exposing cached protected data; an obsolete epoch clears that partition before hydration. Offline clients cannot learn a new revocation instantly. Managed access requires an online authorization check, and cached human views disclose their last authorization time. Native mobile needs its own nesting, pending receipts, removals, and protected-ask rendering tests.

Additive migration

First deploy optional fields and read compatibility, then page through deterministic backfills. Existing anchors remain observed or manual; no default spend consent, automatic refill, or session adoption is inferred. Existing decisions retain human authority and source visibility. Keep the old cap field until all readers and rollback paths are retired.

Next enable project observation and explicit task adoption. Add claims, credentials, permits, events, and access invalidation behind capability gates before managed execution. Reconciliation jobs store cursor and revision in existing orchestration events, index by operation identifier, and resume in bounded pages. They report conflicts rather than silently crossing workspaces. Old clients retain readable flat views and human asks; managed writes require the new protocol. Backend capability deployment precedes clients that call new endpoints. Rollback disables new admissions while preserving receipts, decisions, and reconciliation of outstanding effects.

4. Delegation, review, decisions, and lifecycle

Existing rails and proposed flow

Existing, from the reviewed source. Task bindings, pending messages, daemon commands, decision records, and session state already move work through Codecast. Some native processes are discovered after launch. Existing message delivery does not prove a manager processed the message. These mechanisms do not already provide the admission and authority contract below.

Proposed. Every managed transition uses the records in section 3. The server authorizes internal effects in a transaction. An isolated execution gateway mediates external effects as described in section 5. A local observer can recommend the same steps, but cannot promise to enforce them against a hostile process on the host.

Adopt and delegate a task

The first project lead starts in observe/recommend mode. A human selects the project and tasks, checks source access, chooses the responsible person and host, and reviews the proposed budget. Saving the preview records explicit consent. Existing sessions remain manual unless separately adopted. A reporting link is not consent to send instructions, stop a process, or move its inbox card.

A delegation request names a task, acceptance criteria, evidence requirements, runtime capability, and operation identifier. The task's canonical project and plan bindings determine scope. A specialist request retains one accountable lead; a second role receives a narrow request and does not become another manager. A lead cannot create a task in a sibling scope merely because both projects share a workspace.

The proposed admitTask transaction performs these steps:

  1. Authenticate the principal and check its current generation, grant revision, scope, and consent. Validate task access separately from role membership.
  2. Read the expected task execution revision. Refuse a live claim or an expired claim whose external execution remains uncertain. Confirm that the requested adapter can enforce the selected management mode.
  3. Resolve the bounded canonical ancestor path. Check role and workspace admission accounts, the device capacity row, account quota eligibility, and the required reservation. Queued permits consume capacity.
  4. Create the conversation metadata, immutable origin, permit, task claim, task-history entry, and launch command. Increment authoritative counters in the same commit. Stamp policy, consent, topology, and attribution revisions on the permit.
  5. Return the accepted operation receipt. The client replaces its provisional row by operation identifier. Failure returns a reason and removes the pending claim without inventing a completed launch.

Concurrent requests conflict on the same task and shared budget rows. Only one task claimant commits. A retry with the same identifier and arguments returns its prior receipt without another attempt or charge. A request declined for capacity may be retried after capacity changes, using a new identifier. Repeating the original request retains its original refusal.

Dispatch and confirm a start

A dispatcher leases the command and moves its permit from queued to starting in one transaction. Immediately before launch, it validates the role generation, task generation, policy, consent, and account eligibility again. The gateway uses launch_token as its idempotency key and persists an external execution identifier before reporting running.

A command lease is scheduling ownership, not proof of process uniqueness. If the dispatcher crashes before receiving the launch result, mark the permit uncertain. Another dispatcher queries the gateway by launch token. Finding an execution attaches to it. A definitive absence permits retry. An adapter that cannot distinguish absence from a lost response cannot safely replay a launch and does not qualify for managed starts.

A lost heartbeat retains the capacity reservation. A reconciler confirms termination or keeps the permit uncertain. Task lease renewal requires the current task fencing counter and authenticated execution identity. After lease expiry, old task writes fail even if its process continues. A new executor is admitted only after the old execution is fenced at the gateway and its process or effects are reconciled. This avoids treating elapsed time as a kill acknowledgment.

Every start path must use admission: ordinary spawn, fork, trigger, refill, resumed compute, model turn, and native helper launch. Retrospective daemon discovery labels an unpermitted process unmanaged. It cannot retroactively make its launch safe. A managed adapter must disable native helpers or intercept them before creation.

Report with evidence, then review

A worker's state update reports its next actor and current situation. It does not complete the task. The report mutation validates the active execution and stores claims, evidence references, source revisions, observed times, and limitations in task history. It changes a managed task to in_review and inserts the review event in the same transaction.

The task may remain in review after the worker process stops and its capacity is released. The completion proposal survives in completion_history_id. A later review compares both task revision and evidence revision. If another attempt changes the task or replaces the evidence, an old approval fails with REVISION_CONFLICT.

An independent review policy requires a reviewer principal different from the executor and outside its delegated credentials. Another conversation controlled by the same executor does not satisfy independence. The server checks the reviewer assignment, resource access, and current authority. Where meaningful independence cannot be provisioned, a human reviews. A managing role that implemented the work cannot approve its own report under this policy.

The reviewer examines artifacts and reproduces relevant checks. Acceptance writes the verdict, reviewer identity, reviewed revisions, task completion, and parent event atomically. Rejection appends specific unmet claims and leaves the task unfinished. Further implementation requires a valid execution claim and compute admission. A reviewer does not silently restart the old worker by sending an unbudgeted message.

A role report links these records rather than treating completed-task percentage as proof of quality. It distinguishes verified results, worker claims, stale evidence, unresolved effects, and coverage gaps. Digests read only material visible to their destination. Private source text must never enter a broad model prompt in the hope that its output will omit it.

Decide without delaying human asks

A decision has a typed answer authority. A protected or unknown request is assigned to the responsible human at insertion. That same transaction makes it visible in the human queue and creates its notification outbox. The queue never waits for a lead to recommend, forward, or finish a model turn.

For an ordinary coordination question, route to the nearest available role authorized for that class and resource. Keep the task's assigned reporting role unchanged. A vacant or paused role is skipped only when computing this escalation destination. The human can inspect and take any routed question. A genuine runtime permission prompt also escapes folds, regardless of a session's origin or automation mode.

A recommendation appends a bounded hop and leaves human answer authority intact. An ordinary role answer compares the question revision, assignee generation, and policy. Answer, audit hop, and pending answer delivery commit together. Duplicate answers return the original receipt. Competing answers resolve by revision conflict, never last-writer replacement.

An action approval additionally binds the concrete resource, argument hash, resource revision, audience, policy revision, and expiry. Editing an option invalidates prior approval. Free-text approval of an approach does not authorize a deployment, purchase, or message to another person. Section 5 defines the gateway check.

Timeout processing pages the decision deadline index. Each mutation advances one decision to an eligible ancestor or the human and records why. Upward routing is bounded; no automatic downward bounce exists. A missing recommendation is acceptable when it would delay escalation. Repeated equivalent questions can be shown together, but remain distinct requests unless they share an exact operation identifier.

A human override cancels pending authorization and dispatch where cancellation is still possible. If dispatch started, set the effect to uncertain and reconcile. If an effect completed, record a corrective request with evidence of what happened. Do not automatically undo database changes, revert unrelated commits, or claim that an override erased an external action.

Wake events and acknowledgment after effect

A wake key is a tuple encoded canonically: (source_type, source_id, source_revision, kind, destination_role_id). Two settles at different revisions create two events. Replaying the same source revision creates one. A destination role, rather than its current conversation, owns the event across rotation.

The source transition and event insertion commit together. A scheduler pages ready events, checks audience and current destination authority, and leases at most 32. It creates an immutable pending-message batch. Several routine changes may share one turn, but every event remains recorded. An active lead reads its inbox at a safe yield rather than receiving repeated interruptions. Coalescing delay is configurable; urgent human delivery bypasses it.

Processing uses deterministic operation identifiers derived from event identity and effect kind. For an internal effect, applyRoleEffect checks all fences, applies the change, stores the effect receipt, and acknowledges the event in one transaction. For an external effect, it first records a dispatch intent. Only reconciled completion can acknowledge successful processing. A durable cancellation or explicit human deferral can also close processing, with that disposition recorded.

If transport succeeds but acknowledgment is lost, delivery may repeat. A new consumer reads the receipt and acknowledges without repeating the effect. Several external effects for one event have separate identifiers; the final acknowledgment requires all dispositions. Sending a message to a pane is not sufficient evidence.

Retries use bounded exponential delay and an attempt limit. Use a retry delay of min(retry_base_ms * 2^attempt_count, 300000) with bounded jitter. The selected policy records attempt limits; the pilot must measure them before choosing defaults. Exhausted retries create a visible dead letter with replay and reconciliation controls. Routine budget exhaustion leaves events pending. It does not drop them or allow free recommendation turns. A non-model path stores human questions and emergency-stop requests even with zero compute allowance.

Loop controls bound sends per ordered principal pair, total role wakes, and causal depth. Persist window counters in budget account subjects such as send:<from>:<to> and wake:<role>. Agent-authored chat never wakes another bot. A refusal records a terminal control event that does not itself trigger the same model wake. Backlog size and oldest event age remain visible.

Pause, hibernate, vacancy, and rotation

Pause changes routing. It stops routine managed dispatch to the role, preserves its inbox, and sends urgent asks to the human or an eligible escalation target. It does not prove the process stopped. Resume routing requires current consent and policy, then drains retained events through normal admission.

Hibernate changes physical execution. A daemon command checkpoints if reserved capacity permits, stops the process, and records acknowledgment. Only confirmed termination releases its runtime capacity. The anchor remains occupied by the same conversation unless the operator also vacates it. Waking a hibernated conversation requires a new admitted resume and current credentials. Routing can be paused independently.

Vacancy removes the current role occupant. Killing a role conversation increments its generation, revokes its capability, and clears conversation_id in one mutation. Child reporting edges and provenance remain unchanged. This action does not stop the subtree. Workers retain their own bounded execution authority; a replacement lead can manage them after reading current claims. Any request carrying the former lead's capability is rejected.

The vacancy mutation records a reconciliation event rather than rewriting every decision and pending message. Readers immediately treat the role as unavailable. Bounded workers reroute ordinary decisions and redispatch unacknowledged events. Protected asks were already with the human. A stale consumer cannot acknowledge an event after the generation changes.

Rotation combines vacancy and replacement while preserving the role identity. An optional handoff captures current claims, evidence, open decisions, and uncertain effects. A dead role can be replaced without a handoff. A compare-and-swap advances generation and selects one replacement; launch follows admission. The old session cannot reclaim the seat by waking first. Its token, pending commands, state writes, task actions, answers, dispatches, and acknowledgments all face the generation fence.

Revocation, scope moves, and retained work

Membership revocation first invalidates the principal's access epoch and prevents new reads and dispatches. Server transactions recheck current resource ACLs. Removal events clear replicas and derived summaries. A gateway rechecks before dispatch; an already dispatched effect is reconciled, since permission changes cannot retract bytes already sent. Revoking a person does not silently choose a new responsible human. Unassigned responsibility is a visible blocker.

Reparenting begins with a human preview of affected tasks, audiences, budgets, and running or uncertain permits. The first managed pilot rejects moves with active execution. A later migration may freeze admissions, increment topology and grant revisions, and page through bindings with a durable cursor. Each page validates the expected scope revision. A concurrent binding edit becomes a conflict, not a silent rewrite. Finalization requires all pages reconciled before admissions reopen.

Old receipts and permit attribution paths never move. New work uses the new path. Existing permits finish or reconcile against the path reserved at admission; moving a project cannot erase a parent's liability. Changing workspace requires a separate visibility migration and explicit consent, not merely a parent-pointer edit.

Retirement stops new admissions and preserves decisions, receipts, and role history. A subtree stop requires an explicit preview and only affects sessions covered by managed consent. Existing containment behavior remains separate from reporting. No lifecycle transition deletes a worktree. Retention may archive verified clean work after a policy period. Dirty files, unmerged commits, pending approvals, and uncertain effects block automatic archival cleanup. Destructive deletion remains a separate human-authorized action.

5. Authority, runtime limits, and budgets

What can be enforced

Existing, from the architecture review. CLI authentication identifies a user and token, not a session principal. Native runtimes can launch detached processes. Account heartbeats report account windows, while transcript messages may contain model and token usage. None of these facts establishes isolated worker authority, complete usage coverage, or a hard monetary cap.

Proposed. Offer two honest modes. An observed role on a trusted local machine produces scoped reports and recommendations. Managed execution requires an isolated runtime, a scoped principal, mediated effects, and supported admission controls. No existing Claude, Codex, or other adapter is assumed to satisfy those requirements merely because it supports spawning or reports tokens.

A human sharing a workstation with an unrestricted agent cannot rely on a prompt to protect credentials. The agent may read configuration, launch another CLI, reuse a browser session, or call a provider directly. Server checks cannot stop an effect that never reaches the server. Local observation is useful, but its cooperative limits must remain visible.

Actor authentication and current authority

A proposed scoped token contains signed claims {principal_id,actor_kind,role_id?,session_id,generation,workspace,audience,scope_ref,expires_at,grant_version,access_epoch,permit_id?}. For a role principal, role_id and the current anchor generation are required. For a worker, permit_id is required and generation is its task fencing counter; its reporting role is attribution, not the worker's credential owner. actor_kind is worker, role, or service; the token cannot claim human authority. Tokens are short lived and audience-bound. --from, session identifiers, acting_user_id, and origin fields remain attribution only.

Store revocation state in proposed execution_principals: principal_id, actor_kind, role_id?, permit_id?, delegation_root_id, session_id, generation, workspace, scope_ref, grant_version, access_epoch, audience, expires_at, revoked_at?, and credential_key_id. Index by principal_id and role_id,generation. No raw token enters a synced record or transcript. A service authenticates its own dispatcher role and does not impersonate a worker by changing request arguments.

Every managed mutation checks the token signature and audience, then loads current principal, applicable anchor or task fence, policy, consent, and target access. The check and internal write occur in one transaction. Equality of generation is required, not merely a lower-bound comparison. Historical ownership, a device identifier, or a plausible session name cannot replace the check.

A reviewer assignment requires a different delegation_root_id from the executor. Only the human control path may provision an independent reviewer root; workers cannot mint one by opening another session.

A human-only endpoint uses a distinct control channel whose credentials are unavailable to the managed runner. Browser login alone is insufficient if the runner controls that browser. Sensitive confirmation binds the exact operation through this channel. Legacy host-token endpoints cannot offer an alternate path to mutate managed claims, grants, approvals, or permits. During migration they must reject those writes or delegate to the same verified control path.

Grants narrow resource authority. Workspace access, resource ACL, role scope, and allowed operation must all pass. Visibility of a team project does not imply permission to stop its sessions. Parent scope does not grant membership in private rooms or #standup. A chat request from a human creates a preview of scope, adopted tasks, allowance, and sensitive effects. Confirming that preview creates one operation keyed to the source thread message and its revision.

Protected effects and approvals

Protected classes are purchases and billing, destructive data changes, production changes, auth and access changes, external communication, and unresolved user-facing product choices. Ordinary coordination includes choosing among already authorized implementation approaches or scheduling an allowed retry. A question labeled approach can still request a protected effect. The gateway classifies the concrete operation and resource, rather than trusting the label.

Unknown operations require human review and remain disabled if no safe execution adapter exists. Keywords may flag suspicious prose for review. They never grant authority, prove the absence of a protected effect, or secure shell access.

An approval binds operation, exact resource, argument hash, resource revision, policy revision, destination audience, expiry, and permitted principal. A mutation that changes any of these requires a new approval. Approval of a production deployment does not also approve deletion of a database or a message announcing the release. An ordinary answer and its rationale grant no implicit external capability.

The gateway validates the approval immediately before dispatch and records its operation identifier. Internal authorization and dispatch intent commit together. External success cannot share the database transaction, so the gateway records a receipt or an uncertain outcome. It retries only when the provider supports idempotency or reconciliation proves no effect occurred. Human overrides cancel pending intents. Completed effects require an explicit corrective action.

Compute allowance is a separate permission. It may fund model turns within an approved budget. It does not authorize buying subscriptions, increasing provider limits, provisioning paid infrastructure, changing billing, or sending email. A budget increase and a purchase approval are different operations with different targets.

Sandbox and adapter capability matrix

Managed isolation must deny access to host tokens, the human browser profile, production secrets, and unrestricted host filesystem paths. Filesystem writes are restricted to approved workspaces. Network credentials and effectful services are reached through gateways. Native child processes and tools are either mediated before execution or disabled. An adapter unable to impose these restrictions remains observed.

Reservations before compute

All queued, starting, running, and uncertain launches occupy capacity at the role's applicable ancestors and device. A queued launch is already a reservation, so two daemons cannot both consume the last slot. Admission also increments daily launch count. A cancelled admission releases capacity and unused money after reconciliation; it does not erase the admission from the daily count and invite unlimited launch churn.

Each model turn, trigger wake, resume, fork, and supported native helper requires the relevant permit before spending. A long-lived process does not gain unlimited autonomous turns from its initial launch permit. A new turn can reserve money without taking another process slot. Permit kinds make the distinction explicit.

For each applicable ancestor, enforce:

settled_usd_micros + reserved_usd_micros + request_usd_micros <= limit_usd_micros.

The admission transaction checks every account independently. A minimum of nominal limits is insufficient because siblings have already spent different amounts. Capacity and daily counters use analogous checks. Ancestor budget rows exist even where no standing role occupies that scope. Skipping a manager does not skip the workspace budget.

Illustrative example, not measured usage. A workspace allows $100 for a period, a project $40, and a plan $20. Workspace settled spend is $70 with $15 reserved. The project has $20 settled with $12 reserved. The plan has $8 settled with $4 reserved. A request bounded at $6 yields totals of $91, $38, and $18. All three checks pass.

After that reservation, a sibling plan requests another $4. Its own account might have ample room, but the shared project now has $20 settled and $18 reserved. Adding $4 would reach $42, so admission fails. No permit or task claim is created. The workspace's larger limit does not rescue the project.

For an illustrative count check, suppose workspace, project, plan, and device hold 5/8, 3/4, 1/2, and 3/4 slots. The accepted launch takes them to 6/8, 4/4, 2/2, and 4/4. Another project launch fails even if a sibling plan has zero workers. These counts include queued starts and uncertain executions.

If the admitted $6 request completes at $4.50, settlement transfers $4.50 to settled usage and releases the remaining $1.50. Each ancestor applies the same unique receipt once. A duplicate receipt makes no change. The three views describe the same $4.50 charge; adding workspace, project, and plan totals together would triple-count it.

Hard money bounds and honest estimates

A hard USD cap requires a defensible maximum charge before dispatch, covering the provider request, bounded output, applicable tools, retries, and billing rules. If the adapter cannot provide that bound, hard_required admission fails. The most expensive model currently in a price table is not an upper bound for an unknown model or future tool charge.

Estimated mode still enforces admitted launch and turn counts. It records priced estimates, authoritative charges where available, and missing coverage separately. A spend threshold can refuse further requests once known estimates exhaust it, but it cannot guarantee a dollar ceiling. Do not claim a universal overshoot bound of one heartbeat or one turn; those units have no known monetary maximum on an uncontrolled adapter.

Reservations for hard coverage include a small configured checkpoint allowance. It is charged against every ancestor when admitted, not invented when the main budget runs out. A checkpoint permit may use only that reserve for a bounded handoff. If no reserve remains, record status and the human decision without another model call. Emergency stop, approval storage, and reading the queue remain available at zero compute budget.

Already admitted requests may finish within their reserved bounds. Further requests are denied at the boundary. Emergency revocation may interrupt a running request; the design does not promise that every process always finishes. Unknown in-flight charges remain reserved until reconciliation rather than being released by a timer.

Receipts, periods, and historical attribution

Transcript usage and provider or adapter receipts supply evidence. Account percentage windows describe account quota health, not session cost or pricing. Keep quota checks independent of estimated dollars. Respect the parent account's limits and provider restrictions. Do not create or switch to a fresh account to evade them. Reset or an explicitly permitted account change requires a new admission check.

Normalize receipt sources before settlement. Provider request identifiers take precedence over a matching transcript observation when they describe the same charge. A stable mapping prevents charging both. Replayed transcript lines deduplicate by source identity and revision. Cumulative counters carry an epoch and apply only validated differences. Resets start a new epoch; edits append correction evidence. Contradictory or unmatched observations remain incomplete rather than becoming guessed charges.

The receipt insert, normalized delta, permit settlement revision, ancestor balance updates, and bounded daily projections commit atomically. Corrections preserve prior evidence. Periodic rebuilds compare the projection with receipts and permits. They run in pages and cannot reset live admission counters beneath active permits. A mismatch freezes affected admissions until reconciled.

Each workspace policy selects an explicit timezone. Store concrete start and end instants for every period, including daylight-saving changes. All descendants use those period boundaries regardless of host location. Timezone changes take effect only at a future closed boundary, never by rebucketing today's spend. Concurrency uses lifetime capacity rows rather than resetting at midnight.

Book a request to the immutable scope and ancestor path captured by its permit. Receipt arrival after midnight or after a move still settles that original reservation. This admission-period budget view can differ from a provider invoice-date view; label them separately. A turn spanning a boundary retains its original period until it settles. New requests use the new period.

Scope moves affect future permits only. Old liabilities stay under the old parent even when the UI now groups the role elsewhere. A current-parent activity view can link historical charges, but cannot reassign their accounting. Work without a reliable admission binding stays explicitly unattributed or observed; the proposal does not fabricate a conversation workspace or claim complete historical coverage.

Human control and visible limits

A budget edit records an immutable policy revision, effective period, reason, and authenticated human authority. Raising a child allowance does not raise an ancestor. Lowering a cap below settled plus reserved usage blocks new admissions and shows the existing commitment; it does not rewrite history or blindly cancel completed work.

The interface should distinguish settled charges, estimates, reservations, and unpriced coverage. It names the refusing ancestor or device only when the viewer may read it. Queue age, quota reset information, uncertain liabilities, and checkpoint availability explain why work is waiting. Warning colors are presentation choices, not alternative enforcement thresholds. No dollar amount, concurrency count, or automatic refill policy becomes consent merely by appearing as a suggested default.

Use pure tests for scope resolution, bounded paths, immutable attribution, cost arithmetic, audience intersections, and inbox placement. Use a transactional test environment for claims, quotas, generation changes, answer revisions, and receipt settlement. Export the seed and transition log on failure so the sequence can be replayed exactly.

End-to-end paired evaluation

Run the deterministic scenario through the real server, daemon, CLI, browser, and mobile UI in a scratch workspace before enabling managed execution. Verify clicks and rendering, including collapsed roles, offline pending requests, human ownership, stale counts, and permission prompts. Shared projection fixtures do not prove native mobile implements nesting or cache invalidation.

Evaluate usefulness separately from mechanical correctness. Collect seven working days of baseline observations before setting rollout defaults. Then run small paired tasks with similar scope and difficulty: human coordination versus an observed lead, followed by a managed lead only after its capability gates pass. Alternate ordering, use equivalent task sets where replay would reveal the solution, and keep reviewer judgments independent of the tested role.

Measure human attention time, manager compute overhead, unresolved escalations, missed critical asks, quality-adjusted outcomes, and unpriced usage coverage. Record task difficulty and evidence completeness. Do not treat a low override rate as proof of correctness: humans may miss bad recommendations or accept them without inspection. Investigate every missed critical ask and unauthorized effect separately from average performance.

Report quality is the match between claims and evidence, freshness of that evidence, and coverage of the actual work. A report with 90 percent of tasks marked done can still omit the only production blocker. Review sampled claims against source artifacts and revisions. Score unsupported assertions, stale evidence, missing critical constraints, and truthful uncertainty. A shorter report that exposes an unresolved effect can be better than a complete-looking task summary.

Performance targets and release decisions

The following are proposed targets, not measurements. Under a synthetic load of 100 active executions, 1,000 pending routine events, and three standing role levels, target p95 admission below 500 ms excluding external launch time. Target protected asks visible within two seconds of server commit for an online client. Target routine dispatch within ten seconds when budget and capacity exist, with a configurable coalescing window inside that allowance.

Keep each hot mutation within the bounded reads and writes in section 3. Target no growth in admission work with total historical conversations. Measure contention, retries, event backlog age, browser rerenders, and mobile memory. Benchmark large histories separately from active execution counts. Do not borrow unrelated machine-load anecdotes as evidence that these targets are met.

Gate observation on privacy and truthful reports. Gate managed project pilots on authenticated actors, claims, admission, event recovery, independent review, and adapter isolation. Gate wider hierarchy and automation on paired evaluation and operational evidence. A failed safety case blocks the affected capability, even if average latency and completion counts look good.

Rollback disables new managed admissions and preserves outstanding permits, receipts, decisions, and human controls. Continue reconciliation until liabilities are resolved. Do not erase the ledger, clear reservations because the feature flag changed, or kill unrelated sessions. Record which guarantee failed and which modes remain usable. The release decision must name tested coverage, remaining unknowns, and the evidence supporting it.

Pilot scope and operating limits

The first pilot should use one project, one lead, selected tasks, and a named responsible human. Choose work with reproducible criteria and reversible local artifacts. Keep production changes, purchases, destructive actions, auth changes, and external communications as protected requests outside worker authority. Existing human sessions remain independently controlled. Do not bulk adopt a project's historical sessions.

Use a supported isolated runtime for managed work. Record the billing account, device, allowed tools, compute allocation, concurrency limit, and review classes before admission. Where metering cannot establish reliable priced exposure, stay in observation or use a separately authorized supervised test that clearly discloses the limitation. Uncontrolled native tools offer an estimated meter and launch cap only. They do not provide a hard money cap.

Admission must check settled + reserved + request <= limit at every ancestor. Queued and starting work count. Receipts settle each usage event once. Rollups display the immutable attribution path without charging it twice. Daily periods use an explicit workspace timezone fixed for that period. Unknown costs remain visible, including the fraction of activity that could not be priced.

Compatibility, deployment, and rollback

Implementation should add compatible fields and read fallbacks first. Existing anchors retain behavior until explicit adoption. Legacy decisions keep their human route; missing classification is unknown. Do not backfill old questions as ordinary approvals. An old client may read safe compatible state, but cannot acquire managed authority through missing actor or version fields.

Release the backend through packages/convex/deploy.sh before a client calls new functions. Ship the required CLI adapters before enabling managed execution on a device. Web and native mobile oversight must be ready before managed workers depend on nesting. Shared projection changes alone do not satisfy mobile acceptance. These are future deployment requirements; this proposal performs no deployment.

Rollback disables new managed admission and returns pending human obligations to visible human routing. Existing approved attempts are inspected and either allowed to finish within their authority or stopped through an explicit control. Preserve tasks, evidence, decisions, receipts, lineage, and unresolved effects. Revoke old capabilities and fence stale sessions. Never delete dirty worktrees or unmerged commits as rollback cleanup.

The operator must be able to store a human answer and request emergency stop when the compute allowance is exhausted. Completed external effects require reconciliation. Retrying a stopped or uncertain operation must not repeat a purchase, message, or deployment blindly.

Source facts that materially shaped the design

An anchor already separates identity from hosting. The bot user provides a visible identity, while a human host runs the session. That makes it a useful durable role primitive. It does not make the bot's displayed name an authenticated service principal.

Session ownership already has separate dimensions. Human owners, runner/biller, device and initiator answer different questions. Adding a reporting role should preserve those meanings. Putting bots into the human owner set would break the existing inbox responsibility model.

The task association is historical, not an exclusive lock. tasks.conversation_ids records related sessions. The inspected tasks.update binding path can associate more than one session with a task; checking a conversation's current task does not reserve that task against another claimant. A managed attempt needs its own atomic claim contract.

Nesting has existing semantics. parent_conversation_id identifies contained subagents. spawned_by_conversation_id records provenance, with special presentation for Claude team members. The shared rider traversal handles chains, but the existing cleanup and individual surfaces need explicit review. Supporting a deeper placement model does not automatically build an organization UI on mobile.

Account capacity and session consumption are different measurements. Messages can carry token usage. Provider window percentages come from account reporting. Neither a percentage nor an absent receipt should be converted into an invented dollar cost. The declared anchors.daily_session_cap was not an enforced budget in the surveyed implementation.

Current summaries have different purposes. cast summary and cast handoff extract transcript structure deterministically; server insights and story summaries use model generation. Both can help recovery. Neither guarantees that a test ran, an artifact exists or a user accepted the result.

Current messaging uses human authorization plus attribution. performSessionSend validates the caller's right to send to the target; its optional sender reference supplies provenance. Managed agent authority requires an additional authenticated actor context. A source guard checking for a function name cannot establish that trust.

Questions resolved by engineering

The organizational parent points at a role, so replacing a session does not rewrite reporting history. The UI resolves the live session when it needs to show a conversation. A departed session keeps its history and loses authority to affect the current role generation.

Vacancy and escalation differ. A task can remain assigned to a vacant lead while its pending decision routes to the next eligible actor. This keeps responsibility visible and prevents a temporary outage from silently reorganizing the project.

The human control path remains available when agent execution is paused or out of budget. Saving an answer or issuing stop cannot depend on admitting another model turn. Execution resumes only when an eligible permit and valid approval exist.

Summary generation preserves the audience of its inputs. A broad project lead cannot copy private task details into a public channel because it can read them. The receiving surface must be entitled to the disclosed facts. Deleting or revoking access removes cached previews as well as server reads.

Retention preserves work. An idle process may hibernate; a completed attempt may archive. Neither action authorizes deletion of dirty files, unmerged commits or artifacts still under review. The cleanup preview must identify those conditions.
