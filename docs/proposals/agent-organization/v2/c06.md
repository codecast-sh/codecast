## 6. Integration map

The organization is only worth building if it is made of the primitives people already use. This chapter walks every one of them and states, in one row each, what it does today, what the organization adds, and what it does not touch. A row that says "unchanged" is a promise.

### Work items

| Primitive | Today | With an organization | Unchanged |
|---|---|---|---|
| Task | Created by humans or agents; claimed by a session with `cast task start`; comments typed progress, blocker, review or note; `cast task ready` lists unclaimed work; subtasks two deep; acceptance criteria, verification evidence and execution status already on the row; synced both ways with Linear and GitHub issues | The task's filing is its reporting line. Its state and comments feed the lead above it. A lead may create, update, assign, start with `--spawn`, and close tasks in its scope at stage three. The task gains a read only chip: the lead it reports to. | Schema, statuses, depth cap, ready rules, issue sync. Workers' commands. |
| Plan | Groups tasks toward a goal; a session binds with `cast plan bind`; comments carry decisions with rationale; progress derived from task statuses | A plan may have a lead. Its decision log is the plan lead's log. Plan orchestration, implementer and reviewer waves, is what a plan lead runs. The plan page shows the lead's brief headline. | Binding, comments, progress derivation, `cast plan context`. |
| Project | Groups tasks, plans and docs; the triage unit; Linear teams and GitHub repos import as projects; project updates with an agent author and a digest kind already exist; plans have an owner, projects do not | A project may have a lead and gains an owner. The project page gains a lead panel: brief headline, next actor, freshness, a link to the lead's page. The lead's cadence brief posts as a digest update, so the existing updates surface carries it without flooding. Refiling a task or plan between lead scopes is a human action; the server refuses it from a role credential or the claimant session. | Filing, `cast project show`, `cast project post`, integrations import. |
| Doc | Agents and humans create and edit; six types; `cast doc` CLI; live editing state, but no browsable version history and no role owner | Briefs, standing briefs and scope notes are docs with two new types, an anchor as owner, and a version record the brief diff reads. | Everything else. |

### Sessions and agents

| Primitive | Today | With an organization | Unchanged |
|---|---|---|---|
| Anchor | One standing agent member per team or personal workspace, with its own bot user, a host who runs and bills it, a persistent conversation, a persona, a project path and a daily session cap; a standing briefing generated from the row at each send; woken through one delivery function by chat mentions, `cast anchor wake` and Slack; speaks with `cast anchor say` | The anchor is the workspace lead. Its scope type gains `project` and `plan`, and uniqueness becomes one anchor per scope. It gains the brief format, the cadence wake and the morning brief page. `cast anchor create` learns `--scope project:<name>`, keeping the verb; the existing `-C` flag keeps meaning the working directory. The bot user's team membership is what gives a lead read access, since an `agent:` assignee on a task grants nothing today. | The single wake function, Slack channel links, `say`, the daily cap as the launch cap. |
| Spawned sessions and subagents | `cast spawn` starts fresh sessions; `--subagent` sets a hidden parent, and the row leaves the top level list; the visible spawner pointer only labels and links; one containment rule decides which pointer nests. The task spawn function already sets the hidden parent to the session that created the task's plan. | A lead's workers nest under the lead: `cast task start --spawn` passes the calling session and the task spawn function sets the hidden parent to the lead's session instead of the plan's creating session. Nested rows leave the top level list and the phone's inbox, as subagents do today; the tree and the reporting chip are where they are found. Reporting line is computed from filing, not from spawn, so a refiled worker keeps its spawn history and changes its lead. | Spawn provenance, the containment rule, nesting rendering, the projection version bump those tests require. |
| Forks | `cast fork` branches a conversation into the human's inbox | A lead may fork itself to explore two directions on a question and fold the answer into its brief. The forks nest under it. | Fork semantics. |
| State line | `cast state --status` pins what a session is doing and who acts next; the inbox files the session by status | A lead's state line is the first line of its brief and acknowledges the wake's events. Workers' state lines are what leads read first. Dormant is the lead's resting state between wakes. | Statuses, buckets, the settle classifier. |
| Labels | Personal filing per user, one label per session, invisible to teammates | Not used for scope: a lead's label would land in its host's personal filing and overwrite the human's own. The fleet watch filters by reporting line instead: `cast sessions --reports-to <lead>` reads the cached reporting pointer. A lead never touches labels. | Everything. |
| Stash, hide, kill, restore | Inbox visibility gestures | A lead uses them to tidy its finished workers, under the retention rule. The brief lists what it tidied. | Semantics. |
| Sessions watch | `cast sessions -w --json` streams state transitions | The server watches on the lead's behalf and delivers transitions as event wakes; a lead does not run a watch of its own. `--reports-to` narrows the human's watch to a lead's subtree. | Everything. |

### Decisions, chat and triggers

| Primitive | Today | With an organization | Unchanged |
|---|---|---|---|
| Decisions | `cast decide` posts a question with options and context; it lands in the human's queue; advisory mode keeps working with a default; the row is never a delivery channel, the web client sends the answer as a message | A decision still lands in the human's queue at insertion. Leads attach recommendations as hops, and a lead with a grant may answer first. The card shows the ladder and carries the grant control. Protected classes have the human as holder from insertion. A lead's answer needs one new mutation that resolves the row and sends the message in one transaction, callable with a role credential, and a holder index. | The command, options, context, advisory mode, edit and cancel. |
| Team chat | Channels, threads, mentions resolved by roster name; `@anchor` starts an agent turn on a human's line through a placeholder message; a channel to anchor mapping table already routes a channel to a chosen anchor, with the team's first active anchor as the fallback; `cast chat reply --pass`; `cast anchor say` | Binding a channel to a project or plan lead is a row in the existing mapping table, written by `cast anchor link-channel --chat`, allowed only when the lead's bot user is a channel member. `@lead` is a new resolver that reads that row, and the team fallback filters to the workspace anchor so project leads never catch unbound channels. Intake proposals render in the thread. Leads never wake on agent written lines. | Mentions, threads, reactions, the follow rules, the one turn per thread rule. |
| Triggers and wakes | Triggers: `--in`, `--every`, `--on` for pull request, push and issue webhooks; a trigger binds to a conversation and dies with it; `--safe` runs remove edit tools and block push, commit and deploy commands. Anchor wakes: one delivery function that enqueues a pending message with a client id that deduplicates; it does not merge. | An event table and a batch builder sit in front of the delivery function: events wait while the lead is working, a batch is built when its state line lands, and the batch id is the client id, so delivery is idempotent. The new event kinds (task transition, decision climbed or answered, worker settled, stall, brief rewritten below) are backend work. Only the cadence is a trigger row, owned by the role and retargeted on replacement. Leads at understand and decide run in the existing safe mode. | Trigger commands, webhooks, the delivery function. |
| Publish | `cast publish` makes a page with versions and comments | A workspace lead publishes a weekly report if the standing brief asks for one. Viewer comments on it reach the lead as an ask (a message that starts a lead's turn; chapter 8 lists the three kinds of wake). | Everything. |
| Memory and search | `cast search`, `cast context`, `cast ask` across sessions | A lead's scope notes are the durable form of what it learned. Search is how it finds prior sessions on a stall. | Everything. |

### Surfaces

| Surface | Today | With an organization |
|---|---|---|
| Inbox | Buckets by who acts next; cards; subagent nesting; a teammate rides its lead's bucket; a worker's open decision already lifts its parent into the questions bucket | Workers nest under their lead. Cards gain a chip naming the lead they report to. One new filter, by lead. Lead sessions file stashed and hidden by default and surface only when blocked. Human obligations show through folds by the existing lift rule. Nothing removed. |
| Task board and project pages | Lists, filters, project triage | Project and plan pages gain a lead panel. Task rows gain the reporting chip. |
| Decision queue | Cards with options and context | Cards show the ladder, recommendations, and the grant control. |
| Conversation view | Transcript, header pills, comment rail | A lead's conversation is an ordinary conversation. Its header shows the scope it leads. A worker's header shows the lead it reports to. |
| New | The orchestration dashboard and fleet board already show agents by plan and wave | The morning brief page. The organization tree, grown from the fleet board. The lead page with track record. The health page. The hire flow. |
| Mobile | Inbox and transcripts; decisions are synced but no screen shows or answers one | The brief page, a decision card that can answer, and the tree. |
| CLI | | `cast org` and the extended `cast anchor`, chapter 9. |

### What the organization never touches

- The workspace access key and the team routing field stay separate, as the codebase requires. A lead reads through the same access checks as any agent. Reporting lines grant nothing.
- Conversations keep their own visibility rules. A lead's brief is computed only from what the lead's audience may read.
- Local first rendering. Every organization surface renders from the store; the brief, the tree and the health page are synced collections registered once, with feeders, like everything else.
- The settle classifier, work states and buckets. A lead is a session and is classified like one.
- Human sessions. Visible in briefs where the audience rules allow; never directed without the grant in chapter 5.
- Private sources. A brief is rendered per reader from claims that carry their source audience (chapter 3); a lead's prompt is fed only sources at the brief's declared audience; cost lines need financial read authority.
