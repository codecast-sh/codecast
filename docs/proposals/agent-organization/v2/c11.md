## 11. Data model and engineering map

The product needs five additions to the data model. They are leads at project and plan scope on the anchor row, a brief document type with required coverage and versions, routing fields and a short id on decisions, grants as policy revisions, and a responsible human on projects and plans. Everything else is a query over records that exist. Version one's enforcement contracts, its chapters 3 and 5, stand unchanged, and this chapter uses its names.

### Existing records the organization stands on

| Record | Exists today | What the organization relies on |
|---|---|---|
| `anchors` | Team and user scope; a bot user with a team membership; a host who runs and bills; a persistent conversation; persona, project path, model, status and a daily session cap; a standing briefing generated from the row at each send; one delivery function for every wake; a channel to anchor mapping table | The role. Extended to project and plan scope with a parent pointer. The bot membership is the lead's read access. |
| `conversations` | Three distinct parent pointers: a hidden subagent parent, a visible spawner filled once and never changed, and the team stamps a coding agent writes; one containment function decides which nests; work bindings to a task or plan; state line and work state; a session insight per settled session | Reporting line is computed from the work binding's filing. Nesting is unchanged. The task spawn function points the worker's hidden parent at the lead session. |
| `tasks`, `plans`, `projects` | Filing relationships; task history and comments; acceptance criteria, verification evidence and execution status on tasks; plan entries with decisions and rationale; a join policy and orchestration metadata on plans; orchestration events per plan; project updates with an agent digest kind | The scope graph. No new relationship is added; the reporting line is a query over the ones that exist. Orchestration events are the lead's event source for its own workers. |
| `docs` | Typed documents; live editing state; owned by a user; no browsable version history | Briefs, standing briefs and scope notes, with the additions below. |
| `session_decisions` | Question, options, context, advisory default, answer, resolver; asked by a session; the row is never a delivery channel, the web client sends the answer as a message; indexed by asker's owner and status | Gains routing, a short id and a resolve and deliver mutation, below. |
| `role_policy_revisions` | Proposed by version one chapter 3: append only budgets, grants of decision classes, launch caps, with author, reason and effective time | Budgets, stage and grants all live here. `anchors.daily_session_cap` stays as the launch cap until readers retire, as version one said. |
| Anchor delivery, triggers | One delivery function enqueues a pending message with a client id that deduplicates and cancels; triggers bind to a conversation and die with it, with webhook shaped event filters | Event and ask wakes ride the delivery function with the client id as the coalescing key. The cadence is a trigger row owned by the role and retargeted on replacement. New event kinds are backend work. |
| Team chat | Channels, threads, mentions resolved by roster name; anchor wake on human mentions through a placeholder message; a channel to anchor mapping table; the team fallback picks the first active anchor | A mapping row per bound channel; a new `@lead` resolver that reads the row; the fallback filtered to the workspace anchor. |
| Store registry | One registration per synced collection; feeders; wake signatures | Every new collection below is one registration with `feeds`, and every surface reads the store. |

### New fields and records

**On anchors.** `scope_type` gains `project` and `plan`; `scope_id` points at the project or plan; uniqueness becomes one non retired anchor per `(scope_type, scope_id)`, as version one indexed it; `parent_anchor_id` is the lead above, recomputed from filing when a project or plan moves; `stage` is `understand`, `decide` or `direct`; `brief_doc_id` keeps version one's meaning, the standing brief; `digest_doc_id` is the account this version calls the brief; `notes_doc_id`; `cadence` as a time of day or an interval; `coalesce_ms`, `stall_after_ms`. Generation and lifecycle are as version one defined them. Consent is given at hire for the scope, not per task; chapter 12 records that change.

**Docs.** Two new types, `brief` and `standing_brief`; an `anchor_id` owner; a `doc_versions` record with the version number, the writer, the watermark and the body, which the diff view reads; and a per user, per doc last read version, which "show changes" reads. A brief's metadata carries `source_watermark`, `coverage:{sessions_read, sessions_total, tasks_read, tasks_total}`, the declared `audience_ref`, and a `claims` array of `{text, source_refs[], audience_ref}` so per reader rendering, the claim audit and the diff view do not parse prose. The server refuses a brief without coverage. Versions are kept for 7 days, then one per day.

**On decisions.** Version one's fields: `decision_class`, `class_assigned_by` (server, from an action request or the classifier), `assigned_role_id` as the holder when a lead holds a grant, `answer_authority` as `human` or `role`, `route_deadline` per hop; a paged `decision_hops` table as version one specified, never an inline array; a short id with a new prefix, `cd-1042`, so a decision can be named in briefs, cards and the CLI; `override_reason?`. A new mutation resolves the decision and enqueues the answer message in one transaction. It accepts the responsible human, the scope's owner, a team admin, or a role credential with a matching grant; today only the row's owner may resolve. First commit wins and the second caller sees who answered, as today. `resolved_by` widens to a bot user; a `by_holder_status` index serves the lead's queue. Protected classes, limit changes, and questions from human started sessions get the human as holder at insertion, with no hop. A decision asked by a lead's own session carries its scope and gets the scope's responsible human as holder.

**Grants.** A policy revision whose `ordinary_decision_classes` names the class and whose `reason` links the decision card it was granted from, with `expires_at` 30 days out. Agreement counting is a query over hops and answers, by originating lead, class, scope and distinct askers.

**Owners.** `projects.owner_user_id`, new; plans already carry `owner_id`. Set at hire for a scope with a lead and editable on the page. A task's responsible human is its assignee, else its plan's owner, else its project's owner.

**Spawn and filing.** `cast task start --spawn` passes the calling session; the task spawn function sets the worker's hidden parent and visible spawner to it. The conversation caches `reports_to_anchor_id`, recomputed on refiling, never trusted for authority, and `cast sessions --reports-to` filters on it. The task and plan update mutations refuse a change of plan, project or parent from a role credential and from the task's own claimant session; a move between lead scopes is a human action.

**Close.** `cast task done` from a role credential is refused unless a verdict row matches the task's `review_policy`, which the server sets from the diff's paths and the effect class; a lead may tighten it, a human may set it either way.

**Wakes.** An event table with `event_key`, kind, source id, source revision and destination role, as version one chapter 3 defined; a batch builder that leases up to 32 events while the lead's work state is not working and enqueues one pending message with the batch id as the client id; `cast org ack <batch>` with `--defer`; a 15 minute batch lease. Stall events key on the conversation's message count and last activity time, both existing fields. Scope note entries carry an `audience_ref`.

**Credential.** Stage one needs the minimal per session role credential from chapter 8, a server side allow list keyed on it, and the trigger runner's existing safe mode for lead sessions. Stage three needs version one's full scoped credential and admission.

**Track record.** Not a record. A query over decisions by originating lead and outcome, over sampled answers, and over brief claim audits, rendered on the lead's page. If it proves slow it becomes a rebuildable daily projection, as version one did for usage.

### Queries the product needs

- **Reporting line** for a work item: follow task to plan to project to workspace, return the first non paused anchor at each level and the responsible human. Bounded to four steps.
- **Organization tree** for a workspace: anchors with their headline, freshness, next actor and obligation count per reader, plus raw project and session rows where no anchor exists. One paged query, registered as a synced collection, grown from the fleet board's query.
- **Scope read** for a lead: everything in scope since a watermark, the input to every cadence wake, served by `cast org scope`.
- **Brief with diff**: two doc versions and their claims arrays, filtered to the reader.
- **Decision queue for a holder**: decisions where the holder is this role and the hop deadline has not passed.
- **Grants for a scope and class**: a single indexed lookup on the current policy revision, used on every lead answer.
- **Health**: counts over decisions, grants, brief versions and usage by anchor for a period.

### What ships where

| Piece | Backend | CLI | Web | Mobile |
|---|---|---|---|---|
| Leads at project and plan scope | Anchor scope extension, uniqueness, reporting line query, owner fields | `cast org`, `cast anchor create --scope` | Hire flow with host and payer, lead panel, lead page | Read only |
| Credential | Per session role token, server allow list, safe mode for lead sessions | none new | Host line on the hire flow | none |

| Wakes | Event table and batch builder in front of the delivery function, new event kinds, cadence trigger owned by the role, retarget on replacement, batch lease | `cast org ack`, `cast org reply` | none | none |
| Ladder | Server assigned class, holder, hops table, short id, resolve and deliver mutation, holder index | `cast decide escalate`, `answer`, `ls --for-me` | Card with ladder and recommendations | Decision card that can answer |
| Grants | Policy revisions with expiry, agreement query, sampled review | `cast org grants`, `revoke` | Card control, lead page, handled overrides | handled overrides |
| Tree | Tree query, synced collection, `--reports-to` | `cast org`, `cast sessions --reports-to` | Organization view | Tree |
| Health | Aggregation queries | `cast org health` | Health page | none at first |
| Direct | Full scoped credential, admission, spawn parent change, filing and close refusals, reviewer provisioning from the lead above, stall events | none new | Budget on the hire flow | Stop with preview, take over review |

Backend pieces ship before the clients that call them, through `packages/convex/deploy.sh`. Every query that only enriches an existing surface goes through `useQueryNoThrow`, so a client ahead of prod shows today's view instead of an error boundary. Two gaps the surveys confirmed and version one already named: an `agent:` assignee grants no read access, so leads read through their bot user's membership; and no per session token or dollar accounting exists in the backend, so the cost section of every brief depends on the usage receipts from version one chapter 5, and reports "unpriced" until they exist.
