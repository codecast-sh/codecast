## 9. CLI and agent workflow

The CLI is how leads work and how humans inspect them from a terminal. The design rule is that a worker learns nothing new, a human learns one verb, and a lead uses commands that already exist plus a short list under that verb. Every command below that does not exist today is marked new.

### For humans: `cast org`

```
cast org                            # new: the tree with each lead's headline
cast org brief [scope]              # new: read a brief; --diff since your last read; --json
cast org hire --project Codecast    # new: the hire flow; opens the standing brief in $EDITOR
cast org pause codecast             # new: stop wakes, keep the brief
cast org refresh codecast           # new: replace the lead's session from its records
cast org retire codecast            # new: keep history, stop the role
cast org grants [lead]              # new: what each lead may decide, where, since when, until when
cast org revoke codecast retry      # new: take a class back
cast org health                     # new: the health page as text or --json
cast org ask codecast "is sync landing this week?"   # new: an ask wake; the answer arrives as a message
cast sessions --reports-to lead:codecast -w --json    # new flag: watch one lead's subtree
cast search "cursor test" --author lead:codecast     # new flag; briefs and notes are indexed
```

`cast anchor` keeps working and gains a scope flag, because the workspace lead is the anchor: `cast anchor create --scope project:Codecast` is the same as `cast org hire --project Codecast`, and the existing `-C` flag keeps meaning the working directory. Existing anchor verbs apply to any lead: `wake`, `brief` to resend the standing brief, `say`, `link-channel`.

### For leads: existing commands plus four new ones

The examples below are a project lead's turns. Decisions have a short id of their own, `cd-1042`, which is new: today a decision has no short id. Version one wrote `sd-29`, a prefix the codebase already uses for project ids, so this version changes it and chapter 12 records that.

```
# Event wake. The wake message already lists the events and the decisions at this lead.
# Read compressed signals first: everything in scope since the last brief's watermark.
cast org scope codecast --since 2026-09-05T08:20Z --json    # new: plans, tasks, transitions,
                                                            # comments, bound sessions with state
                                                            # lines, child briefs, usage by scope

# One worker is stalled. Read compressed first, then the tail.
cast summary jx7a2f1
cast read jx7a2f1 40:
cast diff jx7a2f1

# Escalate with a recommendation (stage one), or answer (stage two, granted class only).
cast decide escalate cd-1042 --recommend 1 \
  --why "same test stalled two other plans this month; skip and file"
cast decide answer cd-1042 1 --why "..."

# Rewrite the brief. The server refuses a brief without coverage.
cast org brief write --file brief.json      # new: six sections, claims with sources, coverage, watermark

# End the turn: acknowledge the batch, deferring nothing, then pin the state line.
cast org ack wb-77a2                          # new; --defer <event id> for an unfinished effect
cast state --status dormant "Sync reliability stalled on the cursor test; \
  skip decision escalated with a recommendation. Next wake: worker settle or 09:00."
```

```
# Stage three: start work under budget, brief from the task, review on completion.
cast task update ct-49230 -d "..."           # constraints go on the task, not only in the prompt
cast task start ct-49230 --spawn --message - # the worker brief on stdin; nests under this lead
cast task done ct-49230 -m "Checked by review jx7c11e on 4b1c2: replay test reproduced."
cast stash jx7a2f1                           # tidy a finished worker this lead spawned
```

The new commands a lead needs are `cast org scope`, `cast org brief write`, `cast org ack`, `cast org reply`, `cast decide ls --for-me`, `cast decide escalate` and `cast decide answer`, plus the decision short id. Version one chapter 6 proposed the two decide verbs with these names and this version keeps them. `cast task start --spawn` changes on the server: it now receives the calling session and stamps the worker's parent and spawner from it, so the worker nests under the lead. A lead never runs a watch; the server watches its subtree and delivers transitions as event wakes. A human uses `cast sessions --reports-to lead:codecast -w --json` for the same view.

Independent review is not something the lead spawns. A human sets the review policy on the plan or task, and an independent reviewer is provisioned from the lead above or from the human control path, as chapter 4 describes. A lead may run its own check on a worker's claim, and the brief calls that "checked by the lead", never "verified".

### For workers: nothing new

A worker's commands are `cast task start`, `cast task comment`, `cast state`, `cast decide`, `cast task done`. All exist. One optional flag is new, `cast decide --class`, which proposes a class the server may tighten but never loosen. The only behavioral difference a worker may notice is that its `cast decide` may get an answer from a lead, and the answer says who gave it.

### Chat

```
@lead is sync landing this week?          # in #codecast, bound to the project: reaches the Codecast lead
@lead codecast how is sync?               # from any channel: reaches a named project's lead
@lead what needs me today?                # in an unbound channel or DM: reaches the workspace lead
```

A lead replies in the thread with `cast chat reply`, as the anchor does today, and passes on lines that are not for it. Agent written lines never wake a lead. A channel can be bound to a lead only if the lead's bot user is a member of it, and the lead's answers in a channel are filtered to what that channel's members may read.

### Structured output

Every `cast org` read takes `--json`. The brief's JSON is its six sections with source ids and audience per claim, coverage as numbers, and the watermark, so a parent lead, a script or a test can read it without parsing prose. The tree's JSON is the reporting graph with each node's headline, next actor, freshness and obligation count. The health page's JSON is the exit criteria from chapter 10 as numbers.
