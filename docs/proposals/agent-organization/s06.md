## 6. Agent workflow and CLI

Agents should work through the same tasks, plans, decisions and conversations that people see. The management feature adds explicit scope and authority to those operations. It should not require a second task tracker or a separate agent runtime.

**The commands below are proposed interfaces unless the table marks them existing.** They specify behavior for implementation. They are not instructions to run against today's CLI.

### Keep familiar commands

| Interface | Today | Proposed change |
|---|---|---|
| `cast anchor create`, `ls`, `wake`, `brief`, `say` | Standing agents for a user or team | Add project and plan scope, role IDs, permissions preview and observe mode |
| `cast task start`, `done`, `comment` | Bind work, change status, record progress | In managed execution, acquire an exclusive attempt and submit evidence for review |
| `cast plan bind`, `context` | Connect sessions and shared planning context | Preserve discussion bindings; distinguish them from holding execution authority |
| `cast spawn --subagent` | Start a nested worker session | Add a managed admission path that records task, responsible lead, permit and runtime coverage |
| `cast decide` | Ask a human with context and options | Route eligible ordinary questions to the assigned lead; preserve direct human escalation |
| `cast state` | Publish a short statement of current progress | Include structured next actor and evidence links in managed reports |
| `cast sessions -w --json` | Watch session membership and work state | Add filtering by reporting role and explicit authority/coverage fields |
| `cast trigger` | Schedule a turn or fresh session | Capture the role and policy version; recheck permission and admission when it fires |
| `cast label` | Personal, exclusive session filing | Preserve filing as a personal organization choice |

A role identifier must resolve independently of the current session. This page uses illustrative IDs such as `ro-4`; final naming remains a product choice. A CLI response should always include both the role ID and current session ID when a person needs to inspect execution. Product copy says “Observe”; the stored enum is `observed`. The CLI maps `--mode observe` to that enum, and `--request-id` to the API `operationId`. It must not introduce a second policy vocabulary.

### Create, inspect and adopt

```bash
# Proposed: starts in observe mode and shows the requested scope.
cast anchor create --project "Codecast: Sync & Reliability" --mode observe

# Proposed: inspect the persistent role, not just its current process.
cast anchor show ro-4 --json
cast anchor digest ro-4
cast anchor tree

# Proposed: preview exactly which work would become managed.
cast anchor adopt ro-4 --task ct-4102 --preview
```

The adoption preview includes the task title and revision, current owner, active session, proposed coordinator, current approvals and any access conflict. It reports whether the selected runtime can enforce the requested controls. Adopting a task does not silently take control of a person's running session. The human can retain that session, let the lead observe it, or authorize a separate managed attempt.

An authenticated human confirms the preview through the UI or a human CLI control path. The resulting adoption operation records its input revision and idempotency key. A worker cannot gain authority by calling the same endpoint with `--from` set to a human session.

### Delegate with a complete brief

```bash
# Proposed: the task and accepted criteria already exist.
cast task start ct-4102 --spawn --reports-to ro-4 --request-id launch-4102-a
```

The server resolves the project, plan, owner and role from the task. The flag verifies the caller's intended coordinator; it cannot move work into a different scope. The response distinguishes admission, process start and completion:

```json
{
  "operation_id": "launch-4102-a",
  "task": "ct-4102",
  "attempt": "attempt-3",
  "role": "ro-4",
  "state": "accepted",
  "execution": "queued",
  "controls": {
    "launch_limit": "enforced",
    "money_limit": "estimated"
  }
}
```

An accepted launch is not proof that a process started. Repeating the request returns the same operation. A daemon reports the launch receipt, and the task then shows its running session. When the outcome is unknown, the system reconciles that operation before issuing another start.

Return actionable refusals. For example: “The project has two active permits and a limit of two. Nothing started. Wait for an attempt to finish or ask the owner to change the limit.” The structured result names the limiting scope, dimension, current reservations and retry condition. A retryable device outage differs from a policy rejection; neither should produce an invisible extra worker.

The task brief includes:

| Field | What the worker receives |
|---|---|
| Intended outcome | The user problem and accepted success criteria |
| Work boundary | Task, plan, project, allowed resources and excluded effects |
| Responsibility | Human owner, coordinating role and reviewer |
| Evidence | Relevant source links, checked revisions and known gaps |
| Attempt | Current claim, generation, lease and operation IDs |
| Execution | Runtime capabilities, permitted tools and reserved allowance |
| Reporting | When to checkpoint, which outcomes require a question, how to submit results |

A prompt should contain the minimum evidence needed for this task. The worker can request more through an authorized retrieval path. Copying an entire manager transcript into every child wastes context and may expose unrelated work.

### Ask, recommend and approve

```bash
# Proposed: ordinary implementation question within approved criteria.
cast decide --class approach "Use the existing ledger or recompute totals?" \
  -o "Existing ledger :: use the audited calculation" \
  -o "Recompute :: add a second calculation and comparison tests" \
  --context -

# Proposed: a lead resolves a question it is authorized to answer.
cast decide answer sd-29 1 --why "The accepted criteria require parity with the ledger."

# Proposed: preserve the same decision and add a recommendation.
cast decide escalate sd-29 --recommend 1 --why "Changing the accounting rule exceeds this task."
```

The asker may request direct human review. The lead can narrow or escalate a request, but cannot turn a protected effect into an ordinary question. An unknown class stays with the authorized human until classified.

Decision answer and action approval are separate. “Choose the existing ledger” permits work within the current task. “Delete the legacy column” needs approval bound to that exact change and target. The UI should display that distinction without asking people to understand internal permission tokens.

If the question changes, increment its revision and invalidate an answer that referred to the previous effect. If the human overrides a completed action, pause affected future work and show what already happened. The agent proposes a repair; it does not reverse a production change merely because a later message disagreed.

### Report evidence, then stop

```bash
# Existing basic form; proposed managed mode adds evidence metadata.
cast task comment ct-4102 "Reproduced duplicate delivery with two concurrent events."
cast state --status working "Fix implemented; running the duplicate-event regression."

# Proposed evidence submission.
cast task submit ct-4102 --attempt attempt-3 --revision abc123 --evidence report.json
```

`submit` is proposed as the explicit agent verb. Existing `cast task done` remains compatible for manual work. In a managed attempt it either maps to submission with a clear response or refuses missing evidence; the CLI must never print “completed” when it only moved the task into review.

```json
{
  "task": "ct-4102",
  "attempt": "attempt-3",
  "revision": "abc123",
  "criteria": [
    {
      "criterion": "One notification for concurrent duplicate events",
      "evidence": "artifact:duplicate-event-test",
      "result": "passed",
      "checked_at": "2026-09-04T17:30:00Z"
    }
  ],
  "not_verified": ["Production delivery"],
  "remaining_concerns": []
}
```

The task enters `in_review`. The reviewer checks the submitted revision, acceptance criteria and limits of the evidence. A later code change invalidates approval of the previous revision. Verification can finish while production deployment still awaits authorization.

### Short role briefs

Generate the structural part of a brief from the same versioned policy the server enforces. Store editable behavioral guidance in an existing document. Show both versions on the role page; a prose edit cannot grant additional permissions.

**Workspace lead**

> Help the responsible humans understand commitments across projects. Read current project outcomes, open decisions and coverage before reporting. Resolve coordination questions within your approved scope. Identify conflicts between projects and recommend an owner or priority change. Keep project leads small in number. Propose an additional lead only when measured coordination work justifies it. Do not create new authority through a chat reply. Route protected actions to an authorized human immediately; attach a recommendation when you have useful evidence.

**Project lead**

> Coordinate this project's approved work. Preserve its human owner and existing task assignments. Keep the current outcome, evidence, blocker and next action visible. Start a worker only after a valid claim and admission permit. Resolve routine choices within accepted criteria. Submit a question when the work changes scope, resources, external commitments or user experience beyond those criteria. Verify results before closing work. If a worker is quiet, inspect its durable state before retrying. Report uncertainty and missing evidence as such.

**Plan lead**

> Run this plan's approved dependency graph. Read the plan context and current task claims before each wave. Start only tasks whose dependencies are satisfied and whose resources fit. Delegate implementation and review with bounded attempts. Wait for evidence at the revision being reviewed. Escalate repeated failures with the approaches already tried and a recommendation. Keep recovery information in task comments, plan entries and execution records. A replacement session must be able to continue without guessing what your last message meant.

**Worker**

> Work on this attempt's task and accepted criteria. Make ordinary reversible implementation choices within that boundary. Your tools and resources remain limited by the runtime's permissions. Checkpoint useful progress and preserve unmerged work. Ask your lead when evidence is missing or the proposed approach changes scope. Protected effects require approval of the exact action. Submit the result with the revision, tests, artifacts and unverified areas. After submission, wait for review or end the attempt; do not start unrelated work.

These prompts guide behavior; tests must verify that the server and runtime enforce the corresponding contracts. A prompt that says “do not deploy” cannot remove deployment credentials from an unrestricted shell.

### A lead's working loop

The lead first consumes pending role events and obtains a digest at a named watermark. It reconciles active attempts before dispatching anything. It deals with human obligations and stale claims, then selects ready work using the existing plan dependency model. A cheap deterministic check should precede an expensive review call.

After a worker submits, the lead inspects the result or delegates an independent review. It records accepted evidence or a focused revision request. Retry budgets include all attempts, including sessions that crashed before reporting. Repeated failure becomes an escalation containing the diagnosis so far, useful partial work and the choice that needs a person.

The loop goes dormant when no action is available. Timers support deadlines and recovery; they should not produce periodic “still working” conversations. A new source event or human request wakes the role. The human can see which event caused the wake and what the lead did with it.

### Compatibility and structured output

Preserve current short IDs and command aliases. New JSON fields are additive until a managed capability requires a version upgrade. Publish an operation schema with stable result codes: `SCOPE_CONFLICT`, `CLAIM_HELD`, `STALE_GENERATION`, `APPROVAL_REQUIRED`, `BUDGET_EXHAUSTED`, `UNSUPPORTED_ADAPTER`, `OUTCOME_UNCERTAIN` and `ACCESS_REVOKED`.

Each response distinguishes a policy refusal from an infrastructure failure. Include a safe recovery action, not just an error string. Machine output carries IDs and revisions; human output names the task, responsible lead and next actor. Never silently ignore an unsupported safety flag, even if a generic harness wrapper historically did so for optional model settings.
