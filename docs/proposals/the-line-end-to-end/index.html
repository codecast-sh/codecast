Every change.
One line.

A signal from the world becomes a cause, a cause becomes one change with red then green proof, and you answer one question about it. Code changes, prompt changes and escalations all ride the same fifteen stations, the same card and the same gate. Click any station.

Code decides what code can check. A model is asked only what needs judgment, one decision per call.

1

sense

LE3 · signals.ingest · cast signal add

Anything that watches the world writes what it saw through one door, and types it itself.

finder: a trigger or cron

Reads

The world: Sentry error groups, PostHog funnels, the eval nightly, AgentWatch judges, session insights, cast-lessons, org health, synced issues, or a person typing cast signal add.

Decides

The finder picks the kind (bug, regression, prompt_miss, ux, cohesion, request) and computes a fingerprint: error group, eval surface and check, cluster id.

Nothing classifies free text afterwards.

Writes

One signals row: source, kind, fingerprint, title, bounded detail, evidence link, optional subject and goal hint.

Not a node on the line. The line starts at attach.some finders use a model (AgentWatch judges); the door is code

attach

LE4 · one cause per problem

Every signal lands on exactly one cause, and the record says how it got there.

code firstone small call as fallback

Reads

The new signal. Open causes holding the same fingerprint. Failing that, the five closest open causes by title and subject.

Decides

  1. Fingerprint match takes it. Deterministic.
  2. Otherwise one call: "same cause as one of these, or none?" unsure counts as none.
  3. Otherwise a new cause, triaged as suggested.

Writes

signal.task_id and attach: fingerprint, judge, new or person. On the cause: signal count, first and last seen, fingerprints.

A cause in watch that gets a signal reopens.

One cause has at most one live run. Siblings are visible to it.LE1.4

ground

LE5 · cast goals --brief

Every cause names the goal it threatens, or it never reaches you.

one model callpriority is computed

Reads

The workspace's goals as one compact brief: initiatives with metric targets and the latest scoreboard, each project's charter, the product principles. Plus the cause and its signals.

Decides

  • goal_ref: the metric or goal it threatens, or none
  • category: code, prompt, ux, infra, data
  • risk: low, review, plan
  • readiness, with one line why

Writes

The four fields on the cause. Priority = goal priority × severity × signal count, in lib/linePriority.ts. Never judged.

A cause grounded to none parks until its signal count crosses the threshold.

Risk plan (schema, billing, cross cutting design) routes the run through the plan gate.LE5

admit

LE6 · orgLine.sweep

Work starts at the rate you finish decisions. You are the drum.

code

Reads

Your open card decisions on this line, the hands used today, and waiting causes ordered by priority.

Decides

Starts the next cause only while both hold:

  • open cards < caps.cards (5)
  • hands today < caps.hands_per_day

Writes

A run on the cause. A cause that waits shows queued behind 5 open cards on the line page.

Answering a card frees a slot and the next cause starts.

More agent throughput than your answer rate only adds waiting and rubber stamping.LE1.3

plan gate

LE7 · only when risk = plan

Architecture and anything protected stops for your yes before a line of code exists.

agent writes the planyou answer

Reads

The grounded cause and its signals.

Decides

An agent writes a short plan: the approach, the files, what will be proven red, the size budget. You answer Approve, Revise with a note, or Drop.

Writes

The plan on the task. Scope freezes at the gate. New information during build sends the run back here instead of steering build.

prove

LE8 · proof before the fix

Before any fix, the run shows the miss. No red, no build.

agentcode checks it failed

Reads

The cause's signals and the real moments behind them.

Decides

Code, ux, infra: a failing test or repro script on the branch.

Prompt: freezes with one judge sentence each; ./evals check on the base must fail them.

Writes

The failing output, or the before set of failing replies.

Cannot reproduce? The cause closes as dissolved with the evidence. That counts as a success.

If the freezes pass on the base, the bug is not in this prompt.P9.2

build

LE8 · one change, in a worktree

One change, sized to be read. Prompts follow the prompting standard.

agent

Reads

The cause, the plan if there was one, the red proof, and docs/prompting.md for prompt changes.

Decides

The fix. For a prompt, the rewrite sits at the instruction that caused the miss, never a filter around it.

Writes

A branch in its own worktree, inside 400 changed lines. More than that splits, or returns to plan.

A Revise answer on the card lands here with your note.LE11

verify

LE8 · cheapest first

The repository's own checks, then the tests that matter.

code

Reads

The worktree.

Decides

Pass or fail: cast ws check, then targeted tests.

Writes

Check results as evidence on the task. Two failed rounds stop the run with a decision to the owner.

No model reads a typecheck.LE1.1

eval

LE8 · ./evals stale + ./evals check

Every prompt surface the branch touches is replayed, five reps, against the base.

code

Reads

./evals stale --base main names the surfaces the diff reaches; each runs ./evals check <surface> --reps 5.

Decides

Passes only when the proven freezes now pass, no gate fails in any rep, and no surface is separated: worse.

Writes

The after set and the flipped examples: before reply, after reply, judge note.

"Looks better on two draws" is not evidence.P9

review

LE9 · the diff against the intent

A fresh session on a different model family from the builder.

model, other family

Reads

Only the task, the card draft and the diff. Never the builder's reasoning.

Decides

  1. Does it do what the cause needs?
  2. Does it do anything else?
  3. Does it reuse what exists?
  4. Does it follow CLAUDE.md?

Writes

Four pass or fail lines, each with a reason. One fail is changes.

Smaller context is cheaper, faster and harder to fool.P7

assembled by codethree fields by one call

The ChangeCard, rendered once as the page on the task and inline in the decision. See the mock below.

The only place the back half asks you anything.

you

Decides

LE12 · cast line merge

The approved branch.

LE12 · tasks.watch_until

Seven days of listening for the same problem.

code

Reads

Incoming signals, matched by the cause's fingerprints, for watch_days (default 7).

Decides

A matching fingerprint reopens the cause with the signal attached. A quiet week closes it.

9

Rules the whole line keeps

Nothing here adds a third engine, a second decision rail or a second evidence model. Every station is a node in the DOT engine, every question is a decision row, every artifact attaches to the task.

LE1
1Code decides what code can checkGit, checks, eval verdicts, dedupe, admission, routing. A model gets only judgment, one decision per call.
2Atomic nodesOne thing, a declared input, a declared output, replayable alone. A prompt making two decisions is two nodes.
3The person is the drumWork is admitted at the rate decisions are answered.
4One cause, one runSignals attach to a cause. A cause has at most one live run, with its siblings in view.
5Proof before the fixStart by showing the miss. End by showing the same check passing, with examples.
6One card shapeCode, prompt, UX and escalations all end in the same card. The PR is evidence.
7A click is a wireAnswering a gate resumes the run that asked. No decision travels as text.
8Fix behavior in the promptRewrite the instruction that causes the miss, prove it with evals. Never a filter.
9Every stage shows its statePaused, starved or failing, and since when, on the line page.

Who wrote what

Only the three fields tagged model are written by a model, in one call that reads everything else.

Cause, goal, proof dots, examples, checks, diff, risk and cost are assembled by code from what the stations recorded. Nothing on the card is a summary of a summary.

Red, then green

Each square is one replay. The same seven freezes run on the base and on the branch: four real misses and three guards that already behaved.

A win needs separated: better: an exact one sided Mann-Whitney at p ≤ 0.05, five reps a side. With five fails against five passes the smallest possible p is 1 in 252.

Same card for everything

A Sentry crash shows a failing test as red and the passing test as green. A UX fix shows a screenshot pair. An escalation shows the ask and the options. The shape never changes, so you learn to read it once.

6

The prompting standard

Every prompt the product ships, and every prompt a station runs, follows it. A prompt change is a behavior change and ships like code: proven broken, rewritten, proven fixed.

docs/prompting.md · P1 to P10
P1Intent, not a script

Name the reader's job and who it serves before any rule. Give the reason with the rule. Describe the quality of the output, never its words.

Escalate to a directive only when a measured run shows the principle failing.
P2One prompt, one decision

Score, extract and classify in one call is three prompts. A JSON call states its schema once, with each field's meaning and its value when unsure.

Each call can then be evaluated and improved alone.
P3Examples last

Examples anchor. Use one only when a principle cannot carry the behavior, keep it far from likely inputs, prefer a contrast.

Never paste a production failure in as a "don't".
P4Write it clean

A revised prompt reads as if it always said this. No "no longer", no removed rules, no changelog.

History lives in git and the eval run sets.
P5Fix it where it is caused

A bad output means an instruction causes it or none covers it. Rewrite that instruction at its own site. Never add around a model call:

  • a guard or post-hoc filter
  • a retry loop hoping for a better draw
  • a second model call that checks the first
The one exception: conditional context injection, after a rewrite was tried and measured.
P6Facts, not adjectives

Who, what state, which numbers, what was done, in a stable labeled block apart from instructions.

Untrusted text is fenced and named as data. It never carries authority.
P7Scope what it sees

A reviewer sees task, criteria and diff. A judge sees the reply and the expected behavior, not the prompt.

Smaller context: cheaper, faster, harder to fool.
P8Shared text has one home

A policy, vocabulary or lifecycle that two prompts need lives in one partial both render. A lifecycle described in a prompt and again in a UI string will drift: render both from the same source.

P9Prove it

The eval protocol below. Claims of improvement need separated: better, an exact one sided Mann-Whitney at p ≤ 0.05 with five or more reps a side.

"Looks better on two draws" is not evidence.
1Freeze the missReal failing moments become freezes, each with one judge sentence. Add two or three moments that already work as guards.
2Show it redFive reps each on the current prompt. Misses must fail. If they pass, the bug is not in this prompt: stop.
3Rewrite at the siteAt the instruction that caused it (P5), clean (P4).
4Show it greenSame freezes, five reps. Misses pass, guards pass, no gate fails, no surface separated worse.
5Show the differenceThe card carries at most three before and after pairs, with the judge's note.

P10 · the reviewer's seven questions

Pass or fail, one line each. One fail sends the change back.

  1. Does the rewrite sit at the instruction that caused the miss?P5
  2. Does it state intent and reason before rules?P1
  3. Does each call still make one decision?P2
  4. Are new examples justified and non-anchoring?P3
  5. Does it read clean, with no history?P4
  6. Is shared text rendered from its one home?P8
  7. Red, then green, on the same freezes, with guards?P9
