One line

A task moves along its scope's line through stations. Every human gate is a decision in the queue. Evidence attaches where it was made. Chains are runs. One model, read by every page and every command.

The strip on every task page. Stations are the team's statuses, the six defaults here. The line under a station is the run's node there. The red chip is an open blocking decision.

Codecast has every part of an automated factory and none of the joints. This proposal adds no new part. It joins the parts that exist with nine words, one ask rail, and one place for evidence.

Sessions do the work. Tasks hold it. Decisions ask a person. Published pages carry evidence. DOT workflows route a task from node to node. Chains run agent definitions in order. Org roles own scopes and stand by as agents. Each part is built and tested. Each one also has its own rail, so they cannot see each other. A workflow gate never reaches the queue. A decision names a station but nothing holds the task there. A chain leaves no run behind. A page belongs to a session and to nothing else.

The fix is a contract, not a feature. A scope owns a line. A task moves along it through stations, which are its statuses. A run is one passage. A gate on the line is a decision in a person's queue, inside a stack when the graph declares one. A blocking decision holds its task. Evidence attaches to the task at the station that produced it. A chain run is a run. The sweep starts the line for tasks assigned to a role.

What changes for the person. One queue answers every question a machine has for them, including the ones a workflow used to hide in a run panel. One task page shows where the work is, who holds it there, and what it produced. One scope page shows the whole line as columns. A teammate who can read the task can read its run. The person's day is the queue, the task page, and nothing else.

1Why now: the seams

Every seam below is a real gap between two shipped parts. Each one costs a person a page they did not need to open, or hides a fact they needed. Together they are why a workflow with a human gate still feels like a script and not like a colleague.

Two ask rails

A workflow gate pauses the run and polls its own gate_response. It never becomes a decision. The queue, stacks, the ladder and roles cannot see it.

fix: a gate is a decision (L4)
Station stored, not enforced

cast decide --station is stored and shown. Nothing keeps the task at that station. The rule lives in prose.

fix: a blocking decision holds its task (L5)
Chains leave no record

cast exec --chain runs headless. No run row, no task comment, nothing on the scope page. Parallel -j runs likewise.

fix: chains are runs (L7)
Pages float free

A published page belongs to a session. A task, a station or a decision option cannot own one. The design comparison, where a page matters most, has no home.

fix: evidence attaches at the station (L6)
Web runs lose node attributes

A run started from the web drops definition, reviewer and timeout. The line's independent review quietly becomes the role's own session.

fix: node fidelity (L8)
Nothing starts the line

A role's charter says "run the line". No code does. A task assigned to a role waits for a person to type the command.

fix: the sweep (L9)
Runs private to one user

A teammate who can read a task cannot see its run. The run panel is empty for everyone but the starter.

fix: runs belong to the workspace (L8)
Two workflow pages

/workflows and /routines are two pages under two names in two menus for one idea.

fix: one entry, a Runs tab (L10)

None of these needs a new concept. Each one is a missing pointer between two rows that already exist, and one rule that says which row reads it.

2The model in nine words

Nine words, each with one meaning and one table behind it. Nothing else is coined. This is L1 of the contract, and every section after it uses only these words.

WordMeaningTable
scopewhat a role owns: projects and plansorg_roles.scope
linethe workflow a scope's tasks run on; one per scope; shipped line by defaultorg_roles.line_workflow_slug, workflows
stationa task status. The team's statuses, in order, are the stationstasks.status / status_id
runone task's passage along a lineworkflow_runs
gatea workflow node where a person decides. A gate IS a decisionsession_decisions with workflow_run_id
holda pending blocking decision bound to a task keeps it at its stationsession_decisions.task_id + station
evidencewhat a station produced: pages, images, docs, files, a PR, verification textartifacts.task_id, tasks.*
stacka person's ordered set of decisionsdecision_stacks
handa session a run or a role starts for bounded workconversations.org_role_id

Two words deserve a note. A station is not a new state. The run moves the task through its statuses exactly as a hand would with cast task handoff and cast task verdict. And a gate is not a new kind of ask. It is a session_decisions row like every other, with two extra fields that name the run and the node.

The shipped line has four working nodes: analyze, implement (in a worktree, three visits at most), verify (the repo's check), and review (an independent session that sees only the branch, the title and the criteria). Edges route on the task's own fields, refreshed after every node: handoff, outcome, review_verdict.

// packages/cli/src/workflow/templates/line.cast (edges)
start -> analyze
analyze -> implement
implement -> verify   [condition="handoff = done"]
verify -> review      [condition="outcome = success"]
verify -> implement   [condition="outcome = failure"]
review -> exit        [condition="review_verdict = approve"]
review -> implement   [condition="review_verdict = changes"]
review -> exit        [condition="review_verdict = reject"]

3A day on the line

A scenario is the honest test. This one assumes all three waves have shipped. The scope is the Product project. Its role is @product, trust direct, six hands a day. Its line, slug design, is a copy of the shipped line with two gates added. approve sits after analyze, with edges [A] Go and [B] Rework. pick sits after verify and before review, with edges [A] Left rail to review and [B] Top bar back to implement. The graph carries stack="Empty state". Ashot is the person.

08:51A person assigns a task

Ashot files ct-50210, "Empty state for the decision queue", and assigns it to agent:product. Nothing else happens. The task sits at open with no run.

08:52The sweep starts the line

orgLine.sweep runs every two minutes. It finds one task in the role's scope assigned to the role, at open, not blocked, with no run, and the role has used two of six hands today. It creates a run as the role's host user with the role's project path, spawner the role's standing session, and a run_workflow command for the host's daemon. It bumps the hand counter and comments once on the task. If the sweep runs again before the daemon picks it up, nothing happens: a task with a run is never started twice.

08:53Analyze

The analyze hand reads the task and the code it touches and writes five steps a reviewer can check. The task page shows the strip with open lit, and under it "analyze · hand jx7c6zk · 2 min". The run reaches approve, its first gate. The stack "Empty state" is created and the gate sd-380, "Criteria as written?", is its first member. Ashot answers A from the laptop a minute later and the run goes on.

09:01Implement, in a worktree

The implement hand starts in worktree line-ct-50210 on its own branch. Node start moves the task to in progress. The hand builds two candidate layouts behind a flag, publishes each as a page with cast publish --task ct-50210, and both pages attach to the task at in progress. It commits, pushes, and ends with a handoff: status done, the evidence text naming both pages, and the files. The handoff posts a review comment and moves the task to in review.

09:24Verify

Verify runs cast ws check in the worktree: success. The edge out of verify leads to the second gate, not to review. Ashot picks the layout before an independent reviewer spends a session on it.

09:41A gate lands in the queue

The run reaches pick. pauseAtGate asks through askCore as the role's standing session: task ct-50210, station in review, options A and B from the edges, the prompt as context, doc="$implement.output" as the body, blocking. The body is the handoff evidence, so it names both pages. This is the run's second gate, so it joins the stack "Empty state" as sd-402. The run stores the decision id and pauses. Ashot's queue shows the stack, one answered and one open, with a run chip on the open card. The task is now held at in review: a chip on the strip links to sd-402.

09:58The person answers from the phone

Ashot opens the queue in the phone browser. The stack header says one of two answered. The card shows the question, the run chip "design · pick", the body with both page links, and a link to the task. On the task page the Evidence section shows the two pages side by side as thumbnails under in progress. Ashot opens each, goes back, and picks A. finalizeAnswer sees workflow_run_id on the row, writes gate_response = "A", and sets the run back to running. The run consumes the answer; no message goes to the asking session.

09:59The run resumes, the hold releases

The runner's poll reads the response and follows edge A to review. The decision is no longer pending, so nothing holds the task. Both members are answered, so the stack is done. The role's standing session receives the answer as a passive fact on its next wake.

10:10Review

Review starts a fresh session with the branch, the title and the five steps, and nothing else. It checks each step against the diff and ends with cast task verdict ct-50210 approve. Approve closes the task: it moves to done, and the run exits. The reviewer is a session outside the role, so the independent review rule is met.

10:12Evidence on the task, a column move on the scope

The task page's Evidence section lists, by station: two pages at in progress with thumbnails, the files changed and the verification text from the handoff, the PR, and the approve verdict at in review. On the scope page's Line tab the card slides from the in review column to done. The scope feed shows one run row: design, 80 minutes, two gates. The role's brief counts one hand and two decisions answered today.

Count the person's touches: one assignment, two answers, one of them from the phone. Everything else is on the record with the run's id on it, readable by any teammate who can read the task.

4Surfaces

Five pages and the CLI read the model. None of them stores anything the others cannot see. Every held marker, run chip and evidence count is derived from the same rows: the task's decisions by by_task, its runs by by_task, its artifacts by by_task.

4.6 The CLI

The same model from the terminal. cast task show prints decisions with id, status and station, runs with status, node and gate, and evidence. The rest are small verbs on rows that already exist.

# the line
cast workflow run --task ct-50210          # no file: the caller's role line, else `line`
cast role line @product --set design       # a scope edit: human only, logged, wakes the role
cast workflow runs --task ct-50210

# stations
cast task handoff ct-50210 --status done --evidence - --files a,b --pr <url> --page <slug|url>   # --page attaches a page published without --task
cast task verdict ct-50210 approve --note -
cast task show ct-50210                    # decisions, runs, evidence

# evidence
cast publish two.html --task ct-50210      # attaches at the task's current station
cast decide "Which layout?" -o "Left rail :: keep the filter rail" -o "Top bar :: one column" --option-page 1=rail.html --option-page 2=bar.html

# stacks and the queue
cast stack policy ds-17 --due "tomorrow 9am"
cast stack reorder ds-17 sd-402,sd-380
cast stack remove ds-17 sd-380
cast decide ls --mine
cast decide edit sd-402 --category review   # every ask field

# chains
cast exec --chain triage --plan pl-531     # records a run: chain-triage, one box node per step
cast org feed                              # prints run rows

5Mechanics

5.1 Gate to decision to hold to release

1The run reaches a hexagon

The runner calls pauseAtGate with the node id, the prompt, the choices from the edges, the doc body, the category and the graph's stack name.

2The asker is chosen

The session that started the run, or the role's standing session, so the ladder and grants apply. Else the run's primary session.

3askCore inserts one row

Task and station from the bound task, options from the choices, context from the prompt, blocking, with workflow_run_id and gate_node_id. The run stores the decision id and pauses.

4The task is held

A pending blocking row with the task's current status holds it. A session that tries to move the status is refused with the decision's id. A person on the web may move it; a note comment names what they moved past.

5Any path answers

The queue, the page, the card, cast decide answer, a role under a grant, a stack policy. All end in finalizeAnswer, which writes gate_response and sets the run running. The run consumes the answer; the asker is not messaged.

6Release

The row is no longer pending, so nothing holds the task. The runner's poll reads the response as before and follows the chosen edge. Nothing was written to the task for the hold.

Free text still works. The run panel's respondToGate answers the same decision: a message that starts with a key picks that option; anything else is answer_text and routes the run on its unconditional edge. Withdraw goes both ways through settleResolution: cancelling the run withdraws its open gate; withdrawing a gate fails the run with the reason "gate withdrawn". Ladder roles receive either as a passive fact. The runner's existing decisions for a reject verdict and for exhausted retries carry workflow_run_id too, so the run panel and the task page show them as the run's decisions.

5.2 Evidence binding

Evidence is never copied. It is a pointer on the row that already carries the thing, and one query that gathers the pointers.

  • cast publish --task ct-N and --plan pl-N set the task, plan and station on the artifact. Without a flag, a publish from a session bound to a task attaches to that task at its current status.
  • cast task handoff --page <slug|url> attaches an existing page: it patches task_id and station.
  • A decision option may carry a page in options[i].page_slug. cast decide --option-page n=file.html publishes the file through the same path --report uses and sets it.
  • Images from cast image have no row. They attach through the message that carries them: a bound session's images are the task's images.
  • tasks.evidence({ task_id }) returns one object: pages by station with thumbnail urls, docs with the task in task_ids, images from bound sessions, files changed, verification text, the PR, and the review verdict. The task page and cast task show render it.

5.3 The sweep and caps

orgLine.sweep runs every two minutes. For each active role with trust direct it reads the tasks in the role's scope that are assigned to agent:<handle>, at status open, not blocked, and without a run. Each one gets a run while counters.hands is below caps.hands_per_day. The run is created as the role's host user with the role's project path; the spawner is the role's standing session; a daemon_commands row of kind run_workflow reaches the host's daemon. The sweep bumps the hand counter, comments once on the task, and skips paused roles. When the host has never pushed the line's slug, the run carries the slug as its workflow name and the daemon resolves the graph from the shipped template, as cast workflow run <name> does. The run's primary session is a hand of the role, and it is the one that counts against the daily cap.

The sweep is idempotent because the task row is the record: a task with a workflow_run_id is never started twice. A role at understand or decide trust starts nothing; a person types the command. Hands the run starts are unattended principals: reversible actions run, and anything in a protected category goes through cast decide, which pins the holder to a person. A stalled hand is killed by the runner's timeout and the task returns to open with a comment. Two implement cycles, then the task goes to in review blocked with a decision to the person.

5.4 Chain compile

A chain is definitions in order; each step's output feeds the next prompt. cast exec --chain <name> and cast agent run <name> compile it into a linear workflow with slug chain-<name>: one box node per step carrying the step's prompt template and definition= the step's agent. The CLI upserts it, creates a run with createFromCli bound to the task or plan when given and with the current session as spawner, reports each step with updateProgress using the output's head as the preview, and completes or fails the run. cast exec -j N records one run with a component fanout node and one node per input. Output still prints to stdout and to --json. The run therefore shows on /routines, on the task page and in the scope feed like any other.

6Data model

Every field below is in the schema today. No table is added. Each field is a pointer between two rows that exist, or a copy of an attribute a run used to lose.

session_decisions

options[i].page_slug? string a published page for this option (L6)
workflow_run_id? Id<workflow_runs> the run this gate belongs to (L4)
gate_node_id? string the hexagon node in that run (L4)

workflow_runs

gate_decision_id? Id<session_decisions> the open gate; gate_prompt and gate_choices stay as a mirror (L4)
gate_node_id? string
workspace string the ACCESS key, from computeWorkspaceKey at create, createFromCli, ingestSnapshot (L8)
team_id? Id<teams> routing only (L8)
indexes by_workspace_updated, by_task, by_plan

artifacts

task_id? Id<tasks> the task this page is evidence for (L6)
plan_id? Id<plans>
station? string the task's status when it attached
indexes by_task, by_plan

workflows.nodes[]

definition? reviewer? timeout? temperature? persisted, so a stored graph runs as a local one (L8)
doc? category? gate attributes: the decision body and its proposed category (L4)

decision_stacks

policy.due_at? number cast stack policy --due; the queue shows it and sorts overdue first (L10)

org_roles

line_workflow_slug? string default "line"; a path, the caller's workflow by slug, or a shipped template (L2)

Two things are deliberately not stored. A hold is derived from the open decisions by task, so it can never go stale. A station is the task's status, so a run adds no state to a task and the board keeps one source of truth.

7Guardrails

The contract prevents a short list of things. Everything else it makes visible and leaves to a person. The split matters: a refusal costs a round trip, so it is spent only where the alternative is a silent wrong state.

Prevented

  • A session moving a held task's status. The error names the decision and the command that answers it.
  • A role's session closing its own task without an approve verdict from a session outside the role.
  • A session changing a scope's line. The picker is human only, logged to role history, and wakes the role.
  • The sweep starting a task twice, or starting past the role's daily hand cap, or for a paused role.
  • A hand inside a run taking a protected action. Protected categories stay human held; cast decide pins the holder to a person.
  • A blocking stack member answering itself. Auto default applies to advisory members only.
  • A run asking a person by any rail but session_decisions.
  • A teammate reading a run on a task they cannot read. Access is the run's workspace key.

Visible, not prevented

  • A person on the web moving a held task. The decision stays open; a note comment names the decision they moved past.
  • A hand that stalls. The runner's timeout kills it; the task returns to open with a comment.
  • A third implement cycle. The task goes to in review blocked, with a decision to the person.
  • A withdrawn gate. The run fails with "gate withdrawn"; ladder roles receive the fact.
  • A page published with no task flag from an unbound session. It stays a session's page and attaches to nothing.
  • An image with no artifact row. It is the task's image only while the session that carries it is bound.
  • A stack past its due time. It sorts first and the header says overdue.

8Rollout

Three waves. Wave 1 is server and CLI, in parallel slices that touch separate files. Wave 2 is the web. Wave 3 is what makes it feel finished. Convex deploys before the web push in every wave, so the live site never asks for a function that is not there.

Wave 1 · Server and CLIparallel slices

The contract rewritten clean. Gates are decisions: pauseAtGate creates the row, finalizeAnswer releases the run. Station holding and decision hygiene: the hold rule in the two status mutations, cast decide edit with every field, withdraw through settleResolution, cast stack remove and reorder. Workflow fidelity and team visibility: nodes keep their attributes, runs carry workspace and team, one runs list. Chains are runs. Evidence attaches: the artifact fields, --task and --option-page, tasks.evidence. Scopes own the line and start it: line_workflow_slug, cast role line, the sweep.

Accept when: a gate in a run appears in the queue, is answered there, and the run resumes; a hand that tries to move a held task is refused by name; a chain run appears in cast workflow runs; a page published from a bound session shows in cast task show at the right station; a task assigned to a direct role gets a run within two minutes and never a second one.

Wave 2 · Webthree surfaces

The task page as the line: the strip, the held marker, decision cards, evidence by station, the run panel reading the decision card. Decisions with option pages, gate cards and stacks: the comparison row, the run chip, due on the header, overdue first. The scope Line tab, the Routines Runs tab, one Workflows entry with a Dynamic tab.

Accept when: the day in section 3 runs end to end from the phone browser at 390 pixels and from a laptop at 1280 pixels, and every held marker, chip and thumbnail on the page is derived from the rows, with no field written for display.

Wave 3 · Polishuntil it disappears

cast task show and cast org feed print the same model. This page. A review wave over every slice. Polish rounds with browser verification and a Convex deploy.

Accept when: a teammate who was not on the project reads a task page and can say where the work is, who holds it, and what it produced, without opening the run or the transcript.

9What we do not build

  • A mobile queue and a mobile task line this round. The web queue and the task page read well in a phone browser, and that is what the scenario uses. Native surfaces come in a later plan.
  • Dollars. Tokens stay the unit on the role page and in the brief. A price table is a later layer on the same counters.
  • Roles for labels or paths. A scope is projects and plans. A label is personal filing and a path is a machine detail.
  • A second ask rail. No run, chain or role asks a person by any path but a decision row. The run panel's free text answers the same row.
  • New task states. Stations are statuses. A run never adds a state the board cannot show.
  • A stored hold. "Held" is derived from open decisions by task. A stored flag would be a second source of truth that could go stale.
  • Pages on gate edges. A gate's options come from its edges and carry no page in this round. Option pages ride decisions asked with cast decide; a gate's pages are the station's evidence.
  • Peer negotiation between hands. Conflicts go up the ladder to the role and, when protected, to a person.
