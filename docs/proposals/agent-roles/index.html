An organization
of agents

Hung on the work you already track. Layered agent roles that each own a project or a plan, wake on what changes inside it, and report upward as facts plus a short narrative. You read the company at whatever altitude you want, and answer only what nobody below you was allowed to decide.

codecast product proposaldraft three, twice reviewed2026-09-05grounded in anchors, spawn, session_decisions, tasks, plans, projects, chat wakes, pending messages, change log
Codecast already has every part of an organization except the middle. The org chart is not a new tree. It is the project and plan tree with roles hung on its nodes, so it can never drift from the work.

Sessions do the work. Tasks, plans and projects hold the work. Chat and the decision queue carry the conversation. One anchor stands by. What is missing is a layer of standing agents between the human and the sessions. Each one is a role over a project or a plan, with a charter, a scope, an authority list, a budget and a memory. A role wakes when its scope changes, delegates to hands, answers what its authority allows, and escalates the rest with a recommendation. It keeps a brief the layer above can read in ten seconds.

This proposal covers the product end to end: the concepts, how they map onto what codecast does today, every surface they touch, the mechanics that make it cheap and trustworthy, the schema changes, the guardrails, and a four phase rollout with acceptance tests. It is written from first principles against the code. Two review rounds of six lenses each were folded in, and every claim about existing code below was checked against the file it names.

What makes this different from "spawn more agents". Three commitments. First, roles hang on the existing work graph, so scope is never a second configuration surface. Second, every rollup separates facts the system computed from narrative the agent wrote, and every narrative line links to evidence. Third, the brief is the role's memory and the session is disposable, so a role survives compaction, model swaps, usage limits and restarts without losing the plot.

01Why now: the human is the integrator

A codecast user runs many sessions a day. Each one is a peer: it files under a personal label, binds to one task or plan, talks to other sessions with cast send, and settles into an inbox bucket that answers one question, who acts next. The inbox is excellent at that question. It is silent on every other one: what is the state of the Infrastructure project, which of these eleven sessions are pulling in different directions, what did we decide yesterday about the sync layer, what does the whole thing cost.

Today the only node that holds the whole picture is the human. Every card must be read, every decision answered, every collision noticed by them. The product has already grown the instruments that hint at the fix:

  • a session's pinned state says what it is working on, and the settle classifier says whether it is done;
  • a project has an Updates tab that already anticipates an agent digest;
  • tasks have a human board and an internal board;
  • an anchor stands by as a persistent member with a bot identity and a reserved field for a daily session cap;
  • hands nest under the session that spawned them.

Each instrument works at one altitude. Nothing connects the altitudes.

The result is a familiar ceiling. Below about ten live sessions the human is a good manager. Above it they are a switchboard. The fix is not a better switchboard. It is the thing every organization invents when the founder can no longer hold everything: a layer whose job is to hold one part of it and to tell the founder only what the founder needs.

02The idea: an organization is a context hierarchy

Strip a company down and it is a device for managing context. The person at the top holds goals and a one line status per department. A department head holds their department's plan and a paragraph per project. A project lead holds the plan and knows every open thread. An engineer holds the diff. Each layer compresses what is below it and carries intent from above. Nobody reads everything, and the company still moves as one.

Agents need this more than people do, because an agent's context is a hard budget and it decays with every compaction. A standing agent that tries to hold a whole workspace in one transcript fails the same way a founder with forty reports fails. So the org is built as a context hierarchy first and a delegation hierarchy second.

Concretely:

  • A role owns a scope. A scope is a node in the work graph the product already has: the workspace, a project, or a plan. A role sees the facts of its scope, wakes on changes inside it, and files its writes there by default.
  • A role keeps a brief. One living document per role: goal, state, blockers, decisions, what happens next. The system computes the facts, the role writes the narrative. The layer above reads briefs, not transcripts.
  • Roles report up and delegate down. Down: start hands with task text, assign tasks to subordinate roles, append intent to their briefs. Up: a state line, a digest, and decisions that exceed the role's authority, each with a recommendation.
  • The human sits wherever they want. At the top by default. Or in a role's seat, when they want to lead a project themselves. The org does not care whether a seat is held by a person or an agent.

The payoff is a single new question the product can answer at any altitude: how is this going, and what do you need from me? Ask it of the workspace and the anchor answers in five lines. Ask it of a project and its lead answers with a brief. Ask it of a plan and you get the plan lead's view. Ask it of a session and you get today's inbox card. Same data, four altitudes, one gesture.

03Principles

1

The org is the work graph, not a second tree.

Roles hang on projects and plans. There is no separate org chart to keep in sync. Retire a project and its lead has nothing to hold; move a plan and its lead moves with it.

2

Facts computed, narrative written, every claim linked.

Task counts, hand states, open decisions, tokens spent and staleness are computed by the server and injected. The role adds judgment on top. A narrative line without a link to a task, a diff, a message or a decision does not count as a report.

3

The brief is the memory. Sessions are disposable.

A role must be restartable from its charter, its brief and its scope facts with nothing lost that matters. That is the test for what belongs in the brief, and it is what makes model swaps, limit parks and compaction survivable.

4

Sleep by default, wake on events, coalesce.

No standing meetings, no polling. A role goes dormant at the end of every turn and is woken by changes inside its scope. Events within a short window fold into one wake with a digest, by the rules in appendix A.3. A quiet scope costs nothing.

5

Advise first, decide within authority, escalate with a recommendation.

Every role has an explicit list of what it may decide alone, and that list starts empty. Anything outside it moves up the chain. Nothing reaches a person without the intermediate roles' recommendations attached and the chain visible.

6

One identity per role, billed to a host.

A role is a bot member of the team. Its comments, chat posts, task assignments and briefs carry its name, through one actor resolver on the server. The human host's account runs and pays for it, exactly as the anchor works today.

7

Blast radius is explicit and pausable.

Daily caps on hands, wakes and tokens per role, enforced from the first version. Role creation fenced to scope. A role can be paused with one gesture, and pause is a delivery gate, not a cosmetic hide.

8

Reuse the rails.

Wakes are pending messages. Hands are spawns. Reports are project updates and thread states. Escalations are session decisions. Charters and briefs are docs. Identity is the anchor's bot user. The org adds three tables and a handful of fields, not a new runtime.

06The shape of an org

Shapes are not prescribed. The rule is that a role's scope must sit inside its parent's scope. With three scope kinds that gives a depth of two roles below the root: a project lead under the anchor, a plan lead under a project lead. The cap rises when a new scope kind is added. Hands are leaves and do not count. Two shapes cover almost everyone.

Hands are listed inside the role that started them.

Shape one: a solo builder

The anchor, one lead per active project, hands. Three altitudes. The human talks to the anchor in the morning and to a lead when they want to go deep. This is the shape cast org init proposes by default: it reads the active projects and offers one lead each, with charters drafted from the project's description and its recent updates. A workspace with no projects yet is offered projects first, drawn from its plans and its top level tasks, because a lead needs something to hold.

Shape two: a small team

A team anchor, project leads, and plan leads under the busiest projects. A human product manager may hold a lead seat; the agent leads below them report to a person, and that person's queue is where their escalations land. Section 9.10 defines the seat. The chart shows a dashed node for it.

Boundaries the shapes respect

A workspace has one org. A personal workspace and a team workspace are separate trees with separate anchors, the same boundary tasks, plans and docs already draw. A role's access follows the anchor's rules: the host, the personal owner, or any member of the team can reach it, and only the host, the owner or a team admin can reshape it. A parent and a child role always share one workspace, and --reports-to resolves inside it, so the default parent is the anchor of the same workspace.

A task can sit in a plan and in a project, and the two columns are independent today. A scope event therefore fans out to the union: the lead of the task's plan, the lead of the task's project, and the lead of the plan's project. A project lead's facts are built from tasks by project; a plan lead's from tasks by plan. Task creation under a plan starts setting the plan's project when none is given, with a one time backfill, so the two views converge. A task with neither sits in the root scope and belongs to the anchor. A plan with no project sits under the anchor. A plan that is private to one person inside a team project gets no plan lead in the first version, because a team role could not read it.

Which anchor is the root of a row is read from the row's workspace key, never from its team routing, so a task routed to a team but private to its owner reaches the owner's anchor and nobody else's.

What is not a shape

Peers without a parent, roles scoped to a label, roles scoped to a repo path, roles that report to two parents. Each of these is a real request and each is explicitly deferred in section 13 so that the first version has one scope rule and one chain per decision.

17:30 · digests

Each lead's routine fires. It reads its brief and the day's facts, writes a digest to the project's Updates tab, and refreshes its brief. A posted digest is a scope event for the anchor, so the anchor's summary is one coalesced wake that fires when every lead has posted or at a deadline, whichever comes first. In that turn the anchor reads the full briefs with cast brief and posts a five line summary in the team channel with the day's tokens by role. Ashot reads one message.

Count the human's touches: one page read, one decision, one evening message. The org did the rest, and everything it did is on the record with the role's name on it.

The same day after phase 1 only

One lead exists, over Infrastructure. It holds no authority yet. Its brief's first line sits in the project header and on the overview page. Its evening digest lands in Updates. Every decision from its hands reaches Ashot's queue with the lead's recommendation attached. It starts hands only for tasks a person assigned to it, and never more than its cap. The human's touches are a page read, the queue, and one digest. That is already a shorter day, and it is what phase 1 must prove.

08Surfaces

The org touches nine surfaces. Each gets the smallest change that makes the org visible there, and each reuses the component that already renders the underlying object.

8.1 The org page and the altitude control

A new route, /org, is the flagship. It renders the work graph with roles on its nodes and an altitude control at the top. The control is the interaction the whole proposal exists to deliver.

  • Overview. One line per top level scope, the first line of that scope's brief, with the colored edge and the evidence links. Fits on a phone. It is a projection of briefs, not new machinery.
  • Roles. One brief per role: goal, state, blockers, decisions, next, hands. The chart is drawn at this altitude, as in section 6.
  • Sessions. Every session under every role, as the inbox renders cards, including the hidden subagents the inbox never shows. This is where a plan lead's whole orchestration run is visible.

The colored edge on a node is the subtree's rollup of who acts next, in the inbox's four colors, so the chart doubles as a heat map of attention. A node's actions: open the role, talk to it, pause it and everything under it, add a role beneath it. Adding a role is a two field form: pick a scope from the projects and plans under the parent, name it. Charter and brief are drafted for review. An empty org page offers to propose one.

The page also shows two totals that keep the org honest: tokens today by role, and wakes today by role, with a count of sessions whose tokens are not counted when a backend has no usage writer. A role that wakes fifty times a day is misconfigured, and the number is where the human sees it. A role whose frame truncates is flagged with a suggestion to split its scope.

8.2 The role page

A role's home, at /org/<handle>. From top to bottom:

  1. The brief. Facts on the left (computed, with an "as of" stamp and a count of scope events since), narrative on the right (the role's words, each line linked). The narrative is editable here by the parent role's host and by a seat holder. Stale briefs render greyed the way a stale thread state does.
  2. Talk to it. A composer that delivers into the standing session. The transcript is embedded below it using the existing conversation view, so the role page is also the session page.
  3. Hands. Session cards under the role, live, with the same gestures as the inbox.
  4. Decisions. Three lists: raised by this role, answered by this role on behalf of its hands, escalated upward. The middle list is the audit of delegated authority, and each row shows the category the hand proposed and the category the role confirmed.
  5. Routines and wakes. The triggers this role owns, with pause and run, and the wake log with causes and tokens.
  6. Channels. The chat channels and Slack channels bound to this role.
  7. Charter. The doc, editable inline by humans. A change is delivered to the role as a wake so it re-reads its instructions.
  8. Settings. Model and backend, host, seat holder, budget caps, authority list, restart, status.

8.3 The inbox

A role is hidden from the inbox unless it is hard blocked (a permission prompt, an unresolved API error, a dead or unresponsive agent) or pinned a blocked thread state. A decision it raised or escalated is not a reason to show the role: the decision surfaces once, in the Questions bucket, with its chain. Hands keep exactly the inbox shape they have today: a spawn is a card, a subagent is hidden, a teammate nests. The org page's sessions altitude is where every hand is visible regardless.

  • An Org section at the top of the sidebar lists roles that are hard blocked, in the same card shape, with the role identity in the chip. Empty when no role is stuck, which is the normal state.
  • The Questions bucket shows a decision's chain on the card, and a collapsed "with a lead" group for decisions a role is currently handling, so a person can pull one up early.

8.4 Projects, plans and tasks

Project page. The header gains the lead's chip and the first line of its brief, with a "talk to the lead" action that opens the role composer in a side panel. The Updates tab is where the lead posts digests, badged as digests as the tab already does. The Tasks tab gains a "delegated to" facet so the human can see which tasks a role has handed to hands or to subordinate roles.

Plan page. A plan with a lead shows the lead's chip and brief line in the plan header. The plan's timeline entries written by the lead carry its identity.

Tasks. A role assignee is stored as agent:<handle>, the non user assignee convention the resolver and the name renderer already pass through; --assignee @sync-lead resolves the handle and writes that. Assigning to a role is delegation: it emits a scope event and the role wakes with the task in its frame. Assigning a task to a role never puts it on the human board. A task a person filed stays there and shows the role as assignee. The change is one clause in the shared board predicate: an agent: assignee no longer counts as promotion. Web and mobile share the predicate, so one line changes both.

cast task ready reads the calling session. Inside a role (section 8.8 defines inside) it lists only ready tasks in the role's scope; a human shell sees the workspace, as today. -p, --plan or --all override the default, so a role that needs to look outside its scope asks for it explicitly and the wider read is visible in the transcript.

8.5 Chat

Every team role is a bot member with a handle. Mentioning it from a human line wakes it with the thread excerpt, exactly as the anchor wake works, and the same silence rules apply: a role posts once, in the place it belongs, and passes on lines not meant for it. A line typed by a session, including another role, never wakes anyone. That is the anchor's rule today and roles keep it; a role that needs another role uses cast send @handle or assigns a task. A role's own posts carry its identity through the actor resolver in section 9.5, so cast chat send from a role's session posts as the role.

Resolution for a human line, in order: a direct message room's member role; each role mentioned by handle, one placeholder per role; the channel's bound role; the workspace anchor. Handles are unique per workspace and bots are excluded from name matching, so a person named Lee is never confused with a lead. Unaddressed lines keep the followed thread rule. A channel is bound with cast role channel or from the role page; a person opening a direct message with a role's handle creates the room. The Slack adapter reads the same binding table, so a Slack channel may bind to any role. Personal workspace roles have no channel to live in, so they are reached from the role page and the CLI only.

8.6 Decisions

The decision card and the queue gain a chain. A card shows who raised it, who it passed through, what each of them recommended, and who is being asked now. The options keep the order the asker gave them; the recommendation is tagged, never moved to the top, so the human still reads the question. Answering a card sends the answer straight to the session that asked. When a role answers a decision within its authority the card never reaches the queue; it appears in the role page's audit list and in the day's digest so nothing is decided invisibly. While a role holds a decision, the people it would reach see it collapsed under "with a lead" and may answer it early; a person's answer closes the chain.

8.7 Mobile

Mobile gets the decision queue in phase 2 and overview altitude in phase 3, and nothing else in the first version. The phone already syncs the decision rows; the queue screen lists them with the chain and the recommendation and answers through the same store action as the web card. The org page at overview altitude is the morning page: three to eight lines, each with a colored edge, and a count of decisions. Tapping a line opens the role's brief, whose narrative a seat holder can edit from the phone. That is the whole mobile surface, and it is the one that changes the daily habit.

8.8 CLI

Every gesture is a command, so roles can manage roles and the human can script the org. The full reference is in the appendix, with the map from today's anchor verbs.

Inside a role. A session is inside a role when its conversation carries role_id (the standing session) or hand_of_role_id (a hand). Every command reads that context from the calling session: cast task ready scopes, cast spawn makes a hand, cast decide routes to the role, cast brief reads the role's brief, writes carry the role's identity. A person who takes a seat gets the same context in their own shell: cast role seat --take sets a shell default, so their terminal is inside the role until they release it. cast brief edit refuses outside a role and points at cast brief for. A label created from inside a role is filed under the role's bot user, not the host.

09Mechanics

9.1 Wakes

A role sleeps. Its standing session is persistent and dormant, exempt from auto completion as the anchor is. A wake is one pending message delivered into that session, the rail every trigger, chat mention and cast send already uses. What is new is where wakes come from, the outbox in front of them, and the frame they carry.

The outbox

Coalescing has a home: a role_wake_outbox table and a scheduled flush, the same shape the push router uses for phone notifications. A scope event inserts a row carrying the acting session, and the mutation wrapper schedules one flush per touched role after the handler returns. More events insert more rows and schedule nothing. An immediate event schedules a flush at once. A passive event inserts a row and never schedules. The flush is an action: it checks the pause and cap gates, checks whether the standing session is idle, builds the frame as a query snapshot, then in one mutation writes the pending message with the frame as its content and logs the wake. The numbered rules are in appendix A.3.

Loops. Two rules stop chatter. A role's own writes never enter its outbox. A subordinate role's writes never wake its parent either: the parent reads the subordinate's brief line at its next wake, and only a decision or a digest from the subordinate schedules one. A parent's writes inside the subordinate's scope do wake the subordinate, because that is delegation. A frame with no fact newer than the last delivered frame is dropped. The wake cap is the backstop, not the mechanism.

9.2 The wake frame

The anchor today gets one bootstrap briefing at provisioning and relies on its own memory after that. That is too fragile for a role that will be restarted, swapped and parked. Instead, every wake carries a frame that a fresh session could act on with nothing else in context. The frame has five parts, in this order:

  1. Who you are. Role name, handle, scope, who you report to (a role or a person), who reports to you. Two lines.
  2. Why you are awake. The events since the last wake, as a list of facts with ids and the session that caused each. Immediate events first, then folded, then passive.
  3. Your scope right now. The facts: tasks by status and priority, plans with progress, live hands with their state lines, open decisions, unresolved comments, tokens and wakes today against the caps, the brief's age. After the first frame in a session, sent as a diff against the last delivered frame, with counts always complete.
  4. What your subordinates say. The first line of each subordinate role's brief and each hand's pinned state. Never their transcripts.
  5. Your charter. Verbatim in the first frame of a session; afterwards a hash and the word unchanged, and the full text again only when it changed.

How the frame stays fresh, and why it is stored. The pending message rail fixes a message's text when it is enqueued, and delivery is confirmed by matching the transcript echo against that stored text. So the frame is built once, at flush time, when the standing session is idle and delivery is seconds away, and it is stored as the pending message's content. The flush builds it through a query, which reads a consistent snapshot and conflicts with nothing, then writes the row in a short mutation. A retry reuses the stored frame. The facts are read through the same data context every server read uses, as the role's bot user, so nothing the bot cannot read enters a frame or a brief.

The frame has a size budget, and the org page shows the average tokens per wake per role, so the default caps derive from a number rather than a guess. Lists in the facts truncate by priority and say so; counts never truncate. A role whose scope is too big for its frame is a role whose scope should be split, and the org page flags it. Nothing about the org lives in a static file that could drift from the row; the machine wide instruction snippets that teach every session the cast commands stay as they are.

9.3 Delegation and escalation

Down the chain there are three moves, all existing verbs with a role identity attached:

  • Start a hand. Every session born from a role's session is a hand of that role: cast spawn, an Agent tool subagent, cast fork, a routine's spawned run, cast task start --spawn, and a workflow node started inside the role's session. The child carries hand_of_role_id, inherits the host for billing, and counts against the role's daily hands cap. Rows the server creates get the pointer and the gate in the spawn path; rows that are born from a transcript (a subagent, a routine run) get the pointer when the sync path inserts them, inherited from the parent conversation, and are counted but cannot be refused. The orchestrate skill run inside a plan lead is the intended shape for a plan lead's work, and its subagents stay hidden in the inbox as they are today. A hand runs in a worktree from the warm pool when the scope has a repo. Its first turn is the task text the role writes. The precedent exists: a session spawned for a task already takes its parent from the task's plan.
  • Assign a task to a subordinate role. Assignment is delegation. The subordinate wakes with the task in its frame and claims it as itself.
  • Append to a subordinate's brief. A parent may append to a subordinate's brief narrative, marked as the parent's words. This is how intent flows down without a chat message.

Up the chain there is one move: a decision. A hand that runs cast decide inside a role posts it to the role, with an optional category from the fixed vocabulary in appendix A.4. A missing category is recorded as a proposal of none. Routing then follows four rules:

  1. Never grantable categories go to the person at once. Production, destructive and product decisions are sent to the person the chain ends at and to the role in parallel. The role's recommendation arrives as an edit to the same card, which already re-wakes a changed card. The hand is parked no longer than it is today.
  2. The role confirms the category. The hand's category is a proposal; the role confirms it or reclassifies it, and both values are recorded. A proposal of none must be confirmed before the role may answer. A reclassification into a never grantable category forces rule 1.
  3. Inside authority, the role answers. cast decide answer records the role's id, appears in the role page's audit list and in the day's digest, and delivers the answer to the hand exactly as a person's answer is delivered today.
  4. Outside authority, the role escalates. cast decide escalate attaches a recommendation, grows the chain by one step, and routes to the role's parent, which repeats the rules. Ambiguity resolves upward, never by guessing. An escalation with no confirmed category goes to a person.

A role that cannot act does not hold a decision. Routing checks the role's gate at routing time and again at every flush: a role that is paused, held by a seat, over a cap, parked on a limit or dead is skipped, with a chain step that says so, and the decision moves to the next hop. A blocking decision that a role has held past a short routing deadline escalates regardless. The people a decision would reach can see it collapsed under "with a lead" the whole time and may answer early.

Answers travel straight down. A person's answer is delivered to the session that asked, as today, through a server side answer mutation that does not need the person to hold send rights on the hand's conversation. Every role in the chain receives the answer as a passive fact. Advisory decisions work the same way, with the hand proceeding on its default in the meantime.

Where a root role escalates to. A personal workspace's anchor escalates to its owner. A team anchor escalates to the role's owner set, which defaults to the team admins and can be narrowed from the role page; an empty set falls back to the host. The decision records the set of people asked and materializes one inbox row per person, so each queue is one indexed read; the first answer resolves the rest. A subordinate role never needs the setting: its parent is a role or a person in a seat, and the chain follows that.

9.4 Scope and authority

Access does not change. A role's bot user is a team member, the role row carries the anchor's access fields, and every read a role makes goes through the data context as its bot user. Scope is a narrower default inside that access, and it fences only two things.

  • A write from a role or its hands that names no project or plan is filed into the role's scope. The scope is resolved from the calling session the way the CLI already resolves a workspace for a write, so the write is explicit, not a guess. A write that names another scope is allowed, since the role's access already permits it. It becomes a fact in the role's next frame and in the frame of the lead whose scope received it.
  • Role creation is fenced: a role may create roles only inside its own scope and never above or beside itself. Hands cannot create roles.
  • Charter docs refuse writes from any session that carries a role or a hand pointer, keyed on the stored doc type before the patch, and such a session may not change a doc's type to or from charter or brief. A brief's narrative accepts writes from its own role, its parent, and a seat holder only. Refusals land as facts in the writer's next frame.
  • Reads default to scope so frames stay small, but a role may read anything its access allows. It is a colleague, not a prisoner.

Authority is the role's authority list: a structured field on the role row, empty at creation, edited under Settings on the role page or with cast role authority, never free text. The charter may tell the role how to use its authority; it never grants any. The list is a subset of the fixed category vocabulary in appendix A.4, and three categories can never be granted to a role: production, destructive, product. Who may grant is the same gate that may reshape an anchor today: the host, the personal owner, or a team admin. Never a role.

9.5 Identity

Today only cast anchor say posts as the bot; every other write from a session carries the token owner. The org adds one actor resolver on the server: for any CLI write that carries a calling session whose conversation has role_id, the role's bot user is the actor for task comments, assignments and status changes, plan entries, doc writes, project updates and chat posts. Hands keep the host as actor. This is what lets a lead comment on a task as itself, answer in a channel as itself, and appear in the audit list under its own name. It also means the CLI sends the calling session on every write route, which the scope event collector needs anyway.

9.6 Memory and restart

Principle 3 is the design's strongest claim, so it needs a mechanism and a test.

The brief is a doc. Its facts are not stored: they are computed on read from the same query that builds the wake frame, and cached against the newest change log position inside the scope. A quiet scope costs nothing and a busy one costs one query per read, never one per write. Its narrative is written by the role with cast brief edit, and the charter tells it to do so at the end of any turn that changed its understanding. Inside a role, cast state and cast brief edit write the same field, so the brief's first line, the inbox card and the org chart node cannot disagree. The status flag is accepted, and the placement rule ignores done and dormant for a role, because a role is dormant by definition.

Restart keeps the conversation row. cast role restart <handle> ends the agent process and starts a fresh transcript under the same row, the way the existing restart and repair path does, so routines, held messages, the hand pointers and the outbox all keep pointing at the same session. The first wake after a restart carries the brief in full instead of the first line. The daemon also restarts a standing session on its own when counted context tokens pass a per role threshold, set well under the backend's compaction point, and before any model or backend swap. Restart is preferred to compaction because compaction spends a turn summarizing a transcript that is mostly stale frames, while the brief and the next frame already carry everything the role needs. Each automatic restart is logged as a wake with cause restart and its token cost, so the org page shows it.

The acceptance test for the whole feature is that a role restarted this way gives the same answer to "how is this going and what do you need" as it gave before the restart. If it does not, the brief is missing something and the charter is wrong.

Usage limit parks are handled as they are for any session, and the existing account switch on the same machine is the first recovery. Hands park with their host, and the parent's frame lists the parked subtree. Moving a role to another host is a restart from the brief on the new machine plus re spawning its hands from their task text; uncommitted hand work stays on the old disk. It is for a dead machine, not a limit.

9.7 Budgets

Three caps per role, daily, with defaults inherited from the parent and enforced from phase 1: hands started, wakes delivered, tokens spent. The anchors row already carries a daily session cap field, but nothing reads it; the org adds the counters and the checks. Each cap gates one thing. The hands cap gates hand starts. The wake cap gates system wakes. The token cap gates hand starts and system wakes together. A human message, an escalation and the pause interrupt always pass, and a capped role's frame says it is capped.

Tokens are the only unit in the first version, and they need a writer: the schema has a per message usage field that nothing fills today. Phase 1 adds the writer in Claude transcript sync, summing input, cache read and output, because on a persistent transcript the cache read is the cost. Sessions on a backend with no usage in its transcript are counted as unknown and the org page says how many. Dollars need a price table and can come later. The counters are bumped in three places: the paths that create a hand, the outbox flush, and message sync. A role at a cap keeps folding events until the next day; its parent's frame and the human's Org section each show it once, and a person can raise the cap from the role page or the card.

9.8 Pause

Pause is a delivery gate plus a hand policy, not a hide. While a role is paused, system wakes for its standing session and hand starts under it are held, and its outbox keeps folding. Human messages and escalations still pass, with the pause state in the frame. Each running hand receives one interrupt asking it to stop at a safe point, and a hand still running after its next turn end is killed. Resume releases the held rows and delivers one wake whose frame lists everything folded. Pause cascades down the subtree, which is what pausing a role means; there is no separate subtree verb.

9.9 Conflicts

Two hands in one scope touching the same file is the common failure of parallel agent work and the reason many people stop at one session. The org handles it in three layers:

  • Prevent. Hands are started in worktrees by default when the scope has a repo, from the warm pool the workspace command already keeps, so a hand does not pay for install and generate steps.
  • Detect. The file_touches table and its record mutation exist but nothing writes them today. Phase 3 adds the writer in the transcript sync path, for edit and write tool uses only, reading the absolute path Claude's tools carry and the working directory relative path codex carries. Paths are stored relative to the worktree's own top level and keyed by the repo's common git directory, so two worktrees of one checkout compare equal. Overlap is computed once at a hand's turn end and becomes a fact in the lead's frame, and among leads in the anchor's frame.
  • Resolve. The lead decides: interrupt one hand, sequence them, or merge. It is a judgment call, so it is the role's job, not a rule.

9.10 A person in a seat

A role may be held by a person. While the seat is held, the standing session sleeps and receives no system wakes; scope events fold in the outbox for the single wake delivered when the seat is released, and the brief's facts stay current because they are computed on read. Everything addressed to the role goes to the person instead: a human mention or a cast send to the handle becomes a notification to the seat holder with the excerpt, and the chat placeholder says who holds the seat; a hand's decision routed to the role enters the seat holder's queue at once, with a chain step for the seat. The person writes the narrative from the role page, the phone, or cast brief for. Hands under the role keep their pointer. Releasing the seat delivers one wake whose frame carries the brief in full, and the agent picks up where the person left off. The chart shows a dashed node for a held seat.

9.11 Routines

An organization has a rhythm, and the org gets a small one by default, all implemented as routines: an evening digest per lead into the project's Updates tab, an anchor summary into the team channel once every lead has posted or at a deadline, and a weekly brief rewrite where each lead rewrites its narrative from scratch against the facts. Every routine is a trigger the human can see, pause or reschedule from the role page, and it passes through the outbox like any wake, so it is framed, logged and capped. A routine that produced nothing new posts nothing, because a digest with no events is a fact in the frame and the charter says silence is the right answer to it.

12Rollout

Four phases. Each ships something a person can use, and each has an acceptance test that is a scenario, not a checklist. Phase 1 lets a lead advise before it spends: recommendations on every escalation, an enforced hands cap, and hand starts only on a person's assignment.

Phase 1 · A lead that advises, and an overview line that is trueabout three weeks

The roles table with the anchor migration and the root charter template. The role verbs: create, ls, show, pause, resume, retire, wake, restart, charter, with pause as a delivery gate. Project scope only. The scope event collector and per mutation flush, the outbox as an action, the frame query, the calling session on every write route, the actor resolver. Hands with the pointer through spawn, fork, routine and task spawn, and the transcript sync inheritance. Charter and brief docs with the write fence. The usage writer and all three caps enforced. Decision routing in escalate only mode: every hand decision passes through the lead, which must attach a recommendation and escalate; never grantable categories go to the person at once. The decision inbox and the answer mutation. Overview altitude on the org page and the brief line in the project header. The evening digest as a default routine.

Accept when: over five working days, every decision from a hand under the lead reaches the person with the lead's recommendation attached, the lead's overview line is true against the project's tasks, its digest lands in Updates each evening, it never starts a hand that was not assigned to it or that would pass its cap, and restarting it loses nothing a person can detect.

Phase 2 · Authority and the chainabout three weeks

Grantable categories, the answer verb for roles, category confirmation, the audit list on the role page, the routing deadline, the "with a lead" group in the queue. Hand starts on the role's own judgment within caps. The mobile queue. Chat mentions per role, channel binding, the direct message room. The inbox Org section. The anchor's evening summary on the digest deadline.

Accept when: a decision raised by a hand in a granted category is answered by its lead without reaching a person and appears in the audit list; a decision in a never grantable category reaches the person and the lead in parallel and the lead's recommendation lands on the card; a decision routed to a paused lead escalates within the deadline. The person answers from the phone and the hand resumes. A blocking decision's end to end time is measured and stays under a minute when the lead is idle.

Phase 3 · Depth and safetyabout three weeks

Plan scope and plan leads with the union fan out and the project inheritance backfill. The file touch writer and overlap in frames. Frame budget, charter by reference, facts as diffs, the scope too big flag. Seats. cast org init proposing an org from active projects, or projects from plans and tasks. Roles and sessions altitude. Mobile overview altitude. Automatic restart on counted context tokens.

Accept when: two hands under one lead editing the same file in two worktrees produce a fact in the lead's frame and the lead resolves it without a person. A paused role produces zero system wakes and zero hand turns for a day and resumes with one wake. A held seat receives every mention and hand decision addressed to the role.

Phase 4 · Polish until it disappearsongoing

Wake latency under ten seconds from event to injection on an idle session. Tokens by role in the anchor's summary, and a price table if dollars are wanted. Agreement rate per category on the role page, once there is enough decision volume for the number to mean something. Charters from skills. Org templates for the two shapes. The weekly brief rewrite routine. Frame size tuning by model. A usage writer for codex transcripts.

Accept when: the human's daily touches on a workspace with three leads and ten hands are a page read, the decisions in the queue, and one evening message, for five working days in a row.

13What we deliberately do not build

  • A separate org editor. Roles are created from scopes. There is no drag and drop chart that could disagree with the projects list.
  • Roles for labels or paths. A label is personal filing and a path is a machine detail. Both are real requests for a later version, once scope has proven itself on projects and plans.
  • Peer negotiation. Sibling roles may message each other, but conflicts between them are resolved by their parent. No consensus protocols.
  • Free text authority. Authority is a fixed vocabulary of categories. A role never interprets prose to decide whether it may decide.
  • Roles that run on their own account. A role is hosted by a human's daemon and account, as the anchor is. Independent agent accounts are an infrastructure question, not an org question.
  • Long transcripts as memory. The brief is the memory. A role that needs its transcript to function is a role whose brief is wrong.
  • Refusing writes outside scope. A role's access already allows them, and a refusal would only add a round trip. Out of scope writes are made visible instead.
  • Frames built at delivery time. The rail confirms delivery by matching stored text, so the frame is built seconds before delivery and stored, not rebuilt at injection.

14Decisions for the founder

Should the anchor keep its name, or become "the workspace role"?
Recommendation: keep it. It is a good word for the root, users know it, and the CLI keeps working. The org page labels it "Anchor · workspace".
Should assigning a task to a role keep it off the human board?
Recommendation: an assignment to a role never promotes a task; a task a person filed stays on the board with the role's chip. That is one clause in the shared predicate and it changes nothing about human filed work.
Coalescing window default?
Recommendation: two minutes, with human messages, escalations and blocked hands immediate. Short enough to feel live, long enough that a burst of task closes is one wake.
Who may grant authority categories to a role?
Recommendation: the host, the personal owner, or a team admin, the same gate that may reshape an anchor today. Never a role.
Tokens or dollars on the org page?
Recommendation: tokens in phase 1, with a usage writer for Claude and an honest unknown for other backends. Dollars are a phase 4 layer on the same counters.
Should a phase 1 lead start hands on its own judgment?
Recommendation: no. In phase 1 it starts hands only for tasks a person assigned to it, under an enforced cap, and earns autonomous starts in phase 2 once the caps have held for a week.
Should seats be in phase 1 or phase 3?
Recommendation: phase 3. It is right and it is not what proves the idea. Phase 1 proves that a lead over a project makes the human's day shorter.

A.3 Coalescing rules

  1. A write inside a role's scope adds an event to the mutation's collector with the acting session. After the handler returns, the wrapper inserts the outbox rows and schedules one flush per touched role, due after the role's window, unless a flush is already scheduled.
  2. Further events insert rows and schedule nothing; the scheduled flush picks up every due row.
  3. An immediate event inserts a row due now and schedules a flush at once.
  4. A passive event inserts a row and never schedules a flush.
  5. A role's own writes, and a subordinate role's writes, never insert rows for that role.
  6. The flush checks the gates. Paused, seat held, or over the wake or token cap: system rows are held until resume, release, or the next day; immediate rows from a human, an escalation or the pause interrupt pass.
  7. If the daemon reports the standing session mid turn, the flush reschedules itself for the turn's end.
  8. The flush builds the frame through the frame query. If it holds no fact newer than the last delivered frame, the wake is logged as dropped and nothing is delivered. An immediate event is a new fact by definition.
  9. Otherwise one mutation inserts the pending message with the frame as content and the wake id, logs the wake, and bumps the counters. A retry reuses the stored content.
