# Backend security review

Reviewed 2026-09-21, current shared tree based on HEAD `07a081b853ca9bad1a1872eb757eb69a5c1acd34`. Read-only source review; no live service calls, real credentials, deploys, installs, or production mutations. Read the requested audit-playbook Security and Finding format sections. Scope: Convex authentication, authorization, workspace access, dispatch, machine commands, capabilities, sync, administrative exports and storage. HTTP integrations/publishing belong to parent; Slack alias reassignment is included because its entry point is `users.addAlternateEmail`.

Verdict: **NEEDS_CHANGES**. Concrete authentication and cross-account authorization defects exist. This is a prioritized review, not a claim that every backend endpoint is safe or exhaustively inspected.

## Confirmed and traced findings

### [BACKEND-01] Bind native Apple account linking to the verified token email

- **Severity / confidence:** CRITICAL / HIGH.
- **Evidence:** `packages/convex/convex/auth.ts:39` enables `apple-native`. `platform/packages/auth/src/convex/providers.ts:33` verifies Apple's JWT issuer/audience/signature, but `:42` then prefers caller-provided `args.email` to `payload.email`; `:60` passes that address to `createAccount` with `shouldLinkViaEmail: true`. `platform/packages/auth/src/convex/callbacks.ts:73` looks up any existing user by that address and `:89` returns that user's ID without proof of address ownership.
- **Entry / preconditions / impact:** Public `auth.signIn`, native Apple provider. A caller with a valid Apple identity token for the configured app, whose Apple subject has not already been linked, can attach it to an existing Codecast user by supplying that user's email. They receive the victim's authenticated identity, including any machine control privileges. Knowing the email is sufficient; no victim password or mailbox control is checked.
- **Existing controls:** The Apple JWT itself is verified and an already-linked Apple subject returns its existing account. These do not bind the email argument to the verified identity.
- **Local verification:** Ran the actual provider body with a synthetic verified-JWT result and mocked `createAccount` delegated into the real `makeCreateOrUpdateUser` callback against a fake DB. A different caller-supplied email selected the existing user. Temporary copy changed only the `oslo/crypto` import path to the already-installed dependency; no source edits. JWT cryptography/network and Convex account persistence were mocked, so this is a local control-flow proof, not a live sign-in.
- **Fix sketch:** Accept identity email only from Apple's verified claims and require its verified-email claim before linking. Retain display-name input solely as display data. Harden the shared callback independently so untrusted credentials profiles cannot link by email. Review existing native account links for unexpected associations and invalidate sessions/credentials attributable to bad links.
- **Safe regression:** Distinct verified payload email and supplied profile email must never resolve to the latter account; absent/unverified token email must not auto-link.
- **Effort / risk:** M / MED: preserve legitimate Apple relay-address and first-login behavior; canonical fixes belong in `~/src/platform`, followed by vendoring.

### [BACKEND-02] Do not deduplicate unverified password signups into existing OAuth users

- **Severity / confidence:** CRITICAL when signup verification is disabled / HIGH code confidence; production flag unverified.
- **Evidence:** `platform/packages/auth/src/convex/callbacks.ts:65` discards provider/type/link-verification context and `:73-89` links any supplied email. `platform/packages/auth/src/convex/createAuthConfig.ts:138` defaults email verification to the `AUTH_EMAIL_VERIFICATION` flag, and `:153` omits Password's verify provider unless enabled. Codecast `auth.ts:41` does not override that default. Installed `@convex-dev/auth` Password implementation passes signup profile into `createAccount`; its `implementation/users.ts` invokes this custom callback before the library's normal verified-email linking policy.
- **Entry / preconditions / impact:** Public `auth.signIn`, password signup. With verification off (the source default), an attacker can create the previously absent password-provider account for an existing OAuth-only user's email and receive that user's identity. A victim who already has a password-provider account is protected by the provider's existing-account check; requiring verification blocks immediate sign-in.
- **Local verification:** The actual shared callback returned an existing synthetic user ID for `emailVerified: false`. Traced both installed auth versions (Codecast package pins 0.0.79; 0.0.90 also exists in the install) to the same custom-callback override flow. Did not read environment secrets or test live signup; the deployed flag and which accounts lack password providers remain unknown.
- **Fix sketch:** Gate linking by proven provider identity/email verification, never email text alone. Require verification for password signup. Account creation must not create usable credentials pointing at an existing unrelated identity before verification. Audit accounts already linked through this callback.
- **Safe regression:** Existing OAuth user plus unverified password signup must stay separate or await proof; verified linking must still work; existing password account must not be overwritten.
- **Effort / risk:** M / MED: intentional cross-provider dedup needs a migration/compatibility policy and account-recovery tests.

### [BACKEND-03] Validate the actual table of every generic dispatch patch

- **Severity / confidence:** CRITICAL / HIGH.
- **Evidence:** Public `packages/convex/convex/dispatch.ts:150-174` accepts arbitrary patches under `v.any()`. `:369-381` chooses the field policy from the caller's table label but fetches the caller's document ID without `normalizeId(table, id)`. `:387` checks only the fetched row's `user_id`, and `:458` patches that actual document. Conversation field denylist at `:66` does not forbid membership `role`; bucket policy at `:111-115` also permits membership `team_id`. Membership schema accepts both (`schema.ts:365-368`). `teams.getTeamMembersV2` at `teams.ts:535` returns membership IDs through `smallViewContracts.ts:105-110`. `lib/access.ts:234-241` trusts the stored role for team-admin authority.
- **Entry / preconditions / impact:** Any signed-in member can obtain their membership ID through their authorized roster query, then have a different table's generic policy applied to it. This permits self-promotion to team admin. The same table confusion also permits changing routing/access-relevant fields on other caller-owned rows, and the bucket policy permits retargeting a membership to a known foreign team ID. The latter is a cross-tenant escalation, not just a UI inconsistency.
- **Existing controls:** Sign-in and row ownership checks are present; schema validation still applies to the actual target table. A valid membership role update satisfies that schema. Receipt gating is opt-in and does not remove the generic patch path. TypeScript `as Id<any>` is not a runtime table check; [Convex documents this distinction](https://docs.convex.dev/api/interfaces/server.GenericDatabaseWriter#normalizeid).
- **Local verification:** Real `applyPatches` against the repo fake DB changed a synthetic member's role through the conversation policy, then real `requireTeamAdmin` accepted that membership. No real IDs or live database were used. Cross-team retargeting is source-traced, not dynamically exercised.
- **Fix sketch:** Reject IDs whose actual table differs from the chosen policy before any read/write, then use positive editable-field allowlists. Prefer named validated mutation contracts for security-sensitive fields. Add table/policy mismatch tests across every collection policy, including membership/token/daemon-command rows.
- **Safe regression:** Caller-owned membership supplied under a conversation/bucket label must fail without writes; valid inbox edits and server-owned field rejection must continue working.
- **Effort / risk:** S to stop table confusion, M for allowlist migration / MED: old outbox patches may name formerly accepted fields.

### [BACKEND-04] Authorize the conversation before registering or relinking a managed session

- **Severity / confidence:** HIGH / HIGH.
- **Evidence:** `managedSessions.registerManagedSession` at `packages/convex/convex/managedSessions.ts:253-277` authenticates but never authorizes `conversation_id`. `performRegisterManagedSession`'s device guard at `:117` is optional, and its fresh-owner guard at `:171` only applies to a matching preexisting session ID. A new session ID reaches `:220-229`, deletes every managed-session row linked to the supplied conversation, and `:233-240` inserts the attacker's row. `updateSessionConversation` at `:281-325` similarly authorizes only the source session before deleting/relinking rows for a foreign conversation. `getPendingMessagesForSession` at `:674-684` trusts that link and returns the linked conversation's pending messages.
- **Entry / preconditions / impact:** Any signed-in user or valid API token with a foreign conversation ID can replace its live registration and read its queued prompts. IDs can legitimately be known from prior access/shared sessions; knowing an ID is not execution authority. This also disrupts liveness and subsequent delivery/state handling. Omitting the optional device argument avoids the device-online guard.
- **Existing controls:** Reuse of another user's same live session ID is blocked, and pending-message reads require ownership of the managed-session row. Neither verifies who may attach that row to the conversation. Existing `managedSessions.register.test.ts` tests the same-ID hijack, but not a fresh ID targeting a foreign conversation.
- **Local verification:** Real registration core with a fresh synthetic session ID deleted a freshly heartbeating foreign registration; the real public pending-message query then returned its synthetic private prompt to the attacker. No live service or daemon involved.
- **Fix sketch:** Resolve and authorize the conversation's runner/execution grant before any cleanup or attachment. Apply the same rule to relinking, stale cross-user reclaim and device ownership stamping. Re-check conversation authority on pending reads/status mutations as defense in depth. Preserve explicit server-authorized cross-user handovers; stale heartbeat alone is not identity proof.
- **Safe regression:** Fresh and reused session IDs, omitted device, stale/live foreign owner, and arbitrary foreign `conversation_id` must all refuse without deletion; authorized cross-user reparent must still succeed.
- **Effort / risk:** M / MED: multi-machine recovery and reparenting behavior require targeted integration tests.

### [BACKEND-05] Authorize delivery acknowledgments against the target conversation

- **Severity / confidence:** HIGH / HIGH.
- **Evidence:** `packages/convex/convex/managedSessions.ts:688-706` (`markMessageDelivered`) authenticates the caller, fetches any supplied pending-message ID, then marks it delivered without an owner/execution check. `:715-716` also clears the associated conversation's pending flag.
- **Entry / preconditions / impact:** Any authenticated account that learns a pending-message ID can suppress another account's queued message. BACKEND-04 exposes such IDs and content; this endpoint is independently missing its resource authorization check.
- **Local verification:** Real public mutation handler changed a synthetic foreign pending message to delivered for an unrelated authenticated user. No ownership relation was seeded.
- **Fix sketch / safe regression:** Require the same conversation execution authority as the legitimate delivery path, and reject unrelated readers/team members. Test denial with no writes and successful own-session acknowledgment.
- **Effort / risk:** S / LOW to MED: verify intentional agent-box handovers rather than replacing the check with plain owner equality blindly.

### [BACKEND-06] Filter all-workspaces lists through access predicates

- **Severity / confidence:** HIGH / HIGH.
- **Evidence:** `packages/convex/convex/data.ts:137-145` fetches every row on each member team's routing index. `:201-204` returns all of them for workspace `all`, skipping stored access-key filtering. Public `plans.webList` (`plans.ts:1525`, call `:1558`) explicitly accepts `all`; `docs.webList` (`docs.ts:860`, helper call `:190`) does likewise; `projects.list` (`projects.ts:43-65`) and `initiatives` list helper (`initiatives.ts:399-401`) default to `all` when no workspace is named.
- **Entry / preconditions / impact:** A team member receives another person's private rows routed to that team (`team_id: T`, `workspace: user:<other>`). Plans expose full plan documents before enrichment; docs strip content/entries but still leak private metadata. The dedicated by-ID gate would deny the same rows.
- **Existing controls:** Membership gates stop unrelated teams; explicit personal/team branches apply workspace filters. The newer sync-log path enforces access stamps correctly. The all-workspaces branch remains a bypass.
- **Local verification:** Real `canAccessPlan` denied a synthetic private plan to a teammate, while real `scopedFetch(..., workspace: all)` returned it to that teammate.
- **Fix sketch:** Apply the canonical access judge to the union, including owner/explicit assignee grants and held workspace keys. Do not treat routing-index membership as sufficient. Audit all callers and joins for the same union-without-filter pattern.
- **Safe regression:** Include own personal, team-visible, team-routed-private, explicit-grant and foreign-team fixtures across all supported scoped tables and public list variants.
- **Effort / risk:** S-M / LOW to MED: list contents must agree with existing by-ID access while preserving explicit grants.

### [BACKEND-07] Verify alternate addresses before they claim Slack identities and DMs

- **Severity / confidence:** HIGH / HIGH source confidence; full integration not executed.
- **Evidence:** Public `packages/convex/convex/users.ts:209-229` (`addAlternateEmail`) accepts an address after syntax/primary-owner checks, does not prove mailbox ownership, and schedules `slackSync.claimSlackPeopleByEmail`. `slackSync.ts:1641-1663` assigns matching nonmanual Slack identities in the caller's teams. `:1622-1629` schedules room retargeting; `:1253-1285` (`retargetPersonRooms`) changes DM membership to the new user or moves the messages into their room.
- **Entry / preconditions / impact:** A team member can claim the email of a Slack person not already represented by another Codecast primary email and not manually mapped, receive that identity's mirrored DM membership, and reattribute past messages. Team membership does not authorize access to every other person's DMs.
- **Existing controls:** Requires sign-in, caps aliases, rejects another Codecast primary address, operates only in teams the caller belongs to, and preserves manual mappings. None proves the claimed alternate email. The comment promises checks for already-claimed aliases, but the implementation only queries primary addresses.
- **Local verification / missing verification:** Traced the entire server write chain and room membership reassignment; did not exercise a live Slack workspace or real DM. `users.updateProfile` does not accept primary-email changes, which is a useful negative finding. Parent should combine this with its Slack integration review.
- **Fix sketch:** Verify alias ownership (or bind via provider OAuth) before aliases participate in identity/authorization decisions. Store verification separately from display aliases; enforce uniqueness on verified identities. Require proof or admin-reviewed mapping before room reassignment; review existing alias-triggered mappings.
- **Safe regression:** Unverified alias must not schedule identity/room reassignment; verified claims must preserve manual mappings and refuse already-owned addresses.
- **Effort / risk:** M / MED: existing aliases and Slack mappings require a clear migration policy.

### [BACKEND-08] Require the presented share token for public content search

- **Severity / confidence:** MEDIUM / HIGH.
- **Evidence:** Public `packages/convex/convex/messages.ts:2583-2614` (`findMessageByContentPublic`) accepts conversation ID and a search term, checks only that a stored `conversation.share_token` exists, then searches every message and returns a matching message ID/timestamp. It neither authenticates nor accepts/checks the actual share token. `privacy.ts:132-164` defines the correct presented-token rule used by adjacent search paths.
- **Entry / preconditions / impact:** An unauthenticated caller knowing a conversation ID with any stored share token can test content predicates and learn message existence/timing without possessing the share link. This is a content oracle, not a claim that this query directly returns the whole transcript. It also performs an unbounded collect per query.
- **Local verification:** Real public query returned synthetic private-message metadata to an anonymous context without a supplied share token.
- **Fix sketch / safe regression:** Take and check `share_token` using `checkConversationAccess`, or retire the endpoint if unused. Bound search scanning. Confirm missing/wrong token and revoked access reveal nothing; valid guests still resolve their shared message.
- **Effort / risk:** S / LOW: inspect share-view callers before changing the argument contract.

### [BACKEND-09] Enforce device-bound credentials on directly callable Convex endpoints

- **Severity / confidence:** MEDIUM / HIGH; requires an already-obtained valid token.
- **Evidence:** `platform/packages/auth/src/convex/apiTokens.ts:73-80` deliberately omits device binding in `verifyApiToken`; `:113-124` contains the separate binding check. It is invoked by the HTTP `cliRoute` wrapper (`packages/convex/convex/http.ts:3905`) but public token-authenticated Convex functions remain callable directly. Example: `users.getMyPendingCommands` at `users.ts:3596-3639` verifies only the bearer token; device ID is optional. Many public token endpoints have the same shape.
- **Entry / preconditions / impact:** A token marked as device-bound is accepted over the direct query/mutation API without device identity. This defeats the advertised replay restriction, although possession of the bearer token is already a compromise. A plain caller-supplied device string is itself not cryptographic machine proof, so even the HTTP binding is limited.
- **Local verification:** A synthetic device-bound API token successfully called real `getMyPendingCommands` with no device identity. Existing `apiTokens.deviceBinding.test.ts` models the HTTP wrapper composition, not direct public calls.
- **Fix sketch / safe regression:** Unify credential-class validation at every actual public boundary or make transport-only implementations internal and expose a single authenticated gateway. Decide whether the product promises routing affinity or real device possession; implement signed challenge/proof only if the latter is required. Test direct API calls as well as HTTP routes.
- **Effort / risk:** M-L / HIGH: many CLI/daemon callers use direct Convex APIs; a naive global check would lock out existing daemons.

## Hardening and intentionally limited findings

- `platform/packages/auth/src/convex/callbacks.ts:32` accepts a redirect by raw string prefix, not exact parsed origin. A sibling hostname beginning with the trusted URL passes. Parent independently owns the redirect finding; exact-origin comparison plus path/deep-link validation is appropriate. Auth-code takeover through this path was not established here.
- `images.getImageUrl` (`images.ts:45-53`) and authenticated `getImageUrls` (`:75-79`) resolve any known storage ID for any signed-in user. Guest access is stronger: it checks the share token and verifies attachment membership. The code explicitly treats storage IDs as capability handles; review whether persistent URL/ID knowledge after conversation/team revocation is intended before claiming a separate cross-tenant disclosure. `generateUploadUrl` checks sign-in but no per-user upload quota/type/size policy is visible in this file. No upload abuse was attempted.
- `users.linkGitHub` (`users.ts:2390-2416`) accepts identity fields without provider proof. It prevents collision with an already-linked numeric ID but does not validate username against a GitHub token. Identity-spoofing/assignment impacts are possible; parent should evaluate with installation/OAuth findings. I did not establish this alone as an account-login takeover.

## Coverage and controls that held

- Read canonical authentication factories, provider callbacks, API-token hashing/expiry, CLI relay deposit/claim and desktop relay. Tokens use random bytes and stored hashes; API mint/revoke functions require the current user. Relay deposits require a token owned by that user; desktop claims are internal, single-use, TTL-bound and consume the API token. These controls do not repair the linking findings.
- Reviewed `lib/access.ts`, `data.ts`, conversation privacy, membership/admin checks, representative plans/docs/projects/initiatives list endpoints and resource joins. Owner/explicit grant/workspace-key rules are centralized and generally fail closed; the all-workspaces branch is the demonstrated exception.
- Reviewed generic dispatch patch machinery and representative named side effects, capability binding/admin gates, managed-session registration/relink/delivery, daemon heartbeat/claim/result/pending reads, device ownership and cloud placement, cloud Git credential issuance. Ordinary daemon queues are user-scoped; admin broadcast commands require global admin. Cloud placement checks conversation runner and own device. Team capability bindings require team admin and disallow local-path scope keys. No new arbitrary shell-injection claim is made from intentional local execution/configuration.
- Reviewed sync-log read scopes, access-stamp projection and relevant architecture (`sync-log-cargo.md`, plus daemon-loop context). `getRange` rejects non-held scopes and removes cargo when its stored access stamp denies the caller. Legacy change-feed IDs rely on downstream by-ID authorization; this review did not fully verify historical log population or revocation sweeps.
- Inventoried public exports with a source scan for missing identity checks and sampled admin/debug APIs. `admin_mergeUser`, `debugTmp`, `debugTmpDiet` are internal exports. `systemConfig` writes and daemon-log admin reads check global admin; public minimum-version and coarse calibration reads intentionally expose nonsecret global data. Public profile reads project fields rather than returning raw user secrets.
- Reviewed storage URL/upload boundary and representative vault-note scoping; no real storage operation performed. Publishing/artifact storage lifecycle remains parent's scope.
