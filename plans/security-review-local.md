## Findings

### [LOCAL-01] Isolate active vault attachments from daemon authority

- **Severity / confidence**: HIGH / HIGH for the code chain; browser execution and terminal creation were not exercised.
- **Evidence**: `packages/cli/src/vault/vaultScope.ts:402` serves SVG as `image/svg+xml`. `packages/cli/src/vault/vaultServer.ts:160` sends the original bytes with no CSP sandbox, script restriction, or download disposition. `packages/cli/src/vault/vaultServer.ts:349` accepts the ordinary daemon token in an attachment URL. `packages/cli/src/terminal/terminalServer.ts:21` permits any HTTP loopback origin; its WebSocket handler checks that same token at `:379` before allowing shell creation at `:386`.
- **Entry / attacker prerequisites**: Attacker supplies an SVG in a repository/vault the victim browses. The victim opens the served image URL as a document, for example through the browser's Open image in new tab action. Ordinary inline `<img>` rendering does **not** execute SVG scripts. The UI builds token-bearing asset URLs in `packages/web/lib/vault/client.ts:154` and uses them in `packages/web/components/vault/VaultFileView.tsx:128` and `:144`.
- **Trace / impact**: Direct navigation renders attacker-controlled SVG as a document at the daemon's `http://127.0.0.1:<port>` origin. Its script can read its own token-bearing URL. Both that origin and that token are accepted by terminal control and authenticated filesystem/vault writes. Attachment content therefore crosses from untrusted repository data to the victim's local command authority. The comment at `vaultServer.ts:346` that a leaked attachment URL can provide only file reads is incorrect: the value is the full daemon token, regardless of which route first conveyed it.
- **Controls / limits**: Vault path normalization, realpath containment, file-size limits, and Markdown HTML sanitization exist. The Markdown policy strips inline SVG/script, but it does not sanitize separately served SVG bytes. Token authentication still protects requests that have never obtained an attachment URL. No zero-click Markdown execution is claimed.
- **Safe check performed**: Called the real `handleVaultHttp` with a fake request/response, a scratch vault and an inert SVG. Result: HTTP 200, `image/svg+xml`, no CSP, no disposition. The real `originAllowed`, `tokenMatches` and `authorizeLocalRequest` accepted the synthetic attachment token for a loopback-origin terminal/write envelope. No browser, terminal or live endpoint was driven.
- **Missing verification / regression**: In an isolated test environment, navigate to a synthetic SVG that records only an execution marker; require that it cannot run script. Verify that an attachment capability cannot authenticate `/term/ws`, `/fs/*` or vault mutations. Preserve SVG display in `<img>` and normal media/PDF previews.
- **Fix sketch**: Serve untrusted attachments under a restrictive response CSP, including sandbox without script or same-origin privileges, and add `nosniff`/appropriate disposition. Replace URL use of the daemon bearer with an expiring, file-scoped read capability. Keep content delivery separate from the origin/token that authorizes local control; narrowing loopback dev origins adds defense in depth.
- **Effort**: M, including capability changes and browser regression coverage.
- **Risk**: MED — media/PDF rendering and local-development origins need compatibility checks.
- **Browser semantics reference**: [MDN: SVG as an image](https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/SVG_as_an_image) distinguishes inert image usage from direct/document rendering; [MDN: CSP sandbox](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox) documents response-level sandboxing.

### [LOCAL-02] Authenticate hook ingress and gate all effects on acceptance

- **Severity / confidence**: MED / HIGH for unauthenticated mutations and the rejected-event side effects; larger confidentiality impact remains conditional.
- **Evidence**: `packages/cli/src/daemon.ts:2105` accepts `GET /hook/status` before the authenticated terminal/vault handlers, with no Origin, Host or bearer check. `:2112` accepts a caller-supplied `transcript_path`. `:27721` checks launch admission inside `handleStatusData`, but `:28030` calls that function and then independently persists the record and schedules transcript ingestion at `:28035`. `packages/cli/src/launchToken.ts:203` explicitly accepts a missing launch token for legacy hooks.
- **Entry / attacker prerequisites**: An untrusted process under another local OS account can contact loopback without reading Codecast's private token file. A webpage can also send the state-changing GET when its browser/network policy permits reaching loopback; modern local-network restrictions may require permission and were not tested here. Targeted status tampering needs a session identifier; targeted ingestion needs a known readable transcript path. A CORS response is unnecessary to cause a GET side effect.
- **Trace / impact**: The route hands attacker-selected session status, permission mode, message and transcript path to the daemon. Even a launch-token rejection or unknown conversation does not stop the outer sink from persisting the event or scheduling a file sync. That can falsify session state, create durable status records, and trigger ingestion of a caller-selected transcript instead of one discovered through the normal session index. A suitable untracked JSONL transcript can be processed under a supplied session identity, subject to the existing project sync/exclusion gates. This is **not** evidence that arbitrary non-transcript files are uploaded verbatim or that arbitrary commands execute.
- **Controls / limits**: `isSafeStatusSessionId` blocks the old status-filename traversal. Launch tokens reject stale launches inside the status handler, and project sync/exclusion settings constrain a new transcript sync. The ingestion parser, transcript deduplication and existing file-sync entries further constrain effects. These do not authenticate the HTTP sender or make rejection cover the outer sink. The statusline POST at `daemon.ts:2097` is another unauthenticated mutation surface; its 64 KiB body limit is present and valuable.
- **Safe check performed**: Extracted the actual `setHookStatusSink` callback from current source, transpiled it without modifying it, and supplied inert dependencies. A simulated rejection from `handleStatusData` still produced `status-persisted` and `transcript-sync-scheduled`. This proves the surrounding control-flow defect; it does not exercise the complete daemon or network pipeline.
- **Missing verification / regression**: Run a fixture daemon hook router with inert storage/sync dependencies. Require rejection before any write or scheduling for an unauthenticated request, hostile/null Origin, wrong Host, missing/invalid token, stale launch, unknown session or mismatched transcript. Keep a positive test for a genuine installed hook. Prove that no upload is attributed to the caller's alternate session ID.
- **Fix sketch**: Give local hook requests an authenticated envelope (or a private Unix socket). Return an explicit acceptance result and let one outer gate control persistence, status effects and transcript scheduling. Resolve the transcript from the accepted session identity; do not trust an arbitrary HTTP path. Retire legacy tokenless acceptance with a deliberate compatibility window.
- **Effort**: M.
- **Risk**: MED — installed old hooks and early-boot replay require an upgrade path; never silently drop legitimate status delivery during migration.

### [LOCAL-03] Apply cloud-copy containment to the older remote-move path

- **Severity / confidence**: MED / HIGH.
- **Evidence**: `packages/cli/src/remote/session-move.ts:809` invokes `copyGitignoredFiles` after pushing a worktree. `:857` reads repository-controlled `setup.copy`; `:863` and `:866` join those entries into local source and remote destination paths without containment checks; `:870` passes them to rsync. `packages/cli/src/workspace/manifest.ts:374` validates these entries only as strings. The newer path already has the needed security pattern in `packages/cli/src/cloud/transfer.ts:349` (`validateRelativePath`), `:357` (`sourceStat`) and `:373` (`cloudCopyFiles`).
- **Entry / attacker prerequisites**: Attacker edits a repo's `.codecast/workspace.toml` / inherited setup-copy manifest, and the user performs the older remote push/move flow. The named outside file must exist and be readable by the user. The chosen host is user-authorized; this is not an arbitrary internet destination controlled by a webpage.
- **Trace / impact**: Parent-directory entries cause files outside the selected repository to be copied to paths outside the selected remote worktree. A repo collaborator can expand the transfer scope to unrelated local material that the remote host can then read. Parent-directory symlinks are not rejected on this older path either. `rsync -a` preserves final symlinks rather than dereferencing all of them, so a blanket claim that every symlink exposes its target would be incorrect.
- **Controls / limits**: The user intentionally requested remote execution and gitignored setup-file transfer; explicitly configured setup shell commands are intentional capabilities, not findings. This defect is the absence of the relative-file boundary already enforced by the newer cloud flow. Source and destination are passed to a subprocess argv; local-shell injection is not needed for this finding. SSH still protects transport to the configured host.
- **Safe check performed**: Used a disposable repo manifest naming a synthetic sibling JSON file. Extracted the actual function, retained real filesystem/path/manifest resolution, and replaced SSH/rsync execution with inert recorders. It scheduled one rsync whose source and destination both escaped the worktree. No SSH process ran and no bytes left the machine.
- **Missing verification / regression**: Add tests to the real public remote push/move path, stubbing only the process boundary: reject parent/absolute paths, traversal through intermediate symlinks, and invalid manifests before any transfer. Preserve legitimate nested files, directories and `.env` copying. Verify destination containment independently.
- **Fix sketch**: Route this legacy operation through the validated cloud-copy implementation or one shared strict collector/receiver. Fail closed on invalid manifests instead of falling back to unrelated defaults. Make any intentionally wider transfer an explicit user-level capability, rather than something a repo can request with a relative filename.
- **Effort**: S–M.
- **Risk**: MED — callers relying on external shared setup paths need a migration or explicit opt-in.

## Parent-owned findings and remaining hardening

### Extension pre-authentication parser exposure (dependency finding owned by parent)

Confirmed requested reachability: `browser/bridge/host.ts:1200` rejects only `http:`/`https:` Origin values. The literal `null` is accepted for `/ext`, and `:1201` admits this role before it proves the token. `:1123` configures the shared WebSocket parser for 256 MiB payloads; HMAC validation occurs only after receipt of a complete first message at `:1138–1149`. Thus unauthenticated local clients, and opaque-origin browser documents where local-network policy allows the connection, reach the pre-hello parser. This does not bypass HMAC authorization to control tabs.

Parent independently identified runtime `ws@8.18.0` and GHSA-96hv-2xvq-fx4p. The fragment-level advisory is directly relevant to raw local clients; **browser JavaScript does not expose arbitrary RFC6455 fragmentation control**, so do not describe that exact attack as proven from a webpage. Browser-origin large first messages are a separate memory-pressure concern. No exhaustion attempt was made. Upgrade the dependency, reject `null`/unexpected extension Origins before upgrade, reject rather than complete forbidden upgrades, cap pre-auth message size/concurrent handshakes, and test that null-origin `/ext` never enters the parser. Existing tests cover HTTP(S) Origin rejection but not this opaque-origin case.

### Updater shell boundary (manifest-authenticity finding owned by parent)

Confirmed `packages/cli/src/update.ts:35` interpolates both manifest URL and destination into a double-quoted `execSync` shell command. Double quotes do not neutralize command substitution; execution precedes the downloader's later checksum check. Parent owns upstream manifest trust/authenticity classification. Replace this adapter with argv-based `execFile`/spawn and an HTTP(S) URL contract even when manifest signing is also added. No actual payload or network update was run.

### Hardening decisions, not additional confirmed privilege escalations

- **Linux browser isolation**: `browser/remote.ts:48` unconditionally adds `--no-sandbox`; the remote account also holds intentionally forwarded credentials. A browser compromise therefore has a larger blast radius. This is a documented compatibility choice, not evidence of a renderer exploit. Revisit it with a supported sandboxed host image or separate browser OS account/container; test provisioning on that image before removal. Effort M–L, compatibility risk HIGH.
- **Credential scope and host identity**: `daemon.ts:3101` selects reachable registered transfer hosts; CC/provider/agent credentials intentionally fan out. SSH commonly uses `StrictHostKeyChecking=accept-new` (`remote/session-move.ts:161`) and IP-keyed host identity. Explicit forwarding of the laptop SSH agent is opt-in (`cloud/agentBridge.ts:80`), and whole-browser-jar transfer is off unless explicitly enabled (`cloud/browserSync.ts:220`). A compromised authorized remote can read credentials deliberately given to its user; this is not a new bypass. Consider per-host credential grants, revocation visibility, instance-stable SSH host-key pinning and separation between browser and agent execution. Do not label first-use SSH trust by itself as a discovered attack.
- **Config command consistency**: `daemon.ts:7127` has broad read suffixes; config-create/delete at `:7242`/`:7280` use lexical directory checks where config-write resolves ancestors. A hostile symlink can weaken those path fences. Reviewed the issuing boundary: `users.sendConfigCommand` targets the authenticated user's own daemon (`packages/convex/convex/users.ts:4059`), and the administrative endpoint requires admin. No ordinary-teammate escalation established. Track consistent canonical-path handling as defense in depth unless the parent finds a weaker command-issuance path.
- **Auth callback resource bounds**: `platform/packages/auth/src/cli/authServer.ts:77` accumulates `/callback` bodies without a size cap. A strong per-flow nonce protects login substitution; the temporary listener is loopback only. Add a body bound and tighter callback Origin policy as hardening. Canonical package lives in `~/src/platform`; do not patch the generated mirror.
