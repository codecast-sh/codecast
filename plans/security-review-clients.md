# Client trust-boundary audit

Reviewed 2026-09-21 against the working tree identified in `plans/security-review-brief.md` (baseline HEAD `07a081b853ca9bad1a1872eb757eb69a5c1acd34`, with existing uncommitted work). Read the required **2. Security** and **Finding format** sections of the audit playbook. No product source, credentials, production data, services, or permission settings were changed. No vulnerabilities were published. Parent owns the published-page HTTP/owner-token finding; it is not duplicated here.

Verdict: **NEEDS_CHANGES**. Prioritize CLIENT-01 and CLIENT-02. Browser verification used an isolated data-document in the human's Chrome through Cast, synthetic markers only. The tab was closed. Electron verification used the repository's fake Electron harness and extracted policy callbacks, never the live app or OS capabilities.

## Findings

### [CLIENT-01] Sanitize chart output before it enters the authenticated document

- **Severity / confidence:** HIGH / HIGH. Confirmed click-triggered stored XSS in the rendering pipeline; production-site execution was deliberately not attempted.
- **Evidence:** `packages/web/lib/castChart.ts:91` reads attacker-supplied `data-spec`; `:111-126` passes arbitrary mark options and data to Plot exports; `:148` inserts Plot's result without sanitization. `packages/web/components/HtmlSnippet.tsx:120-130` sanitizes the initial HTML, then hydrates charts afterward in an ordinary same-origin shadow root. The installed Plot 0.6.17 implementation at `node_modules/.bun/@observablehq+plot@0.6.17/node_modules/@observablehq/plot/src/style.js:396-404` creates SVG anchors and assigns their `xlink:href` directly.
- **Entry / attacker prerequisite:** `hydrateCharts` via `HtmlSnippet`, reached by `cast-canvas` blocks and all-HTML message bodies. An attacker must get authored content into a message/document the victim views, then have the victim click a chart mark. Authenticated teammates and untrusted material repeated by an agent are relevant content sources.
- **Impact:** The mark's link executes JavaScript in the application's document. Shadow DOM does not isolate script privileges: application tokens, cached conversations, and authenticated actions become reachable. The chart path also reintroduces automatic remote image fetches through Plot's image marks. Mobile does not run this Plot hydrator.
- **Existing controls:** DOMPurify removes scripts, handlers, and unsafe hrefs from the original markup. That does not inspect URL strings inside JSON data attributes or the DOM generated afterward. The transform-name allowlist does not constrain mark URL channels. The canvas click listener handles recognized internal links only and does not block the unsafe generated SVG anchor.
- **Safe verification completed:** Ran the actual sanitizer followed by actual `hydrateCharts` in JSDOM. The generated anchor retained a JavaScript-scheme URL and had neither `target` nor `rel`. Mounted that generated output in a shadow root on an isolated Chrome data-document; activating the mark set a synthetic window marker to `1`. No network requests or real tokens were involved.
- **Missing verification:** No authenticated production exploit, no Electron execution of this payload. The application server source search did not reveal a script CSP; any deployment-only CSP remains outside this audit. Such a policy could mitigate execution without fixing the sink.
- **Fix sketch:** Add an explicit mark/options schema, validate every URL channel including resolved per-row values, and run the generated figure through an appropriate DOM/URL policy before mounting. The final DOM must obey the same script, link, image, and CSS rules as the input canvas. Add a browser regression asserting a synthetic script marker never executes and forbidden image URLs never load.
- **Effort / compatibility risk:** M / MED. Legitimate chart links and image marks need an explicit supported policy. [Plot mark documentation](https://observablehq.github.io/plot/features/marks) documents href as an ordinary mark channel; it is the application's responsibility to constrain untrusted values.

### [CLIENT-02] Keep foreign documents out of privileged Electron windows and authenticate IPC senders

- **Severity / confidence:** HIGH if the foreign-main-document navigation chain holds in the packaged app / HIGH for absent navigation/IPC guards, MED for the complete attacker-reachable chain. The live-app microphone chain was not exercised.
- **Evidence:** `packages/electron/main.js:259-265` gives every shell window its preload, with isolation enabled but sandbox disabled. `:381-385` handles only new-window requests; the shell installs no `will-navigate`/`will-frame-navigate` navigation guard. `packages/electron/preload.js:62` unconditionally exposes the bridge. `packages/electron/main.js:1725-1730` forwards `voice-command` while ignoring its sender. `packages/web/components/calls/VoiceHostPanel.tsx:259-265` executes those forwarded commands; `packages/web/lib/calls/callManager.ts:1371-1376` accepts leave-call, mute, and camera commands. Many other handlers also ignore their sender, including app-window and OS-permission controls.
- **Entry / attacker prerequisite:** A foreign page must first become the top-level document of a shell window. An arbitrary foreign iframe does not automatically have ipcRenderer or the preload bridge. The source-visible path is a normal HTTPS link produced by the chart hydrator (CLIENT-01): it has no target, its default navigation stays in the shell window, the shell has no navigation guard, and the next top-level document loads the unconditional preload. This path does not require first exploiting chart JavaScript. An unsandboxed browser iframe's user-activated top navigation is another candidate. The codecast app must be running; voice impact additionally requires the trusted voice-host window and applicable OS grants/call state.
- **Impact:** A foreign page inherits the preload bridge and can invoke privileged host operations. In particular, it can send commands through main into the still-authenticated voice-host window to change microphone/camera state or leave a call. This is a confused-deputy boundary, not a claim that Node is directly available to page JavaScript.
- **Existing controls:** `nodeIntegration:false`, `contextIsolation:true`, HTTP(S)-only new-window/openExternal handling, and origin checks on selected handlers. Dedicated native browser panes are separately sandboxed and receive no preload. These controls do not guard navigation in shell windows or `voice-command`.
- **Safe verification completed:** The repository's fake main-process harness showed no navigation-guard listener. A test-injected event whose sender URL was a synthetic foreign origin successfully created an app window. With a fake trusted voice host, the same test-injected sender's mute-state command was accepted and forwarded. This proves admission/forwarding, not that an arbitrary child frame can manufacture IPC. No real window, microphone, or camera was used.
- **Missing verification:** Full foreign-frame-to-top-navigation reproduction in a packaged desktop app, and end-to-end call impact. These should be isolated integration tests with fake media, not tests on a person's live call.
- **Fix sketch:** Centralize shell navigation and IPC admission: exact approved origins, main-frame identity, registered shell-window ownership, and per-channel payload validation. Deny foreign navigations or route them to the external browser/native pane. Do not expose the bridge to unexpected documents, and validate the sender again in main. Cover voice commands, screen sources, host-policy extension, settings, notifications, and window controls. Bundle the preload so Chromium sandboxing can be restored as defense in depth.
- **Effort / compatibility risk:** M–L / MED. OAuth, dev origins, detached windows, and voice-host handoffs need tests. [Electron's security guide](https://www.electronjs.org/docs/latest/tutorial/security) recommends navigation restrictions and validation of IPC sender frames.

### [CLIENT-03] Authorize the requesting frame, not its containing window

- **Severity / confidence:** HIGH potential clipboard/media exposure / HIGH confidence in the policy defect, MED in complete capability exploitation.
- **Evidence:** `packages/electron/main.js:3209-3222` trusts hostnames irrespective of scheme/port. `:3249-3253` ignores requesting-frame URL/origin and grants checks even when `webContents` is absent. `:3308-3318` selects a screen without checking the requesting frame or gesture itself. `packages/web/components/browser/backends/FrameBackend.tsx:209-223` frames arbitrary pages and delegates clipboard read/write. This finding concerns iframe-backed panes, not the native panes' separate deny-all session.
- **Entry / attacker prerequisite:** Attacker controls an HTTPS page opened in an iframe-backed browser pane inside a trusted shell window. Browser feature/gesture requirements still apply. A known loopback origin is also broadly trusted by hostname alone, although explicitly opening local development apps is intentional and not itself reported as a vulnerability.
- **Impact:** The foreign frame may receive capability approval because its outer `webContents.getURL()` is Codecast. Clipboard access is a concrete delegated feature on the iframe; media and screen impact depend on other browser and OS gates. The checks fail to represent the claimed first-party-only policy.
- **Existing controls:** Permission-name allowlist; native panes deny all permissions; OS-level consent and browser feature-policy restrictions still apply. These mitigate impact but do not make the frame authorization correct.
- **Safe verification completed:** Evaluated the actual source callbacks with fake Electron objects. A foreign-frame clipboard permission request under a Codecast window returned true, the foreign-origin permission check returned true, the null-webContents check returned true, and an HTTP Codecast hostname received media approval. No clipboard or device API was called.
- **Missing verification:** Actual Electron clipboard/media request lifecycle, and whether a particular frame's feature policy blocks each requested capability. No real clipboard read or capture was attempted.
- **Fix sketch:** Check the requesting frame's exact origin and its relationship to an approved shell document. Deny absent/opaque origins by default. Use request-specific screen-source consent bound to a frame and consume it only for that frame. Make any dev-origin exception explicit and scoped. Add frame-origin and null-webContents cases to main policy tests.
- **Effort / compatibility risk:** M / MED. Screen-share and embedded first-party call flows need compatibility tests. [Electron's Session API](https://www.electronjs.org/docs/latest/api/session) provides requesting-origin/frame details for permission handling.

### [CLIENT-04] Propagate logout and principal changes to every window before reusing cached state

- **Severity / confidence:** HIGH privacy risk on shared devices / HIGH confidence in the storage-event defect, MED confidence in the full account-switch disclosure timing.
- **Evidence:** `packages/web/src/providers.tsx:141` supplies `durableAuthStorage` to ConvexAuthProvider. `platform/packages/auth/src/web/durableAuthStorage.ts:148-180` returns a wrapper object, not native localStorage. Installed `@convex-dev/auth` 0.0.79 `src/react/client.tsx:146` discards events unless `event.storageArea === storage`; native events name native localStorage, so they cannot match this wrapper. `packages/web/hooks/useCodecastSignOut.ts:11-13` clears only the current process's store and shared disk cache. `packages/web/store/syncReplication.ts:38-39,259` uses one origin-wide channel/lock with no principal namespace; `packages/web/hooks/useSyncRole.ts:17-18` rebinds only on eligibility. `packages/web/store/idbCache.ts:85` uses a single account-independent database. `platform/packages/auth/src/web/localAuth.ts:69-71` keeps rendering when an in-memory token remains.
- **Entry / attacker prerequisite:** At least two windows/tabs share a browser/Electron profile; one signs out or switches account while another still holds the previous token/cache. A later user of that profile, rather than a remote unauthenticated attacker, is the principal confidentiality concern.
- **Impact:** Sibling windows do not receive the auth library's logout/account-switch notification. Cached private content can remain visible there, and the unscoped replication host can repopulate a newly signed-in window with old-account state. Server authorization still protects fresh server reads/writes; it does not erase already loaded private content.
- **Existing controls:** Explicit logout purges durable auth and the caller's protected memory. Gesture replication is already principal-scoped. Mobile uses a verified-principal trust anchor and account-change memory clearing. Those are useful precedents; the separate web replication transport is not equivalently scoped.
- **Safe verification completed:** Constructed an actual native StorageEvent in JSDOM and instantiated the real durable-storage wrapper: the auth library's identity comparison rejected the event. No database was opened and no credentials were used. Confirmed canonical `~/src/platform/packages/auth/src/web/durableAuthStorage.ts` matches the vendored copy.
- **Missing verification:** Two mounted auth providers with fake tokens, logout, delayed hydration/replication, and account switch in a browser. Do not infer indefinite server access from this result; token revocation/expiry remains enforced server-side.
- **Fix sketch:** Give the auth wrapper an explicit supported cross-window invalidation mechanism. On logout/principal change, synchronously stop old dispatch/replication, invalidate pending hydration, and clear every window's protected memory. Namespace store/cache and replication ownership by verified principal, or establish a tested single-principal-per-origin protocol. Change canonical platform code, then regenerate its mirror.
- **Effort / compatibility risk:** L / HIGH. Preserve offline boot and queued writes while preventing cross-principal replay. Regression tests must use two providers/windows and delayed callbacks, not just storage-key deletion assertions.

### [CLIENT-05] Enforce canvas network isolation beyond literal CSS URLs and image tags

- **Severity / confidence:** MED / HIGH. Confirmed policy bypass; no third-party request was sent in verification.
- **Evidence:** `packages/web/lib/canvasSanitize.ts:24-25` leaves audio/video/source and poster attributes available; `:35-38` removes only literal `url(...)` and `@import` syntax. The image-specific checks at `:64-76` do not cover those media elements. `packages/mobile/components/CastCanvas.tsx:108-138` duplicates the same CSS/image checks; its WebView at `:325-332` has no network-denying CSP. CLIENT-01 separately covers network-capable elements created by chart hydration.
- **Entry / attacker prerequisite:** Untrusted HTML/canvas content is viewed. Mobile additionally requires opening the canvas modal.
- **Impact:** Media posters/preloads and CSS escape forms can cause automatic third-party requests, exposing viewer IP/timing and any attacker-encoded URL content. This contradicts the documented network-isolation boundary. It does not imply CSS can read arbitrary application secrets.
- **Existing controls:** Ordinary remote images, SVG images/use references, unescaped remote CSS URLs, and imports are stripped. Normal markdown images have an explicit third-party load gate.
- **Safe verification completed:** Actual sanitizer output retained escaped CSS fetch syntax and foreign media URLs. Chrome recognized the surviving CSS as a background image and retained the poster URL. A restrictive CSP on the isolated fixture blocked network access during this test. Existing canvas tests all passed because they cover ordinary spellings/image tags.
- **Missing verification:** iOS/Android WebView network instrumentation; CSS parity is confirmed by source, not a device run. Additional CSS URL-bearing constructs remain to be enumerated.
- **Fix sketch:** Use a complete allowed-tag/attribute policy and parse CSS rather than filtering URL syntax with regex. Add a network-denying CSP in mobile's isolated WebView, and evaluate a similarly isolated web rendering document for stronger enforcement. Explicitly preserve supported trusted-storage images. Test actual browser request attempts with all requests intercepted locally.
- **Effort / compatibility risk:** M / MED. Some media and CSS effects will stop rendering; document the supported canvas contract.

### [CLIENT-06] Confine canvas layout so untrusted styles cannot cover application controls

- **Severity / confidence:** MED / HIGH for the layout escape, MED for product-specific phishing impact.
- **Evidence:** `packages/web/components/HtmlSnippet.tsx:35-39` supplies only a cosmetic host reset; `:103,120` uses a shadow root with attacker-authored styles. The wrapper at `:233` and clip area at `:263` use overflow clipping but no paint/layout containment. `packages/web/lib/canvasSanitize.ts:87-92` preserves arbitrary non-network CSS, including host selectors and fixed positioning.
- **Entry / attacker prerequisite:** A victim views untrusted canvas markup; the attacker controls its CSS. No script execution is needed.
- **Impact:** A canvas can position its host or descendants over surrounding UI and imitate trusted application prompts or obscure controls. Shadow DOM scopes selectors but is not a layout-security boundary. This also increases the credibility of CLIENT-01's clickable content.
- **Existing controls:** Overflow wrappers constrain ordinary flow; ancestor transforms/containment may limit the affected area in some surfaces. Links ordinarily open with noreferrer/noopener. No credential capture or deceptive user flow was tested.
- **Safe verification completed:** Chrome rendered sanitized markup with the host fixed at z-index 2147483647 across the fixture's entire 1512px viewport. It was a neutral audit fixture, not an imitation login screen. Network was blocked with CSP.
- **Missing verification:** Every real message/document ancestor and virtualizer layout; the result proves the component lacks its own confinement, not that every route permits a whole-screen overlay.
- **Fix sketch:** Add a trusted outer paint/layout containment boundary that untrusted CSS cannot target, constrain host styling, and keep fullscreen controls outside the untrusted stacking context. Consider an iframe when rich arbitrary CSS is a requirement. Browser tests should assert canvas hit-testing cannot reach outside its assigned rectangle.
- **Effort / compatibility risk:** M / MED. Sticky elements, overflowing chart tips, and fullscreen sizing may need adaptation.

## Coverage and controls that held

- **Web rendering:** Read canvas sanitizer/component/chart/widget paths, shared conversation markdown dispatch, vault HTML schema and plugin ordering, published-page embed sandbox, frame theme/gesture messaging, trusted image policy, and generated-code sinks. Ordinary React markdown does not enable raw HTML; vault HTML uses `rehypeRaw` before an explicit sanitize allowlist. PublishedPageEmbed uses `sandbox="allow-scripts allow-popups"` without same-origin permission. The parent owns server-side published-page isolation and token exposure.
- **Web privacy/state:** Read IndexedDB hydration/purge, local auth, durable auth, sync host transport, gesture bridge, workspace collection guards, server-confirmed query gates, and explicit logout. Gesture messages bind to user IDs; workspace enumeration uses workspace keys rather than routing team IDs. Server access validation was not re-audited here.
- **Electron:** Read shell/preload navigation and IPC, permission policy, screen sources, native browser panes, deep-link entry, and fake-harness tests. Native panes use a dedicated partition, deny capabilities, disable Node, enable sandboxing, and receive no preload. Packaged CDP is disabled unless explicitly configured; that explicit local capability is not a vulnerability. HTTPS-only external opening and JSON serialization in navigation injection are positive controls.
- **Mobile:** Read canvas WebView construction/sanitization, secure auth storage, verified-principal trust/dispatch gates, link routing/native intents, share-link resolution, and markdown image admission. Raw canvas content is JSON-encoded with `<` escaped before insertion into the trusted shell script. Native auth tokens use SecureStore. No observed direct raw-markup script breakout; the duplicated egress weakness remains.
- **VSCode:** Read the complete extension entry point and package manifest. CLI calls use `execFile` with argument arrays; fallback shell arguments are quoted. Configured CLI execution is intentional. No confirmed injection from filenames or blame labels. Workspace trust/configuration behavior was not integration-tested; no restricted-mode bypass is asserted.
- **Legacy desktop:** `packages/desktop` contains only generated Tauri schemas in this checkout, with no current application source/config to audit. Do not infer a deployed Tauri permission policy from those schemas.
- **Shared contracts:** Sampled entity/deep-link parsing, scope strings/project keys, capability resolver, and encryption primitives. Scope parsing rejects unknown/malformed variants; local filesystem scope keys cannot back team bindings. Capability resolution explicitly leaves consent/pinning to downstream enforcement, so the pure resolver is not claimed to be a security gate. AES-GCM uses random 96-bit nonces. No E2EE product guarantee was inferred from the utility README or unused APIs.
