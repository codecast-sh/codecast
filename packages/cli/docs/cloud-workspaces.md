# Cloud workspaces

`cast spawn --cloud [host]` runs each prompt in a separate native git worktree on a registered cloud host. `--cloud` implies isolation; `--subagent --agent codex` keeps the workers nested under the caller.

```sh
cast spawn --cloud i-084309c56a91e15ff --agent codex --subagent - - - <<'PROMPTS'
First task
---
Second task
---
Third task
PROMPTS
cast hosts ls --json
```

The existing host is woken over AWS and reached over SSH. The repository is refreshed from the real remote's main branch. If the host cannot authenticate to the git remote, the laptop fetches fresh main into a temporary repository and transfers it over SSH; it never rewrites the laptop's branches or index. The refresh is fetch-only: an existing host checkout keeps its HEAD and its uncommitted work; only a shared placement (below) moves HEAD, and it refuses a dirty tree rather than discarding it.

Manifest-listed private files travel directly over SSH, not Convex. Each worktree receives a private input snapshot, including local manifest overrides, without modifying the shared checkout. Healing uses that same snapshot. Setup and dependency installation run on the host. `PORT_WEB` (or the corresponding manifest port name), `CODECAST_PORT_WEB`, and the worktree identity are available in new and resumed sessions. Use the allocated port explicitly when starting a development server.

Port reservations are persisted before setup begins and coordinated across processes and registered repositories. A workspace reserves its ports even before anything listens. Deleting the workspace releases the reservations. Lock owner metadata is published atomically; dead or unreadable owners are never automatically reclaimed. Drain old reservation writers during an upgrade: they share the lock namespace but still have their old age-based reclamation behavior.

Creation, healing and destruction share per-workspace operation ownership. A concurrent same-name operation is refused; another workspace can proceed independently. Ordinary failures release ownership for healing. An abruptly killed owner fails closed: setup children might still be running, so inspect and stop those children before removing the operation file named in the error and retrying. A running server is an advisory warning, not a failed workspace contract. Input staging establishes repository-local Git exclusions for Codecast's worktree and state directories, without editing the project's tracked ignore file.

Cloud Bun installs use a per-workspace cache with the global store disabled. Native git worktrees share the repository's object database, but installed dependency files must not share writable storage with another task. This is working-directory and dependency separation, not a security sandbox: agents running as the same Unix user can deliberately access other paths.

Kill/dismiss cleanup preserves dirty trees, unpublished commits, and worktrees still used by another session. Unknown ownership fails closed. Temporary account and agent restarts must not collect workspaces. Manifest teardown commands are responsible for stopping separately launched development services; killing a session does not promise to find arbitrary detached servers.

## Idle protection

A settled parent does not necessarily mean its background work has finished. The daemon renews host activity for waiting work, open app-server turns, and recent subagent activity. Before allowing idle shutdown, a separate bounded Linux check also looks for live task descendants, detached tmux work, headless workers, and CPU activity in otherwise quiet agents or shells. It follows descendants across elevated commands. Missing or unreadable process evidence keeps the host awake rather than risking a running task.

A dormant agent, idle prompt, or recognized persistent MCP/browser service is not work by itself. An unknown live helper or detached development server can keep the host awake until it exits; stop services you no longer need. The check reads process identity, not another copy of the transcript/workflow parser.

For a deliberately quiet operation, run this on the cloud host before starting it:

```sh
cast hosts keepalive 30
```

Each call creates an independent lease for 1–1440 whole minutes. Leases use the installed host's `/home/ubuntu/.codecast/host-keepalive` directory, not a session's `HOME` or `CODECAST_DIR`. A shorter later lease cannot cancel another caller's longer one. Expiry removes that lease's veto; the ordinary idle grace still applies. The command refuses an older watchdog without lease support; updating only the CLI binary does not upgrade an existing host's watchdog. The command does not wake, provision, or restart a host.

## Updating a host

A provisioned host cannot update itself, and this is deliberate rather than a
gap in the updater. Provisioning installs the CLI as a shim that runs the
bundle under bun, because `bun --compile` output segfaults on Linux, so the
daemon's `process.execPath` is bun itself. The shared updater treats an
execPath containing `bun` as a developer checkout and refuses before fetching,
which is the `forced_update_failed ... error=dev_mode` line such a host logs on
every check. The refusal is protecting you: `performUpdate` replaces the
running executable in place, and on this shape that executable IS bun, so
letting it proceed would overwrite the host's interpreter. The published Linux
artifacts are compiled binaries and would not run here anyway.

So a host moves version only when someone ships it a bundle. Until `cast hosts`
grows an update verb (ct-52223), the procedure is:

1. Build the release you want from a clean checkout, not from a shared tree,
   so no other session's uncommitted work travels. `buildLinuxCast` builds into
   its own directory and returns it.
2. Ship the whole directory with `uploadLinuxCast`. The build is split, so its
   entry is a few hundred bytes that imports its chunks, and there were 246
   of them in 1.1.137. Copying only `main.js` and `daemon.js` leaves the host
   restarting forever on a module it cannot find.
   The upload merges into `/usr/local/lib/codecast` rather than replacing it,
   which is what preserves adjacent files such as `idle-probe.py`.
3. Run `cast --version` on the host BEFORE restarting the daemon. The old
   daemon is still serving at this point, so a bad bundle costs nothing and
   backs out by restoring the previous directory.
4. Restart `codecast-daemon.service`.

This updates the bundle, and only the bundle. The idle watchdog at
`/usr/local/bin/cast-idle-check` and the probe beside it are written by
`baseProvisionScript`, not by the build, so they keep whatever version the host
was last provisioned with. Compare them against what the release you are
shipping would generate before assuming a host is current; on 2026-09-17 they
happened to match, which is not something to rely on.

A restart does not by itself kill sessions on the host, but whether it does
depends on who started the tmux server. A server the daemon spawned shares the
daemon's control group and dies with it under `KillMode=control-group`; a
server started from an SSH session sits in its own scope under the user slice
and survives. The daemon re-adopts existing sessions by name either way. Check
before assuming, and tell whoever is working on the host first.

## Deferred storage optimization

Writable shared package symlinks were tested and rejected: one workspace's package mutation appeared in a sibling. Reflinks were unavailable on the host's ext4 filesystem. An OverlayFS proof isolated writes using a read-only lower layer and separate upper layers, but a production implementation needs per-workspace mounts, cleanup and cache-version lifecycle. That optimization was deliberately not built. Private dependencies and sufficient disk space are the baseline.

## From the composer

The machine dropdown is the standing choice. Picking **Cloud Linux** there turns "run in the cloud" on — cloud mode is derived from the selected machine, never stored beside it — and every later new session opens on the host until another machine is picked, even while the host sleeps (its chip reads "asleep — it boots when the session starts"). The **run in the cloud** toggle is this composer's override: on moves the pick to the host, off moves it back to a laptop, and neither repoints future sessions. With only a cloud host on the roster the toggle stays on and disabled.

One predicate (`cloudPlacementFor` in `@codecast/shared/contracts`) decides, on the web and on the server, whether a launch aimed at the host needs a laptop to prepare it. A folder the host already holds — `~/work/<repo>` and its worktrees, advertised in its roots now that `work` is a project parent — starts there as a plain session; a laptop folder parks the row (`cloud_placement: pending`, a fresh `cloud_placement_token`) and hands the most suitable laptop a `cloud_spawn`. Any client that targets the host with a laptop path gets the same upgrade server-side, so mobile's machine pick and `cast spawn --device "Cloud Linux"` (the display name resolves now, beside the id and the stored label) park rather than running in the host's main checkout. The upgrade only fires when the caller is the session's runner: a team agent box is never parked.

No laptop online is not an error: the row waits with "Waiting for <laptop> to come online to prepare the cloud host", and the next laptop heartbeat that follows an offline stretch (`users.daemonHeartbeat`) re-issues the `cloud_spawn` — to the laptop holding the checkout if one is online, else the one that just came back. Cloud toggled on before a folder is picked parks the row without asking any laptop (nothing to prepare yet, no token); the folder pick is what enqueues the preparation, and a folder change under a park supersedes the running `cloud_spawn` and asks again with a new token. A claimed `cloud_spawn` counts as live for the child's full 25-minute run, and the daemon runs one `cast cloud start` per conversation at a time. A model or agent pick on a preparing row rides the placement (no `start_session` is sent to a pending row). Re-picking Cloud Linux on a row whose preparation failed or expired retries it with a new token, and only that re-pick does: a failed `cast cloud start` reports itself through `cloud.reportPlacementFailure`, which stamps `cloud_placement_failed_at`, and the heartbeat re-issue skips a row carrying that stamp — otherwise every laptop coming back online would wake the box, clear the error the human is reading and fail the same way. That report is fenced by the park's token like placement itself, so a child whose park was superseded cannot write its error onto the park that replaced it.

Pointing a preparing row at a laptop cancels the placement (the runner's call, like the park itself): the live `cloud_spawn` is superseded and the row starts on the laptop. Pointing it at the host for a folder the host already holds ends the placement the same way and starts there plainly. A `cast cloud start` that was already mid-SSH passes the token it was given (`expect_token`); placement refuses it (`{placed:false, reason:"superseded"|"not_pending"}`), the child removes the worktree it acquired on the host (`cast ws destroy`) and exits 0. A row the host already placed re-launches there for the same folder; asking it to move to another folder is refused — start a new session for that.

## Shared checkout

A cloud session runs in its own worktree on the host unless asked for the host's main checkout: `cast spawn --cloud --shared "<task>"` (one task; refused with `--worktree`, with several prompts, or without `--cloud`), or turn **isolated worktree** off while **run in the cloud** is on (on a row the machine pick already parked, the toggle re-parks it with the new mode). The mode is stamped on the row as `cloud_workspace` (`isolated` when absent) and rides the `cloud_spawn` to `cast cloud start --workspace shared`.

One checkout holds one session, and the claim comes first. Before anything in the host checkout moves, the row claims `~/work/<repo>` in Convex (`cloud.claimSharedCheckout`; `cast spawn --shared` parks its row up front through the same rule in `/cli/spawn`). The occupancy rule (`sharedCheckoutOccupant` in `@codecast/shared/contracts`) counts every alive session on that host holding the path: shared rows (a pending one only while it carries no `session_error`) and any session whose `project_path` is the root, which is what a `cast remote move` lands as. The same rule holds for a plain start in a host folder: a launch the placement predicate calls native (the host's own `~/work/<repo>`) goes through the occupancy check in `enqueueStartSession` and lands as that error on the row instead of a second session in one working tree. Two racing shared placements cannot both win; the loser is refused before the root's HEAD moves, naming the winner: "the host checkout … is in use by session <id> (<title>) — run this session isolated, or finish/kill that one". Placement re-checks (exclude-self) when it flips the row.

After the claim the root is refused when it is dirty (the files are listed: commit, stash or reset them on the host, or run isolated) or detached at commits no branch holds; otherwise HEAD is detached at fresh `origin/main` and a per-session branch `codecast/cloud-<hex>` is checked out there. `worktree_branch` is stamped, `worktree_name` stays empty, so the row is a top-level card with a `shared` chip. Ports and install come from the host's `cast ws root --input-root <snapshot> --json`, which records the main checkout under the reserved workspace name `shared-checkout` (`.codecast/workspaces/shared-checkout/state.json`, `state.path` = the root, no `CODECAST_CLOUD_WORKSPACE` or `BUN_INSTALL_*` env: the root keeps bun's global store). `worktreeEnv` reads that record for a session whose cwd is the root, so `$PORT_WEB` and `AGENT_RESOURCE_INDEX` are set as in a worktree; `cast ws acquire shared-checkout` is refused, `cast ws destroy shared-checkout` drops only the record and its ports, never the repo, and `cast ws status/heal shared-checkout` follow the live HEAD. The laptop's manifest secrets overwrite the root's gitignored copies on every placement; the tracked manifest is never written into the root; setup that leaves the tree dirty fails the placement with the file list (commit the lockfile upstream, or run isolated).

Everyone else's refresh of the root is fetch-only. `refreshRemoteCheckout` never moves HEAD unless the shared placement passes `moveHead`, and isolated worktrees are pre-branched from `refs/remotes/origin/main` before `cast ws acquire`, so `cast spawn --cloud`, `cast fork --cloud` and the web's isolated sessions keep working beside a live shared session, and a dirty root no longer blocks them. A `cast remote move` onto an occupied root is refused on the laptop (`fetchRootOccupant`) and again in `devices.moveSessionToDevice`; a moved session is itself an occupant until it is killed. `cast hosts ls` prints `<repo> (shared)` or `(shared, pending)` for such rows and attributes the `shared-checkout` record to its session by path; once that session ends the record reads `main checkout, free` rather than orphan. Each shared HEAD move also prunes the `codecast/cloud-*` branches that `origin/main` already contains (a branch with unmerged commits, or one checked out in a worktree, is kept).

A failed preparation leaves the row parked with the error (`session_error`), which by the occupancy rule frees the checkout for the next claimant; a `cast spawn --shared` interrupted with Ctrl-C after its row exists stamps the row the same way (`spawn interrupted (SIGINT)`), and a web park's child times out after 25 minutes. Only a hard kill of the CLI leaves the claim standing; `cast kill <id>` clears it. A `cast remote back` to a laptop folder is never a checkout move, so sessions sharing that folder do not refuse it; `cast cloud start <id> --workspace shared` re-claims (exclude-self), clears the error and places it. A web create for a busy checkout never throws: the row is inserted parked with the refusal as its error and no `cloud_spawn`, so the card shows it and a later re-pick retries. A host whose `cast` predates `cast ws root` fails closed with a re-provision hint.

## Home mirror

The laptop supplies personal agent context and project documents to cloud hosts. Discovery is recursive and independent of Git ignore rules: instructions, overrides, working notes, rules, skills, plugins, prompts, hooks, scripts and their portable support files travel together. `AGENTS.md` and the `CLAUDE.md` symlink are also tracked in this repository, so fresh clones carry its development rules.

| Source | Coverage |
| --- | --- |
| Personal agent directories | `.claude`, `.codex`, `.gemini`, `.grok`, `.opencode`, `.agents` and `.config/opencode`, including shared skill symlink aliases and portable plugin content |
| Project context | Nested instruction files, Markdown and other text documents, agent configuration, `.mcp.json`, docs/scripts/support directories and referenced files, including ignored and untracked files |
| Supporting context | In-home file references, relevant ancestor instructions and Claude project memory directories; transcripts and process state are excluded |
| Git preferences | An allowlisted global configuration block and global ignore file; host Git identity and access remain owned by host provisioning |

Symlinks are resolved into regular files at their logical destination, so every agent sees its own skill namespace. Cycles terminate; references and resolved paths use the same exclusion and size checks as ordinary files. Portable text receives home and project path rewrites. Binary support assets retain their bytes. macOS commands and paths can still require host tooling; copying a script does not install its interpreter or make an Apple framework available on Linux.

Credentials, session transcripts, databases, sockets, caches, dependency installations and native executables are excluded. Structured configuration is scrubbed of credentials and provider routing before transmission. Portable MCP definitions are retained; their authentication and host dependencies need the provisioning path. Explicit include paths cannot bypass the denylist. From `~/.local/bin` only portable text scripts travel: a script whose shebang names an interpreter inside the laptop home (a uv, pipx or npm launcher) is skipped, since that interpreter is not on the host, and every name the host installs there itself is denied — `cast`, `codecast`, the gh wrapper, the agent CLIs, and the runtimes — so a laptop file never replaces a working host tool. Inventory or parse failures prevent a success report, and the 256 MiB cap fails with a diagnostic instead of silently truncating coverage.

Codecast-owned snippets, hooks and settings remain host-managed. The receiver preserves Claude authentication environment pins from `~/.codecast/mirrored-claude-env.json`, Codex project trust tables and unrelated host configuration, then runs the host refresh step. A failed refresh leaves the mirror incomplete. Files are written atomically as `0600`, or `0700` when executable. Existing same-directory `CLAUDE.md`/`AGENTS.md` aliases are supported; other destination symlinks are refused.

The receiver stores the source generation and the bytes it actually wrote in `~/.codecast/mirror.json`. Later updates reconcile against that baseline. Removed source files and configuration keys are removed only where the mirror still owns them; host edits remain in place and are reported as conflicts, including when both sides changed. The sender never labels a partial apply or conflict current. A first copy can update an older tracked document when its bytes and executable bit still match Git HEAD and the index; dirty or untracked differences remain conflicts. This is a one-way context mirror; cloud edits are not copied back to the laptop.

Project source-to-target mappings live in `~/.codecast/browser/mirror-projects.json`. Repository registration happens after checkout creation, and worktree registration happens before the agent starts. Periodic refresh applies context to registered targets without resetting their source code or running dependency installation. With mirroring enabled, an initial sync failure stops placement rather than starting an agent without its instructions. Disabling mirroring explicitly opts out of that requirement. Existing targets require registration. A deleted target is retired without recreating its directory or deleting retained work; other unsafe-target errors remain visible.

The sender starts another scan one minute after the previous pass finishes and verifies remote file bytes, type and mode on a 30-minute cadence. Scan time depends on the amount of context. It serializes pushes, retries failures with backoff, and never wakes a sleeping host. A matching local generation avoids an upload on the fast path; verification checks the destination itself, not merely the saved receipt. The scheduler can be stopped and its active transfer settled during shutdown.

```sh
cast hosts sync --dry-run
cast hosts sync
cast hosts sync i-084309c56a91e15ff --take-over
cast config cloud_mirror_enabled false
cast config cloud_mirror_exclude ".claude/skills/private-*/**,.codex/prompts/**"
cast config cloud_mirror_include ".dotfiles/skills"
```

`cast hosts sync --dry-run` reports files, exclusions, scrubbed settings and compatibility warnings. `cast hosts ls` reports the last sender result. Another laptop's ownership requires explicit `--take-over`; a different user or target home is refused.

File freshness and loaded instructions are separate. An agent that is already running may retain the instructions and configuration it read at startup. Sync updates its files without forcibly restarting its work; start a new session when a changed instruction or configuration requires a reload. Skill hot reload depends on the agent. A verified disk generation is not a claim that every active model has re-read it.

## Logins and CLIs on the host

The laptop's agent logins reach the host the way the Claude credential does — one way, over ssh stdin, never through Convex — as **one agent-auth bundle** per host applied by a python3 receiver (`remote/agentAuth.ts`, `remote/agentAuthReceiver.py.ts`): codex `~/.codex/auth.json`, grok `~/.grok/auth.json`, gemini `~/.gemini/oauth_creds.json` (+ `google_accounts.json`), opencode `~/.local/share/opencode/auth.json`, pi `~/.pi/agent/auth.json`, and the provider-key slice of `~/.claude/settings.json`'s `env`. Each file is gated by what its harness does with the grant: codex ships only with a live access-token JWT (its refresh rotates the refresh token; an API-key login ships as is), gemini only with a `refresh_token` (Google does not rotate it, and `expiry_date` is the one-hour access token), grok with any scope entry holding a `key`, opencode/pi per entry (expired OAuth entries dropped). A file the laptop lacks is removed on the host only when this same laptop pushed it (the host's `~/.codecast/agent-auth-origin.json` records the pushing device per path): a `codex logout` on the laptop that owns the grant logs the host out of it, while a second laptop of the same user, or a login made on the host itself, is never deleted by a laptop that lacks the file. A file its gate refuses is skipped and reported (`codex login not pushed: access token expired — run codex login on this machine`), and the host keeps what it has. The env slice is an allow-list — `*_API_KEY` and the provider-key registry names, never `ANTHROPIC_API_KEY` (it would move every claude on the box off the subscription), base URLs, proxies, `CLAUDE_CONFIG_DIR`, codecast's own vars, or any value that is a path, loopback, or contains the laptop home — merged into the host's `settings.json` with a manifest (`~/.codecast/mirrored-claude-env.json`) so removals propagate; the file goes 0600 once it carries a mirrored key.

On the host the receiver runs under `umask 077` and `~/.codecast/mirror.lock`: it refuses a bundle whose `user_id` differs from the host's `~/.codecast/config.json` (exit 3, nothing written; the stamp `~/.codecast/agent-auth-origin.json` decides only when config.json has no user), writes 0600 files into 0700 dirs atomically, keeps a host `~/.codex/auth.json` whose `last_refresh` is newer than the bundle's (`kept: codex host-fresher` — a codex session on the box rotated the grant; run `codex login` on the laptop to re-own it), deletes the host's codex profile snapshots whenever codex auth is carried or removed, and appends `[projects."<path>"] trust_level = "trusted"` to `~/.codex/config.toml` for the repo checkout (worktrees under a trusted checkout inherit it) and for a `cast remote move`'s directory. The host daemon never refreshes or re-snapshots a pushed codex login on a timer (`maintainCodexUsageSnapshot` / `maybeAutoSaveCodexAccount` are guarded on remotes); only a running codex session can rotate it.

When it runs: step 1 of `readyHostHome` — every prepare, `cast cloud wake`, `cast hosts wake`, provisioning — plus the laptop daemon's credential cadence (a start backfill, a 30-minute unconditional push, a 60-second tick gated on a **per-host** bundle hash so a host that slept through a change converges on the next tick, and a watch on the exact source filenames). Hosts are never woken for a push. `cast hosts sync-auth [id]` pushes on demand and prints the per-source outcome.

**CLIs and project tools.** Provisioning installs the agent CLIs at the laptop's versions when missing (claude, codex, gemini, grok — `browser/provisionAgents.ts`) and a user-local Node 22 under `~/.local/node-<ver>` symlinked into `~/.local/bin` and `/usr/local/bin`, which shadows apt's node 18 on the daemon's PATH without replacing the distro package novnc depends on. Every prepare and wake then runs the host tools check (`cloud/hostTools.ts`; `cast cloud wake`, the daemon's six-minute wake path, checks without installing): the laptop's own agent CLIs, Node per the installed convex package's `engines` (else the repo's `.nvmrc`/`engines`, never below 20; the laptop's own node is only a hint, capped at the 22 the step can install, and a repo pinned above that is reported, not downloaded), bun at the laptop's version, gh, uv when a mirrored hook or skill calls it, and every helper command named by `settings.json` hook commands or the shebang/first tokens of `~/.claude/hooks/*.sh` and `~/.claude/skills/**/*.sh` — installed user-locally with pinned versions and bounded downloads (`~/.local/bin`, `~/.bun`, never a system package, never sudo for a package), the rest reported as missing with the referencing file. Mach-O executables under those dirs are reported by path as unsupported and never copied or executed. The result is one line — `tools: N ok, M installed, K missing, U unsupported` — on `cast hosts ls` (`--verbose` lists them), `cast cloud wake`, the provision report, and `cast hosts tools [id]` (`--check` reports without installing).

**MCP servers.** The laptop config stays canonical; every Linux adjustment is reported, never silently applied. The tools check classifies each `[mcp_servers.*]` in `~/.codex/config.toml` and each stdio `mcpServers` entry in `~/.claude.json` as **ok** (resolves on the host), **missing_portable** (an `npx`/`uvx`/`bunx`-launched or otherwise installable command not there yet), or **unsupported** (a `.app` bundle, a `/Applications`/`/opt/homebrew` path, a Mach-O binary — nothing on Linux runs it; a browser/computer-use server's diagnostic points at `cast browser` on the host's Chrome instead). Unsupported servers are pinned in the host-side manifest `~/.codecast/host-mcp-overrides.json` (`cloud/hostMcpOverrides.ts`; the readiness path is its sole writer, re-evaluated on every run: pins added for newly unsupported commands, dropped for ones that became resolvable). Today the mirror ships no MCP server at all (`[mcp_servers.*]` and `mcpServers` are host-owned and dropped by `cloud/mirror/transform.ts`), so an unsupported server is never enabled on the host; the manifest is what lets the mirror ship the portable ones later — `maskPins` before its merge, `enabled = false` on the host's copy of a pinned codex server, omission from the host's `~/.claude.json` for a pinned claude server (Claude Code has no per-server flag there) — and a pin whose `source_command` no longer matches the laptop's is dropped on the next readiness run, so a server changed on the laptop is re-classified. `cast hosts tools` and the readiness log print each entry with its name, command, reason and what was done.

## Git push access from the host

A cloud host has two ways to push, and it prefers the one nobody has to grant.

**The GitHub App installation token.** Codecast's GitHub App is already installed on the repositories these sessions work in, so the host can borrow that installation instead of holding a key. The host's `~/.gitconfig` points github.com's credential helper at `cast git-credential` (with `credential.useHttpPath` on, without which git names no repository), and git runs it on every fetch and every push. The helper reads the request on stdin, asks `cloud.hostGitCredential` for `owner/name`, and prints `username=x-access-token`, `password=<installation token>` and `password_expiry_utc`. The server authenticates the caller's api token, checks the calling device is an `is_remote` device of theirs, resolves the installation their team or their person holds for that repository (`githubApp.installationForRepo`, the same rule issue sync uses), mints through `githubApp.getInstallationToken` and its shared cache, and refuses unless the minted token's `contents` permission is `write`. A TEAM's installation covers every repository the team installed the app on, which is wider than one member's own access, so minting from one first asks GitHub, with that person's own OAuth credential, whether they may push to the repository (`viewerCanPush` reads `permissions.push` on the repository); a person with no linked GitHub account, or without push, is refused and falls through to the device key. A person's own installation is their own access and is minted at once. The token lives an hour, and is never written to disk: it goes to git's stdin protocol and the process exits. A refusal is silence — no output, exit 1 — so git falls through to the next helper; `cast git-credential --why get` prints the reason for a human asking on purpose.

**What the token reaches.** The mint asks GitHub for that one repository and for push access only, so a token read off the host authenticates a push to the repository git was working in, not to every repository the installation covers. An App without write access cannot yield one at all, because GitHub refuses a scoped mint asking for a permission the installation does not hold. What this does not narrow: anything on the host that can read the api token can ask for any repository the owner's installations cover, one repository at a time. Scoped tokens are cached in their own `github_installation_tokens` rows, one per installation and repository, so they never answer for the installation-wide token the server's own work uses.

**Two rules the helper lives by.** git reads the helper's stdout as the credential and throws away an answer whose first line it does not know, so git's invocation of the verb bypasses the CLI lifecycle (`fastPath.ts`) the way the SessionStart hook does. An update notice printed ahead of the credential would otherwise fail every fetch and every push on the host, and the readiness probe applies git's own rule (first line `username=`) so it cannot report push access on output git would reject. And the call to the server carries a 15 second budget, because git cannot interrupt a helper: without it a stalled endpoint stalls the git command itself. For the same reason the script sets `core.askPass=/bin/true` when the host has none. git has no per-url form of that key, so it reaches every https remote on the box, which is what a machine with no human at it wants: a credential prompt fails instead of blocking an agent's pane forever.

**gh uses the same token.** gh reads `GH_TOKEN` from its environment, and `~/.config/gh/hosts.yml` never reaches the host, so host git readiness installs a small wrapper at `~/.local/bin/gh` (`cloud/ghWrapper.ts`), which is first on every agent's PATH. On each call the wrapper asks `cast git-credential get` for a token, exactly as git does, exports it as `GH_TOKEN` and execs the real gh. With `-R owner/name` or `--repo owner/name` it asks for that repository; otherwise the helper reads the origin of the current directory. The token lives only in that one gh process, so it is never on disk and never stale. When the helper has nothing (no repository here, no installation, no network), gh runs as it would without the wrapper. An explicit `GH_TOKEN` or `GITHUB_TOKEN` wins, a github.com login made on the host with `gh auth login` wins (the wrapper checks gh's own `hosts.yml`), a `GH_HOST` other than github.com is left alone, and `gh --version` and `gh completion` never ask. The host tools step installs a downloaded gh at `~/.local/libexec/codecast/gh` and writes the wrapper in front of it, and the git step moves any other real gh found at `~/.local/bin/gh` there too; the wrapper finds the real gh there first, then anywhere else on PATH, and skips any file that carries its marker line. The host tools check counts only a real gh, so a host with just the wrapper still gets gh installed. What gh can do is what the token allows: one repository, `contents: write`. Reads of public data and of that repository's contents work; calls that need other permissions (opening a pull request, reading Actions runs, issues) answer 403 until the mint asks for them.

While that path answers, the host's checkout keeps the **https** origin (`hostProbeOrigin(origin, { appToken: true })`), which is the spelling an http password can authenticate, and `refreshRemoteCheckout` clones, fetches and sets `origin` to it. So a repository covered by the App needs no human step at all: no key to add, no bridge to keep up.

`cast hosts ls` names which path is live per host — `app-token`, `device-key`, `agent-bridge` or `none` with the reason — and `cast hosts key` says "pushes … with a codecast GitHub App token — no key to add" instead of printing a key to paste when the token path answers.

**The device key** is the fallback, for every repository the App does not cover, and it is probed and reported on every prepare whether or not the token path answers. The host pushes with its own key — `~/.codecast/git/id_ed25519` on the box, the same file `gitIdentity.ts` publishes through the daemon heartbeat as `devices.git_pubkey`. Nothing secret crosses Convex, and the daemon's git sweep, the WIP snapshot pushes and any agent's `git push` share one identity. Every wake and prepare runs one idempotent script on the host (`ensureHostGitReady`, `cloud/hostGit.ts`, step 2 of `readyHostHome`): it pins GitHub's published host keys into `~/.ssh/known_hosts` (a stale pin fails closed into the laptop transfer path), writes a marker-fenced `Host <origin host>` block in `~/.ssh/config` pointing at the device key, mints the key eagerly, mirrors this laptop's `user.name`/`user.email` (+ `push.autoSetupRemote`) into the host's `~/.gitconfig`, and probes **read and write separately** — `git ls-remote` alone only exercises upload-pack, so a deploy key added with GitHub's default read-only setting would look granted while every push failed; `git ls-remote --upload-pack=git-receive-pack` needs no checkout and answers the question before the clone exists (the read probe asks for `HEAD`, not a branch name, so a `master` repo reads as granted too). It then probes the App path on the same repository's https origin: it asks `cast git-credential` exactly what git will ask it and fetches with what came back. That probe deliberately does not use `--upload-pack=git-receive-pack`, because smart HTTP ignores the option; the server decides the push right instead, by refusing to mint a token without `contents: write`, so a helper that answered holds a pushing credential. Both results land in the laptop registry (`gitAccess`, `gitAppAccess`) so `cast hosts ls` can say them without ssh, and `cast cloud start`'s JSON carries both under `git_access`, whose `path` names the credential this host pushes with now.

**The device key is an ssh credential, so the host needs an ssh origin** (and it is used only when the App token path did not answer). A GitHub `https://` origin (what `gh repo clone` and the clone button produce by default) is spelled as its ssh form on the host — the probe runs against `git@github.com:owner/repo.git`, `cast hosts key` says "probed as …", and `refreshRemoteCheckout` clones/fetches and sets the host checkout's `origin` to that form, so an agent's push and the WIP snapshot push authenticate with the granted key. The laptop's own checkout and its fallback transfers keep the https origin and the laptop's credentials. Any other `https://` origin cannot be guessed: it is reported as "not ssh — the host's key only works over ssh" with no probe (an https probe would report push access the key can never provide), and the agent bridge below is the way to push there.

```sh
cast hosts key i-084309c56a91e15ff            # boot if asleep, print the key, probe the repo here
cast hosts key --repo git@github.com:o/r.git --check
cast hosts key --grant                        # gh auth status, then gh repo deploy-key add … --allow-write, then re-probe
cast hosts provision --git-identity "Name <email>"
```

**Grant it as a deploy key with write access** (recommended: one repo, and GitHub's default for a deploy key is read-only — `cast hosts ls` shows "read-only key … re-add it with write access" when that happened). The account-level key at `https://github.com/settings/ssh/new` is labelled *broad access* everywhere it is offered: it grants every repo you can reach, and the private key sits on the box as the user every agent session runs as (with passwordless sudo), so any agent there can use whatever the key can reach. A public key registers once across GitHub, so a second repo's `--grant` fails with "already in use"; the CLI explains the choice (remove it there, or use an account key). The devices page card says the same.

Identity: the host's commits carry the laptop's identity, resolved from the repo being prepared (so an `includeIf gitdir:` profile applies), else the laptop's global config, overridable with `--git-identity "Name <email>"` on `cast hosts key` and `cast hosts provision` — the escape hatch for a bot-owned box, which the CLI cannot detect. When there is nothing to mirror and the host has no global identity, the script writes `codecast <codecast@local>` **globally** rather than letting git invent `Ubuntu <ubuntu@ip-…internal>`; the repo-local placeholder that `cast remote move` used to write is gone, and an existing one is unset only after a real identity was mirrored. The `IdentitiesOnly` line of the ssh config block is `yes` once the device key is proven to push and `no` after a probe refused it, so while a bridge (below) is up a laptop agent full of unrelated keys cannot exhaust GitHub's six auth tries before the granted key is offered; a run that probes nothing (`cast hosts wake`, `cast cloud wake`, a provision outside a repo) keeps the registry's last word rather than resetting it.

Fallback, opt-in: `cast hosts forward-agent <id>` makes this laptop's daemon hold one dedicated ssh connection (`ControlMaster=no`, its own keepalives, `ForwardAgent=yes`) whose remote side links the forwarded socket to `~/.codecast/ssh-agent.sock` and blocks as `cast-agent-bridge` until the connection closes; the host daemon exports `SSH_AUTH_SOCK` there for every session and its own git. **Security note: while the bridge is up, every key in your laptop's agent is usable by any process on the host — an agent session included.** `--off` closes it within a minute. It requires the version-2 idle watchdog (`cast hosts provision`, idempotent), which subtracts live bridges from the inbound-ssh count so the bridge cannot keep the box awake; `forward-agent` refuses on a host provisioned before it. A host whose sshd forbids forwarding is logged once and not retried until toggled; any other exit backs off from one minute to five (a bridge that lived two minutes starts the count over), and a host whose address changed is reconnected at the new one.

"Works with the laptop closed" holds when the host is in the server's `CAST_CLOUD_WAKE_HOSTS` allowlist (server-side wake, above); otherwise a laptop daemon performs the wake, and `cast hosts ls` cannot tell the two apart yet.

## Browser logins on the host

On the cloud host `cast browser sync <site>` is a request, not a carry. The host has no Keychain (`chromeEncryptionKey` is null off macOS), so the verb asks the owner's laptop daemon to run the same decrypt and inject step it already runs for the laptop's own browser. The path: the host CLI calls `cloud.requestBrowserSync`, which writes a targeted `daemon_commands` row (`cloud_browser_sync`); the laptop daemon runs `cast cloud browser-sync` in a child; the child opens a short SSH port forward (`withCdpTunnel`, `ssh -N -L 127.0.0.1:<local>:127.0.0.1:<host cdp port>`) and runs the unchanged `provisionLocalLogins` against the host Chrome's CDP port. Convex carries device ids, the host Chrome's loopback CDP port, the site **origin** (never a URL, whose query can hold tokens), an optional conversation id for attribution and the `all` flag; the answer carries counts. A conversation id that does not run on the host is dropped from the row, never a refusal, because it is attribution only. Cookies cross exactly one wire, laptop to host inside the SSH forward, into Chrome's memory, and Chrome alone persists them in its own profile. Nothing that looks like a cookie touches Convex, either daemon log, or the host disk outside Chrome's profile; the child's only stdout line is `{ok, injected, sites?, rejected?, host, reason?}`. The host verb runs on both drivers (the host has the built-in CDP driver, the laptop the engine driver; `browser/sync.ts` is the one body). It ensures the managed browser through the driver's own recovery so a stale `instance.json` is replaced and the **live** port goes in the request, and waits `--wait` seconds (150) polling `cloud.commandOutcome`. `--wait 0` prints the request id and returns; a `--wait` that is not a whole number of seconds is refused, as is a site together with `--all`.

Google is never carried. `keepsOwnLogin` refuses it on the host before any request and again inside `provisionLocalLogins` on the laptop, and the host has no Google account of its own, so a Google sign-in wall on the host has no fix here. The allowlist is applied twice: the host's project and machine policy (`refuseNavigation(…, "sync")`, recorded in `audit.jsonl` like a refused `open`) before the request, and the laptop's **machine** policy (`browser_allow` in its `~/.codecast/config.json`, `loadMachinePolicy`, never a project manifest walked up from the daemon's cwd) before anything leaves the laptop. `--all` (the whole cookie jar) is refused under any allowlist on either side, and the laptop refuses it for every host whose entry in its `~/.codecast/browser/hosts.json` does not set `"browserSyncAll": true`, because any process on the host can ask for a carry and name any loopback port, so the laptop cannot prove the listener is the managed Chrome; without a site and without `--all` the host prints the usage line. The local carry paths on the host (`carryLogins` on `open`, the local branch of `sync`) return at once on a remote device instead of failing late on the missing Keychain.

The laptop that carries is the owner's most recently seen **online** local device, or `--via <device-id>`, which must be online and local. An owner with several laptops whose newest laptop never provisioned the host names the one whose `hosts.json` holds it. A carry is never parked: with no online laptop the mutation refuses (`No online laptop can carry your logins …`) and the host prints it with the retry line. A request the laptop does not pick up within the rail's 5 minute TTL comes back as `expired_ttl` ("your laptop never picked the request up … asleep, or its daemon stopped"); an old laptop daemon answers `Unknown command` ("your laptop's cast is older than this host's"); a Keychain failure names the fix (run `cast browser sync <site>` once in a laptop terminal and click Always Allow; the `security` call is capped at 45 s so an unanswered prompt cannot wedge the child); a laptop without the host in its registry names `--via`. The laptop never wakes a host for cookies: it tries the registry address, and when that is dead asks AWS for the instance's state and current address (describe only, never start). A host rebooted by a server side wake gets its new address recorded through `patchHost`; a stopped or pending host is "never woken for cookies".

Concurrent requests for one host serialize on the laptop behind the running carry, however many are parked, so there is one tunnel per host at a time (the next one sees "already has the same cookies"). Nothing retries on its own; only a new `sync` opens another SSH connection. The server refuses a new request while 5 of the user's requests from the last 5 minutes are still unanswered. Two layers make sure a stuck carry cannot leave the forward behind, because one established connection to port 22 keeps the host's idle watchdog from ever sleeping the box: the child closes its own tunnel and fails at `BROWSER_SYNC_CARRY_DEADLINE_MS` (30 s under the daemon's 3 minute cap), and the daemon runs the child in its own process group and kills the whole group at the cap, since a plain SIGKILL of the child would skip the `finally` that closes ssh. A host can opt out of every carry with `"browserSync": false` on its entry in `~/.codecast/browser/hosts.json` (edited by hand today; a future switch writes through `patchHost`). Set it on a host shared with teammates, since any session on the host, including one a teammate steers, acts as the owner and can request any site other than Google that the allowlists admit.

Carried cookies persist on the host in `~/.codecast/browser/profiles/default` (a 0700 directory; Chrome writes its `Cookies` db 0600), where Chrome on Linux without a keyring encrypts them under a fixed key, so they are readable by every session on the box (same Unix user) until `cast browser stop --wipe`. Every sign-in landing on the host names `cast browser sync <host>` (not the extension, not `cast browser login`) and the note about the host's address: it is a datacenter IP, so Google and DuckDuckGo may show a bot wall to the host's AWS address regardless of login; Bing works.

## Where a cloud session starts

An isolated cloud worktree starts, by default, where the person is: the checkout on the laptop that prepares the host — its branch, its HEAD (unpushed commits included) and its uncommitted and untracked files. The opt-out is **origin/main**, a clean worktree at the host's refreshed `refs/remotes/origin/main`, which is what every cloud session got before. The choice is a launch option: the composer's `start from  [my checkout] [origin/main]` control in cloud mode (persisted per device as `clientUI.cloud_start_from`), `--from checkout|origin-main` on `cast spawn --cloud` and `cast cloud start`, `--start-from` on `cast fork --cloud` (its `--from` already names the fork point). It is stored on the row as `cloud_start_from` (absent = checkout), rides the `cloud_spawn` args as `start_from`, and a change on a preparing row re-parks it like a folder change. A shared checkout never seeds from a laptop tree: `cloud_workspace: shared` forces origin/main, the composer pins the control there while the shared toggle is on, and `cast spawn --shared --from checkout` is refused.

The seed is a non-destructive WIP snapshot of the laptop tree (`createWipSnapshotStrict`: a temp index, `git add -A` under `.gitignore`, plus explicit excludes for `.codecast/workspaces`, `.codecast/worktrees` and `.codecast/logs`, so a workspace's Chrome profile never travels even when the repo does not ignore `.codecast`), taken once per fan-out. It is force-pushed over the same shell-quoted ssh transport as the rest of the transfer to a hidden ref `refs/codecast/cloud/<worktree-name>` in the host's main repo — never `refs/heads/*`, so `git ls-remote --heads` does not list it and the host's main checkout is never disturbed — and only after the host has reserved the worktree name, so a refused name leaves no copy of the laptop's uncommitted tree behind; any later failure deletes the ref. The host's own `cast ws acquire <name> --branch <laptop-branch> --alt-branch <laptop-branch>-<hex> --start-point refs/codecast/cloud/<name>` creates the worktree at the snapshot with argv-only git calls: the laptop's branch name first, and `<branch>-<hex>` (hex = the worktree name's suffix) only when git itself reports the primary name exists, so two preparers racing for `feat/x` both succeed and neither ever attaches to an existing branch or directory. `main` on the laptop lands on `main-<hex>` because the host has a local `main`; a detached laptop HEAD seeds `codecast/<name>`. The host's acquire itself runs `git reset --mixed <laptop HEAD>` the moment the worktree exists (a start point whose commit is a codecast WIP snapshot starts at its parent; any other commit-ish is the base as is), so the branch never points at the snapshot commit, not even when install fails a moment later; the laptop then proves the result (HEAD is the laptop HEAD, the ref's tree is the snapshot's). A record whose branch landed on the alternate name says so from that moment, so a failed creation is released and healed on its own branch, never on the primary's owner. A start point never reuses a workspace name: an existing record is an error. Secrets still arrive only through the manifest copy (`setup.copy`), never through git.

Which machine seeds: the server prefers, as preparer, the online laptop whose `local_project_roots` holds the row's repo, so the seed comes from the machine the project was picked on; the seed records `device_id`. `cast cloud start` refuses to seed when the row's `git_remote_url` names a different repository than the laptop checkout's origin (scheme, user, `.git` and slashes ignored), and a cwd inside a linked worktree seeds and stages from that worktree while the host repo is named after the main repo (`resolveSeedRoots`).

What is recorded: `cloud.placeConversation` (and the CLI spawn and fork inserts) stamp one object, `cloud_seed` — `source`, the full base commit, the laptop `branch` (absent when detached), `dirty`, `laptop_root`, `device_id`, `reason`, `at` — immutable placement-time truth beside the daemon's live `git_commit_hash`. It shows as `@<base7>` after the worktree name in the header pill and the inbox chip, as "Started from feat/x @ abc1234 + uncommitted changes (/Users/me/app) on <laptop>" (or "Started from origin/main @ abc1234 — <reason>") in their tooltips, and as `feat/x@abc1234+` on `cast hosts ls` and in `cast spawn --json`.

Automatic downgrades to origin/main happen only when the checkout cannot be a seed in principle — not a git repo, no commits — or the host's `cast` predates `--start-point` (its `cast ws acquire --help` is asked once per host and process; `cast hosts provision` fixes it); each is recorded as `cloud_seed.reason`. A probe that never got an answer (ssh refused, timed out), or a snapshot, push, acquire or reset failure, with "my checkout" requested is fatal, with the tool's own line, never a silent origin/main; only a real answer is remembered. `cloud_seed.dirty` is what the seed carries beyond the laptop HEAD, so untracked content under the excluded dirs never claims uncommitted work.

Seeded worktrees stay collectable. The workspace state (`state.json`) records `startPoint` and `seedBase`; the worktree GC treats a seeded worktree whose HEAD is still the seed base and whose tree (snapshotted the same way, same excludes) still equals the seed snapshot as holding no host-made work and releases it although it is dirty and ahead of origin/main, and the release — like `cast ws destroy` — deletes the seed ref and the branch when its tip is still the seed base. Anything the host changed keeps the worktree with "changes since the laptop seed" until `cast ws destroy`; a seed ref with no state behind it is listed by `cast hosts ls` as `seed ref only (orphan)`. `cast ws heal` rebuilds a seeded worktree whose directory is gone from its start point and base. Server-side wakes never re-seed: a wake resumes the worktree on disk, and a retried `cast cloud start` mints a fresh worktree name.
